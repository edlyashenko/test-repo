# Урок 6. Практика: що беремо в наступну задачу

У пʼятому уроці ми збирали докази для конкретної версії `session-index`: списку сесій у нашому навчальному застосунку. Тепер зʼясуємо, що цей досвід змінив у способі роботи. Почни з [теорії](theory.md), потім повернися до восьми кроків нижче.

Результат практики невеликий: один файл `docs/practice/06-delta.md`. У ньому порівняємо конкретні дії до курсу й на цій задачі, розберемо один висновок і виберемо наступну дію. Новий застосунок, ще один скіл або повторний запуск усіх тестів для цього не потрібні.

## Як працювати разом із відео

Коли лектор відкриває документ, відкривай свою версію того самого документа. На відео достатньо розібрати один рядок порівняння та один висновок. Решту заповни на паузі. У тебе можуть бути інші результати перевірок, а суттєве незакрите зауваження з уроку 5 може залишитися наступною дією. Приховувати його заради завершення уроку не треба.

## 1. Відкрий ту саму роботу

Де лежить твоя реалізація після уроків 4 і 5? Через **File → Open Folder** відкрий її теку в редакторі. Не завантажуй чистий кіт поверх цієї роботи: у виданому початковому стані S0 фіча ще не реалізована.

Через **Terminal → New Terminal** відкрий термінал у корені проєкту. Ці команди лише показують стан:

~~~sh
git rev-parse --show-toplevel
git branch --show-current
git status --short
git rev-parse HEAD
~~~

Подивися на шлях і назву гілки. Не перемикайся на гілку з назвою `practice` лише за прикладом: потрібна саме твоя робота.

- [ ] Знаю, яку копію проєкту відкрито; сторонні зміни не видалено.

## 2. Прочитай рішення з уроку 5

Якої версії стосуються перевірки та яке рішення записано? Відкрий `docs/practice/05-verification.md`. Знайди `CANDIDATE_COMMIT`, докази за вимогами, незалежне ревʼю та своє рішення про приймання. `FEATURE_BASE_COMMIT` лишається початковою межею з четвертого уроку.

Поточний `HEAD` може відрізнятися від кандидата через пізніший коміт самої записки. Це не переносить перевірку на нову версію. Якщо після кандидата змінено код, тести, вимоги чи налаштування перевірок, зазнач це: для приймання нового стану потрібно повернутися до [уроку 5](../lesson-5/README.md).

Для цього підсумку можна використати наявні докази з їхньою датою та версією. Не треба запускати тест ще раз лише заради свіжої дати. Якщо документа чи доказу немає, познач прогалину; не проси агента відновити успішний запуск із памʼяті.

- [ ] Відомі перевірений кандидат, рішення та межі доказів або явно записано, чого бракує.

## 3. Створи одну підсумкову записку

Що варто зберегти, щоб через тиждень зрозуміти цей досвід? Відкрий [шаблон](../../templates/06-delta-audit.md). У ньому пʼять частин: джерела, порівняння, один висновок, наступна дія й підсумок.

У панелі файлів редактора створи `docs/practice/06-delta.md` і скопіюй у нього шаблон. Якщо файл уже є, продовж його, не замінюй заповнені відповіді. Інший варіант: надішли [запит A](prompts.md#a-підготувати-підсумкову-записку) агенту в цьому проєкті. Він допоможе з чернеткою, але особисті відповіді й рішення залишаються за тобою.

Перенеси точний `CANDIDATE_COMMIT` із записки уроку 5. Вставляй посилання на власні документи замість копіювання всіх логів. Для файлів збережи шляхи від кореня репозиторію.

- [ ] Є один підсумковий файл; результати без джерела не заповнено за мене.

## 4. Порівняй дії, які можеш описати

Що на старті було відомо про твою роботу з AI? Відкрий збережений результат першої анкети. Не переписуй його. Якщо файла немає, у колонці «До курсу» зазнач «початкового запису немає».

У §2 записки є пʼять рядків: задача, контекст, виконання, перевірка, висновки. Для кожного коротко запиши, що видно на цій `session-index`, і назви документ чи результат. Наприклад: «У spec є правило сортування; у записці перевірки є результат тесту цього правила». Якщо результату тесту немає, залиш тільки те, що справді відомо.

Один прохід показує твої дії на одній задачі. Він ще не доводить звичку «завжди перевіряю». Не обчислюй зростання продуктивності або різницю балів між різними анкетами. Без стартового запису сьогоднішній підсумок стане точкою відліку для наступного порівняння.

- [ ] Заповнено пʼять рядків; факти відділено від припущень і відсутнього досвіду.

## 5. Розбери один корисний висновок

Що в уроці 5 допомогло помітити проблему або показало межу перевірки? Обери один випадок. Підійде і вдалий механізм: наприклад, рецензент знайшов потрібне правило в spec без повторного пояснення в чаті.

Ось навчальний приклад, не готовий результат твоєї роботи. У вимогах описано порядок сесій з однаковим `mtime`, але тестові дані містять тільки різні дати. Це пояснює, чому саме цей тест не перевіряє додаткове правило сортування. Чи є помилка в самому сортуванні, без іншого доказу ще невідомо.

У §3 назви спостереження, його джерело, можливе пояснення та межу знання. Далі вибери доречний механізм: тест, автоматичну перевірку, уточнення документа або повторення вдалого способу роботи. Створювати нове правило після кожного випадку не потрібно. Якщо причини не перевірено, назви її гіпотезою.

- [ ] Один висновок спирається на власний випадок; не вигадано дефект, причину чи виправлення.

## 6. Обери наступну дію та спосіб її перевірити

Що саме ти зробиш після уроку? У §4 запиши одну посильну дію, дату повернення до неї та очікуваний доказ. Для прикладу з однаковими датами це може бути: «Уточнити тестові дані для погодженого правила сортування; перевірити, що очікуваний порядок взято зі spec». Нові тести чи код зараз автоматично не запускаємо в роботу.

Розрізняй три речі: рішення записано; механізм перевірено на визначеному випадку; його провал блокує потрібну дію. Файл із правилом не доводить двох останніх. Якщо поліпшення лише заплановано, так і напиши. Коли зміна зачепить код або перевірки, докази для нового кандидата збираємо за уроком 5.

Якщо хочеш обрати ширшу тему, є необовʼязкова [анкета наступних практик](../../final-step.html). Це інші 35 запитань: їхні бали не порівнюємо зі стартовими. Заповнювати всі 35 для завершення уроку не потрібно. HTML відкривається у браузері з локального пакета; перегляд файла на GitHub показує його код.

- [ ] Є одна наступна дія, дата й спосіб перевірки; план не названо вже виконаним поліпшенням.

## 7. Дай комусь перевірити логіку записки

Чи зрозуміє інша людина, що вже виконано і що ти тільки плануєш? Перечитай записку самостійно або передай її колезі. За бажанням у новій сесії агента надішли [запит B](prompts.md#b-перевірити-висновки-без-редагування). Спеціальний скіл для цього не потрібний.

Попроси знайти лише непідтверджені висновки, суперечності версій і незрозумілу наступну дію. Це перевірка підсумкової записки, не повторне незалежне приймання коду. Агент повертає зауваження без редагування файлів. Текстова заборона запису сама по собі не встановлює технічних обмежень доступу.

Прочитай кожне зауваження та самостійно виправ потрібні місця. Не підвищуй оцінку результату лише тому, що агент назвав записку переконливою.

- [ ] Можна простежити кожен важливий висновок до джерела або чесної позначки «не перевірено».

## 8. Збережи підсумок і визнач наступний крок

У §5 назви окремо стан фічі за уроком 5 та результат цієї рефлексії. Можна завершити записку з чесною прогалиною. Називати весь навчальний зріз прийнятим до її закриття не можна.

Збережи файл через **File → Save**. Для завершення вправи не потрібні коміт, push, PR, ship чи deploy. Пройди коротку [самоперевірку](worksheet.md). Якщо відповідаєш за команду, за бажанням вибери одне з [семи командних питань](../../templates/06-team-adoption-checklist.md).

Тепер у тебе є конкретний наступний крок. Його можна виконати самостійно. Якщо потрібне обговорення участі в основній програмі, на [чинному сайті](https://agenticengineering.it.com/) є кнопка «Залишити анкету»: це окрема заявка на консультацію щодо покупки, необовʼязкова для завершення мінікурсу.

- [ ] Записку збережено; знаю стан фічі й наступну дію; чужі обіцянки не підміняють власних доказів.
