# Запити до агента для уроку 4

Ці запити продовжують твою власну підготовку `session-index` з уроку 3. Читай [практичний маршрут](README.md) по порядку: там пояснено, що відкрити, коли зберегти базовий хеш і що перевірити після відповіді.

Команди SDD нижче вводимо в чат Claude Code, не у звичайний термінал. Для B, C і D скопіюй текст запиту та команду під ним в одне повідомлення. Перед C, D і E почни свіжий контекст після збереження результатів. Запит F використай у новій сесії одразу після A: це незалежне перечитування карти до реалізації. Відповідники для інших інструментів наведено в [уроці 3](../lesson-3/README.md#якщо-обрано-codex-або-cursor); не запускай кілька агентів одночасно на тій самій копії.

Маршрут звірено з контрактом SDD 2.3.0. Якщо встановлена версія поводиться інакше, зупинись на конкретній розбіжності. Не заповнюй відсутні входи порожніми файлами і не обходь перевірку готовності.

## A. Підготувати карту без змін коду

Заміни `FEATURE_BASE_COMMIT` у тексті своїм повним хешем після збереження документів і до реалізації. Це звичайний запит, не команда SDD.

```text
Підготуй навчальну карту виконання session-index. Початковий хеш
перед реалізацією: FEATURE_BASE_COMMIT. Якщо це ще placeholder або
хеш не існує, зупинись і попроси справжній хеш; не вигадуй його.

Прочитай AGENTS.md, CONTEXT.md, правила в .claude/rules/,
views/AGENTS.md, мою docs/architecture-map.md та документи фічі:
spec.md з inline Test plan, sad.md, Accepted ADR, tasks.json,
Markdown-файли задач і tracker, якщо він уже є.
Відкрий поточні файли коду, потрібні для перевірки цих входів.
examples/ не читай. Не запускай interview, survey або implement.

Звір готовність до реалізації: .size=S і .route=standard,
збережений навчальний override окремих UI/API-стадій, контракт HTTP
і стани сторінки в SAD та відповідних задачах. Файли задач мають
достатній контекст із підписами джерел, AC і перевірні DoD.
JSON містить справжні file/deps/files_hint; залежності без циклів.
Не перенось рішення зі свого припущення до вимог. Якщо є блокувальна
суперечність або відсутній документ, назви її та зупини підготовку запуску.

Створи docs/practice/04-workflow.md за templates/04-agentic-workflow-map.md.
Якщо карта вже є, не перезаписуй: покажи, що потрібно доповнити.
Відносні посилання налаштуй для нового розташування карти, щоб вони
вели до справжніх файлів. Пояснювальні посилання самого шаблону
не копіюй без перевірки їхнього шляху.
Поки змінювати можна тільки цю карту; runtime, тести, fixtures,
залежності, налаштування, вимоги, ADR й інструкції залиш незмінними.
Не коміть нічого на цьому кроці.

Збережи в карті базовий хеш, поточну гілку, початковий git status
і посилання на вимоги, SAD, рішення та задачі. План не переписуй:
потрібні виконавець кожного кроку, вхід, вихід, перевірка та дія при помилці.
Вибери першу доступну задачу з мого tasks.json, назви її реальний ID,
файл, AC та поясни, чому її залежності дозволяють почати.
Не підганяй кількість або назви задач під приклад лектора.

Режим першого проходу: один агент послідовно, без команди й паралелі.
Це один виконавець циклу TDD, не три ізольовані субагенти.
Незалежне рев'ю всієї зміни залишаємо на урок 5.
Запиши поля для бюджету, паузи після першої задачі та фактичних доказів.
Якщо бюджет ще невідомий, залиш питання для мене, не вигадуй суму.
Не називай запит до агента технічним обмеженням прав або витрат.

Перечитай карту: чи вистачає виходу кожного кроку для входу наступного,
чи названо конкретну дію при помилці? Покажи створений файл і прогалини.
Жодного PASS майбутньої реалізації. Пояснюй коротко й зрозуміло.
```

## B. Погодити налаштування

SDD зберігає налаштування в `.claude/sdd.local.md`. Не вставляй туди цілий новий файл. Просимо скіл змінити тільки потрібні поля та показати різницю.

```text
Налаштуй SDD для першого навчального проходу session-index.
Спочатку прочитай чинну .claude/sdd.local.md та правила репозиторію.
Якщо файла немає, створи його за канонічною процедурою встановленого
SDD і потім внеси тільки перелічені нижче зміни через config.
Не замінюй наявний файл шаблоном і не змінюй решту полів:

team_mode: false
workflow_mode: "off"
max_parallel_agents: 1
tdd: true
max_red_retries: 3
stop_on_red: true
cmd_test_unit: "npm run verify"
gate_lint: false
gate_vet: false
require_integration: "never"

Перевір, що npm run verify є в package.json. Ця команда має виконувати
потрібні файлові й HTTP-перевірки S1 разом зі збереженням початкових тестів.
never вимикає тільки окрему integration-стадію SDD з Docker probe;
це не відмова від перевірок взаємодії модулів або файлової системи.
У пакеті немає окремих lint/vet-команд для цього проходу. Не встановлюй
нові інструменти й не вигадуй успішний результат вимкненого gate.

Поля моделей, effort, мови, isolation, auto_commit і branch_strategy
залиш як є. Покажи їхній фактичний вплив на цей запуск.
Якщо модель недоступна, поясни це й погодь використання доступної
моделі або inherit через config; не змінюй моделі приховано.

Поясни різницю між max_red_retries і глобальним лімітом:
після звичайних повторів SDD може ескалувати до сильнішої моделі
або поділу задачі. У запиті implement ми окремо попросимо паузу
після трьох невдалих GREEN на одній задачі до такої ескалації.
Це додаткове правило навчального запуску, не гарантований прапорець SDD.

Покажи конкретний diff налаштувань. Код, тести, fixtures, вимоги
й документи плану не змінюй; implement і наступні стадії не запускай.
```

```text
/sdd:config
```

## C. Перша задача з контрольною паузою

Це вже дозвіл реалізувати погоджену задачу. Перед надсиланням перечитай карту, запиши власний бюджет і переконайся, що збережено базовий хеш. Пауза після першої задачі задається текстом: окремого прапорця для вибору однієї задачі тут немає.

```text
Починаємо реалізацію session-index за власним погодженим планом.
Виконай implement у послідовному режимі й зроби контрольну паузу
після першої завершеної задачі: тест, код, повний gate,
збереження результату за чинним auto_commit, оновлення tracker.
Не починай наступну задачу до мого запиту продовжити.
Якщо твій механізм не може дотриматися цієї паузи, повідом до змін коду.
Це інструкція для уроку, не підтримуваний CLI-прапорець вибору задачі.
Якщо перша задача належить до нероздільної compile-coupled групи,
поясни це до змін і погодь найменшу групу зі спільним зеленим gate.
Не роби червоний коміт заради штучної паузи посеред такої групи.

Прочитай AGENTS.md, CONTEXT.md, правила в .claude/rules/,
views/AGENTS.md, docs/architecture-map.md, docs/practice/04-workflow.md,
чинні налаштування й документи docs/features/session-index/.
Завантаж tasks.json і звір tracker з реальним станом коду та Git.
Конкретний файл обраної задачі є основним brief: прочитай його першим
для виконання. Якщо уривку недостатньо або він суперечить коду,
відкрий джерело у spec, inline Test plan, SAD чи Accepted ADR.
Не вигадуй новий ID, endpoint, ліміт або порядок однакового часу.
examples/ не читай і не копіюй.

Збережи .size=S та .route=standard і явний навчальний override уроку 3:
контракт HTTP та UI-стани беремо з SAD і задач замість окремих
OpenAPI/screens/ux-flows. Не пропускай потрібну поведінку через брак
окремого файла. Якщо в погодженому джерелі прогалина, зупинися.

До production-коду покажи banner: фактичний режим, TDD, команди
перевірок, політику Git. Очікуємо sequential, tdd=true,
cmd_test_unit=npm run verify. Окрема Docker-стадія вимкнена;
файлові й HTTP-тести все одно мають виконуватися в npm run verify.
Якщо налаштування не відповідають цьому, зупинися до виконання задачі.
Не змінюй їх поза config. Один агент виконує цикл TDD послідовно;
не звітуй про ізольованих test-author/implementer/reviewer, якщо їх немає.

Для першого тесту покажи фактичний RED і поясни клас падіння.
Помилка самого тесту потребує виправлення тесту. Не додавай чернетку
production-коду лише заради демонстрації RED. Якщо тест одразу зелений,
перевір, чи поведінка вже існує і чи тест справді відповідає новому AC.
Не вигадуй відсутню поведінку та не ламай видані тести або fixtures.
Після валідного RED додай мінімальний код, повтори перевірку,
за потреби рефакторинг і повний gate. Не послаблюй тест заради GREEN.

Працюй у межах files_hint задачі. Не змінюй вимоги, ADR, правила,
адаптери інструкцій, видані fixtures, залежності чи межі доступу
без окремого погодження. Для views прочитай вкладені інструкції.
Потрібні нові тестові дані створюй у контрольованих тимчасових теках:
синтетичні файли, відомі mtime, прибирання після тестів.
Тести не використовують shell-команди для підрахунків; звір
test/helpers.js і test/oracle.js з конкретними критеріями.
Межу читання доводь перевіркою відсутності заборонених звернень,
не лише правильним числом рядків. Особисті логи не підключай;
вміст JSONL для цієї фічі не читаємо.

Додаткова навчальна зупинка: після трьох невдалих спроб GREEN
на цій задачі зроби паузу ДО зміни моделі, поділу задачі чи нових спроб.
Покажи рядок падіння, AC, зроблені зміни й питання для людини.
Не змінюй вимоги й не відкочуй незрозумілі або сторонні зміни.
Бюджет із карти також є умовою паузи; не обіцяй технічного ліміту,
якщо доступний лише запит і людський контроль.

Після першої завершеної задачі назви її ID, AC, результати RED/GREEN/gate,
змінені файли й коміт, якщо він справді створений. Якщо auto_commit=off,
покажи незакомічені файли й нагадай зберегти їх після перевірки.
Онови tracker за фактичним станом. Зупинись. Review, ship і розгортання
не запускай; підсумковий блок рекомендацій SDD не є дозволом на них.
```

```text
/sdd:implement session-index
```

## D. Продовжити збережений прохід

Перед цим перевір першу задачу й запиши фактичний стан у карті. Запит дозволяє виконати решту погоджених задач. Якщо зараз немає часу, збережи точку зупинки й повернися пізніше.

```text

SAD і Accepted ADR. examples/ не читай.

Якщо tracker суперечить коду, зупинись і покажи розбіжність.
Не видаляй задачі з tasks.json, не змінюй ID й не повторюй завершене
лише для нового запуску. Назви наступну задачу та її готові залежності.

Продовжуй решту погодженого плану послідовно з TDD і npm run verify.
Збережи .size=S, .route=standard та навчальний UI/API override:
контракт і стани зі SAD мають виконуватися у відповідних задачах.
Окрема Docker-стадія вимкнена, але файлові й HTTP-перевірки входять
у npm run verify. Кількість тестів залежить від погоджених AC.
Покажи активний режим і команди перед роботою.

Для кожної задачі: прочитати її brief, RED із класифікацією,
GREEN, рефакторинг за потреби, повний gate, збереження за чинним
auto_commit і чесний tracker. Тест, зелений до нового коду, спочатку
зістав із наявною поведінкою й AC; не створюй штучну поломку.
Працюй у files_hint, не послаблюй перевірки та не змінюй вимоги,
ADR, інструкції, видані fixtures або залежності без погодження.
Дані тільки синтетичні, лише метадані в дозволеній межі;
нові тестові теки тимчасові з контрольованими mtime та cleanup.
Не використовуй shell-команди всередині runtime-тестів.

Бюджет бери з карти. Після трьох невдалих GREEN на одній задачі
зупинись до ескалації, зміни моделі або поділу задачі й покажи докази.
На блокувальному продуктовому чи архітектурному питанні також пауза.
Не відновлюй перерваний запуск наосліп і не стирай сторонню роботу.

Наприкінці звір усі задачі: реалізовані, заблоковані, незавершені.
Назви фактичні gate, коміти, незакомічені зміни та неперевірене.
Не називай частковий прохід готовою фічею. Зупинись після implement.
Не запускай review, ship, публікацію або розгортання автоматично.
```

## F. Перевірити карту до реалізації

Використай після запиту A, ще до запуску implement. Відкрий нову сесію без історії створення карти й передай цей запит. Документи дають достатньо контексту; переказувати розмову автора карти не потрібно.

```text
Незалежно перечитай карту виконання session-index перед реалізацією.
Це read-only перевірка способу роботи, не рев'ю готового коду.
Прочитай AGENTS.md, правила в .claude/rules/, мою карту проєкту,
docs/practice/04-workflow.md, spec із Test plan, SAD, Accepted ADR,
tasks.json і потрібні файли задач. examples/ не читай.
Не редагуй файли, не коміть, не запускай implement, review або ship.

Перевір конкретні переходи карти:
1. Чи зрозуміло, хто відповідає за кожен крок і хто погоджує результат?
   Чи немає двох ролей, які незалежно ухвалюють те саме рішення,
   або кроку, за який ніхто не відповідає?
2. Чи містить вихід попереднього кроку все, що потрібно наступному?
```
