# Урок 4. Agentic Workflows: як правильно розділяти роботу

Продовжуємо session-index після уроку 3. Спочатку розберемо організацію роботи, потім прочитаємо карту виконання й перейдемо до свого коду. Нова задача чи інший репозиторій не потрібні.

## 1. План є. Хто тепер виконує роботу?

У нас уже є початковий дашборд і задача: показати список сесій роботи з агентом. У список мають потрапляти дозволені метадані файлів: проєкт, розмір і час зміни. Порядок, ліміт та поведінку за помилок ми погодили у третьому уроці. Заново вигадувати фічу не потрібно.

План із третього уроку визначає потрібні роботи та їхні залежності. Карта workflow додає виконавців, передачі результатів і точки контролю. Можна віддати всі задачі одному агенту. Можна залучити окремого перевіряльника. Частину роботи взагалі виконує звичайна команда. Сьогодні розберемо, як обрати достатній варіант.

Уявімо помилку на нашій задачі. Агент упорядкував записи за назвою файла, хоча у вимогах зазначено час зміни. Потім написав тест із таким самим порядком. Тест зелений. Самоперевірка також задоволена, бо повторила те саме припущення. Ситуація вигадана для пояснення. Ми не видаємо її за запис фактичного запуску.

Проблема тут у тому, що ніхто не повернувся до погодженої вимоги. Окремий рецензент може помітити розбіжність, якщо прочитає spec і сам перевірить результат. Саме кількість відкритих вікон цього не забезпечить. Нам потрібен зрозумілий розподіл роботи та доказ на кожному переході.

## 2. Агент, скіл та скрипт виконують різну роботу

Почнемо з назв, які часто плутаються. Функція виконує конкретну операцію в коді. Наприклад, порівнює час зміни двох файлів. Скрипт обʼєднує наперед описані дії: запускає перевірки й повертає результат у термінал.

Інструмент, або tool, дає агенту можливість щось зробити. Прочитати файл, знайти текст, запустити команду. Сам інструмент не вирішує, що зараз корисніше для задачі. Його обирає той, хто керує роботою.

Агент використовує модель, щоб обирати наступну дію, викликає інструменти й отримує зворотний звʼязок. Побачив падіння тесту, відкрив потрібний файл, запропонував зміну. Результат попередньої дії впливає на наступну.

Скіл містить інструкції та, за потреби, додаткові матеріали чи скрипти для певної роботи. У нас уже є SDD: його скіли допомагали готувати вимоги й план. Тепер implement описуватиме процедуру реалізації. Скіл сам по собі не є ще однією людиною або окремою моделлю.

Субагент отримує виділене доручення від іншого агента. Наприклад, самостійно прочитати вимоги й перевірити змінений код. У нього може бути власний контекст і набір інструментів. Спосіб запуску визначає, яку історію та правила він отримає.

Нарешті, multi-agent workflow організовує роботу кількох агентів. Важливі питання залишаються ті самі: хто отримує задачу, хто має право змінювати файли й хто приймає результат.

[Skills і субагенти: документація Claude Code](https://code.claude.com/docs/en/features-overview). Приклади функцій тут пояснювальні; реалізація ще попереду.

## 3. Скільки свободи потрібно цьому кроку?

У брифі курсу є драбина автономності: від функції та скрипта до кількох агентів. Вона допомагає поставити питання про свободу вибору. Але механізми не стоять на одній точній шкалі. Скрипт може запускати кількох агентів за жорсткими правилами, а один агент може користуватися багатьма скілами.

Тому для кожного кроку спитай: чи відомі дії наперед? Для запуску npm run verify відомі. Модель може викликати цю команду, проте оцінювати exit code за настроєм їй не потрібно. Для виправлення причини падіння конкретні зміни ще треба знайти. Тут агент має корисну роботу.

Workflow означає організований перебіг дій. У наперед визначеному workflow переходи задані кодом або умовами. В агентному кроці наступну дію обирає модель. В одному процесі ці способи можуть поєднуватися.

У таблиці є кілька поширених патернів. Для нашої невеликої фічі достатньо ланцюжка: задача, перевірка очікування, реалізація, контроль результату. Інші патерни варто впізнавати, але не потрібно додавати кожен до вправи.

Новий агент означає ще одне доручення, контекст і результат для перевірки. Іноді це окупається. Якщо ж він лише переказує вже відомий список команд, організація роботи стає складнішою без очевидної користі.

| Спосіб організації | Як читати схему | Приклад для нашої роботи |
|---|---|---|
| Ланцюжок | Результат одного кроку потрібен наступному | Прочитати задачу → отримати тест → додати код → перевірити |
| Маршрутизація | За умовою обрати потрібний шлях | Помилка запуску → перевірити середовище; неправильний результат → перевірити реалізацію |
| Паралель | Незалежні частини виконуються водночас | Окремо читати політику даних та договір HTTP, потім звірити висновки |
| Координатор і виконавці | Координатор визначає доручення й збирає результати | Дослідити кілька невідомих частин великої зміни |
| Оцінювання й виправлення | Після оцінки вирішити, чи потрібна ще спроба | За конкретним зауваженням виправити код і повторити перевірку в межах ліміту |

[Патерни організації: Building effective agents](https://www.anthropic.com/engineering/building-effective-agents). Це класифікація матеріалу, не єдина можлива система. Приклади для session-index підібрано для уроку.

## 4. Як описати роль, щоб її можна було передати?

Фраза «ти досвідчений розробник, зроби якісно» майже нічого не говорить про конкретну роботу. Спробуй описати чотири речі: вхід, відповідальність, вихід і умову приймання.

Наприклад, автор перевірки отримує погоджений критерій сортування та опис тестових даних. Його відповідальність: перевірити порядок за часом зміни файла. На виході потрібні тест, команда запуску й фактичний результат.

Як зрозуміти, що це корисний тест? Підготуємо два синтетичні файли з різним часом зміни. Нехай один має 10:00, інший 11:00 того самого дня. Якщо очікуємо свіжі спочатку, файл із 11:00 має бути першим. Назви файлів підберемо так, щоб сортування за назвою дало інший результат. Тоді перевірка зможе відрізнити ці два алгоритми.

Виконавець отримує задачу й конкретну розбіжність. Його відповідальність: реалізувати погоджену поведінку, зберігши наявні правила доступу. Вихід містить зміну коду та результати команд. До умови завершення входить і те, що попередня поведінка не зламалася.

Поки ми описали ролі, а кількість сесій ще не обирали. Одна сесія може виконати кілька ролей послідовно. Якщо потрібна незалежна оцінка припущень, для неї організуємо окремий перегляд із власним читанням джерел.

## 5. Окремий контекст і окремі права

У другому уроці ми вчилися давати агенту потрібний контекст. Тепер цей принцип працює для окремих ролей. Автору тесту потрібні критерій і правила тестування. Рецензенту потрібні вимоги та зміна, яку він перевіряє. Кожному не обовʼязково передавати всю історію попередніх спроб.

Окремий контекст допомагає не починати перевірку з висновку виконавця «я вже все зробив правильно». Але назва reviewer нічого не доводить. Треба знати, чи отримав він історію виконавця, які файли прочитав і яку саме версію перевіряв.

Не роби висновок лише зі слова fork: різні інструменти використовують його по-різному. Для незалежного перегляду нам важлива фактична відсутність успадкованого обґрунтування реалізації. Звичайна нова розмова з точними джерелами може бути достатнім способом організувати такий перегляд.

І ще одна межа. Власний контекст не означає ізольовану файлову систему. Якщо дві сесії мають доступ до однієї теки, вони можуть змінювати ті самі файли. Прохання «тільки читай» задає правило поведінки. Технічне обмеження потребує налаштованих дозволів. Навіть без кнопки редагування запис іноді можливий через shell.

У нашій вправі працюємо з виданими синтетичними даними. Особисті журнали агента та додаткові доступи для перевірки списку не потрібні.

[Контекст та права субагентів](https://code.claude.com/docs/en/sub-agents). Конкретний спосіб запуску потрібно перевіряти у своєму інструменті.

## 6. Послідовно чи паралельно?

Після третього уроку в нас уже є залежності задач. Тепер додається питання: які з них можна виконувати одночасно без конфлікту?

Сторінка має знати, які дані отримує. Якщо контракт уже погоджено, її частину іноді можна готувати на контрольованих даних, поки інший виконавець працює над сервером. Якщо контракт ще змінюється, така паралель може закінчитися переробкою обох частин.

Окремо перевір файли. Дві задачі можуть не залежати одна від одної за змістом, але обидві редагувати server.js. Тоді потрібен погоджений спосіб інтеграції або черга. Поле files_hint допомагає побачити очікуваний перетин. Це підказка плану; під час роботи фактичні зміни теж треба переглядати.

Worktree дає окрему робочу теку Git зі своїм індексом і гілкою. Так два виконавці не редагують один набір робочих файлів. Але порт сервера, зовнішня база чи інший спільний ресурс від цього не стають окремими. І результати все одно потрібно звести та перевірити разом.

Для нашого першого проходу обираємо послідовність. Наступна задача починається, коли отримано потрібний результат попередньої. Ми побачимо весь цикл на одній задачі, а потім продовжимо решту. Ніякої вимоги запустити трьох агентів або відтворити чужі вісім задач тут немає.

[Що розділяє Git worktree](https://git-scm.com/docs/git-worktree). Спільні зовнішні ресурси перевіряємо окремо.

## 7. Що перевіряє команда і де тут CI?

Коли порядок дій відомий, його зручно записати в команду. npm run verify запускає перевірки нашого репозиторію. Код завершення показує, чи пройшов цей запуск. Нуль зазвичай означає успіх команди, ненульовий код сигналізує про помилку.

Таку обовʼязкову перевірку перед наступним кроком називаємо gate. Агент не має зараховувати її на підставі власного текстового підсумку. Потрібен фактичний запуск, а ще розуміння того, що саме команда перевіряє.

Для відтворюваності важливі дані й середовище. У нашій задачі сортування залежить від часу зміни файлів. Git цей час не переносить. Тому в кіті є підготовка дат, а власні тести мають керувати датами своїх тимчасових даних. Інакше результат може залежати від того, коли завантажили репозиторій.

Hook привʼязує дію до конкретної події інструмента. CI запускає перевірки за подіями репозиторію, наприклад після push у налаштованому GitHub-проєкті. Наявний файл конфігурації ще не доводить, що потрібний запуск відбувся. Локальна перевірка та CI мають власні результати.

Для команди це означає спільні правила: які перевірки обовʼязкові, які інструменти дозволені, хто може змінювати сам gate. Також погоджують, яких агентів можна підключати й де зберігаються спільні перевірені скіли. Інакше однакова назва процесу в різних людей може означати різні дії. Якщо виконавець прибрав перевірку заради зеленого результату, потрібно переглянути цю зміну.

Команду та події можна звірити з [package.json](../../package.json) і [CI кіта](../../.github/workflows/verify.yml).

## 8. Як зупинити роботу, яка не просувається?

Уяви, що агент уже втретє виправляє одну задачу, але потрібна перевірка досі падає. Команда «працюй, поки все не буде готово» не пояснює, коли повернути рішення людині.

Перед запуском назви умову успіху, умови зупинки й бюджет. Бюджетом може бути кількість спроб або час. Якщо сервіс дозволяє встановити технічний ліміт витрат, його також можна використати. Ліміт у тексті запиту сам по собі не створює такого обмеження в системі оплати.

Нам потрібно відрізняти три ситуації. Перша: потрібну умову перевірено, можна завершувати крок. Друга: сама перевірка не працює, тому результат невідомий. Третя: перевірка працює, але результат після дозволених спроб досі неправильний. В останніх двох випадках не можна просто написати «готово».

У SDD є налаштування повторів і зупинки. Але ліміт повторів конкретного етапу не обовʼязково обмежує весь запуск: далі механізм може пропонувати сильнішу модель або поділ задачі. Тому в практиці додаємо прохання про паузу та стежимо за фактичним виконанням.

Коли цикл зупинився, збережи конкретне падіння, критерій і стан коду. Далі можна виправити середовище, уточнити вимогу або зменшити задачу. Просте повторення того самого запиту без нових даних ще не є просуванням.

[Локальний приклад налаштувань](../../.claude/sdd.local.example.md). Повтор GREEN та подальшу ескалацію звірено з SDD 2.3.0; це не підтвердження платного проходу.

## 9. Як проходить одна задача від тесту до коміту?

Тепер зʼєднаємо ролі в один цикл. Спочатку виконавець обирає задачу, залежності якої вже виконані. Читає її файл і погоджений критерій. Якщо в короткому описі чогось бракує, відкриває джерело у специфікації чи технічному рішенні.

Далі готує тест очікуваної поведінки до зміни коду. RED означає, що перевірка виявила потрібну розбіжність. Якщо тест не зміг запуститися через неправильний імпорт або залежність, спершу треба полагодити запуск. Колір у терміналі ще не пояснює причину.

Зелений тест до нового коду теж потрібно дослідити. Можливо, потрібна поведінка вже існує. Можливо, тест нічого важливого не перевіряє. Не потрібно ламати працюючу систему лише для отримання червоного рядка. Потрібно пояснити, що перевірено і чого бракує задачі.

GREEN означає, що доданий код задовольняє перевірку. Після цього можна впорядкувати реалізацію, зберігаючи зелений результат. Далі запускаємо погоджені перевірки й фіксуємо зміни в коміті. Коміт дає точну версію, до якої можна повернутися під час перегляду.

Цей цикл називають test-driven development, або TDD. Сьогодні він потрібен, щоб бачити порядок виконання та точки контролю. У пʼятому уроці окремо розберемо, чи достатні тести, як перевіряти їхню чутливість і як незалежно приймати всю фічу.

[Процедура implement](https://github.com/genkovich/sdd/blob/main/skills/implement/SKILL.md). Урок перевірено проти локальної 2.3.0; upstream main може відрізнятися.

## 10. Читаємо коротку карту виконання

Відкрий свою копію кіта після третього уроку. У ній уже мають бути spec, технічний документ SAD, погоджені рішення ADR та задачі. У spec є розділ Test plan. Якщо цього немає, повернися до відповідного кроку підготовки. Запуск implement не має виправляти відсутні продуктові домовленості навмання.

Тепер відкрий шаблон карти виконання. Він не просить ще раз придумати задачі. Посилання на tasks.json залишаємо джерелом їхнього порядку, а в карті записуємо спосіб роботи.

Спочатку називаємо вхід і точку відліку Git. Далі визначаємо виконавця кожного кроку, потрібний результат та дію на помилку. Окремо пояснюємо, чому починаємо послідовно, які права даємо та після чого зупиняємося. Наприкінці залишаємо місце для фактичного стану.

Агент може підготувати чернетку за нашими файлами. Тобі потрібно прочитати її й перевірити конкретні переходи: чи отримує наступний крок усе потрібне, чи не загубилася перевірка, чи не додано нового непогодженого обсягу.

Потім дай карту новій сесії для окремої перевірки. Нехай знайде передачу без потрібного входу, перетин відповідальності або цикл без зупинки й пояснить можливу помилку. Переглянь знахідки та виправ карту до запуску implement. Зараз перевіряємо організацію роботи; незалежний перегляд готового коду буде в пʼятому уроці.

На цьому етапі карта є планом організації виконання. Після запуску заповнимо фактичні результати. Це один робочий документ поверх наявних задач; окремий файл передачі контексту нам не потрібен.

| Де читаємо | Що вже є або що додаємо |
|---|---|
| spec.md і його Test plan | Погоджена поведінка й майбутні перевірки з уроку 3 |
| sad.md та Accepted ADR | Технічний підхід і причини рішень з уроку 3 |
| tasks.json і файли tasks/ | Канонічні задачі, залежності та умови завершення |
| docs/practice/04-workflow.md | Спосіб виконання, права, зупинка, початкова версія та фактичний стан |
| .claude/sdd.local.md | Налаштування встановленого SDD, які читає механізм виконання |
