# Урок 4. Чи розумієш ти свій спосіб виконання?

Це коротка самоперевірка після [теорії](theory.md) та [практики](README.md). Не потрібно створювати ще один звіт. Відповідай усно або додай потрібний факт до своєї `docs/practice/04-workflow.md`.

## Перед запуском

- [ ] Можу назвати різницю між планом із третього уроку та картою виконання. План зберігає задачі й залежності; карта пояснює виконавців, передачу результатів, перевірки та зупинки.
- [ ] Знаю, чому тут достатньо одного агента. Послідовний TDD не створює трьох незалежних виконавців лише тому, що в ньому є кілька ролей.
- [ ] Можу знайти наступну задачу у власному `tasks.json`, відкрити її файл і пояснити залежності. Приклад лектора не замінює мій план.
- [ ] Розумію, що скрипт перевірки виконує задані перевірки, а агент обирає зміни коду. Зелений результат не доводить того, чого в тестах немає.
- [ ] Збережено `FEATURE_BASE_COMMIT`. Можу показати зміни від нього, навіть якщо агент уже створив коміти.
- [ ] Карту перечитано у свіжій сесії через запит F. Погоджені зауваження виправлено, а бюджет та інші умови запуску заповнено до C. Це перевірка карти, не ревʼю готової фічі.

## Чотири ситуації для перевірки розуміння

**1. Тест падає, бо в самому тесті неправильно названо імпорт. Це потрібний нам RED?**

Ні. Спочатку потрібно виправити тест і повторити запуск. Тест має показати, яка саме потрібна поведінка ще не працює. Довільний червоний рядок цього не доводить. Для цього не додаємо чернетку production-коду лише заради показу.

**2. Новий тест одразу зелений. Треба навмисно зламати код?**

Ні. Перевір, чи потрібна поведінка вже є і чи тест справді перевіряє погоджений AC. Слабку перевірку треба покращити; наявну поведінку не потрібно видавати за щойно реалізовану. Окреме дослідження чутливості тестів має власний контрольований сценарій, воно не замінює цей розбір.

**3. `max_red_retries: 3` означає, що після третьої невдачі витрати гарантовано припиняться?**

Ні. Це звичайні повтори до подальшої ескалації SDD. У вправі ми додатково просимо паузу після трьох невдалих GREEN на одній задачі до зміни моделі або поділу задачі. Людина стежить за виконанням цієї інструкції та власним бюджетом. Запит у чаті не дорівнює технічному ліміту.

**4. Перша задача завершена й має зелений gate, але сторінка списку ще не готова. Урок провалено?**

Ні, це нормальна точка паузи. Запиши частковий стан і наступну задачу. Назвати всю фічу реалізованою можна лише після завершення всього погодженого плану, зокрема сторінки й потрібних перевірок. Незалежне ревʼю всієї зміни проведемо в уроці 5.

## Що можеш показати після роботи

- [ ] Перший реальний RED: ID задачі, команду, рядок падіння та його причину. Якщо поведінка вже працювала, є пояснення й погоджене рішення щодо плану без штучного RED.
- [ ] GREEN тієї самої перевірки після потрібної зміни або підтвердження вже наявної поведінки; фактичний результат повного `npm run verify`.
- [ ] Коміт задачі або чесно позначені незакомічені зміни; tracker відповідає коду.
- [ ] Погоджену в SAD сторінку після виконання всіх її задач або запис «ще не реалізовано / не перевірено».
- [ ] Пояснення, чому шість виданих сесій не означають шість рядків за будь-якого ліміту.
- [ ] Підтвердження, що файлові й HTTP-перевірки виконувалися в `npm run verify`, попри вимкнену окрему Docker-стадію SDD.
- [ ] Карту без дубля плану, з базовим хешем, фактичним станом, бюджетом і наступною дією.
- [ ] Відсутність вигаданого висновку про пройдене ревʼю або прийняту фічу.

Якщо не можеш пояснити один пункт, повернися до відповідного кроку. Кількість галочок сама по собі не є результатом: важливо знайти документ, команду або зміну, які підтверджують твою відповідь.
