# Урок 3. Домовляємося про результат і готуємо задачі

Після другого уроку в тебе є власні `docs/practice/02-context.md` та `docs/practice/handoff.md`. Вони описують скелет S0: сервер запускається, два тести перевіряють початкову поведінку, а списку сесій на сторінці ще немає. Тепер підготуємо вимоги до першого списку й документи, за якими агент зможе почати роботу в уроці 4.

Залишаємося в цьому пакеті. Джерела задачі вже лежать у [брифі](../idea-brief.md), [дорожній карті](../roadmap.md), [карті архітектури](../architecture-map.md) та [словнику](../../CONTEXT.md). Читай їх разом із поточним кодом. Карта пояснює задум, але твердження про наявну функцію потрібно перевіряти у файлах.

Основний маршрут цього уроку використовує SDD. Це встановлюваний набір команд для агента, який послідовно записує вимоги, технічні рішення й задачі. Нижче є підготовка з нуля. Наявність агента або виконаний `npm ci` ще не означає, що SDD встановлено.

## Спершу звір початковий стан

Відкрий термінал у корені пакета, поруч із `package.json`. Якщо залежності ще не встановлені, виконай `npm ci`. Потім запусти:

```sh
npm run verify
npm run demo
```

Для незміненого S0 очікуємо два тести й повідомлення «No slice is wired up yet.» на [локальній сторінці](http://127.0.0.1:4180). Збережи свій фактичний вивід. Це перевірка скелета; нову функцію вона ще не підтверджує. Після огляду зупини сервер через Ctrl+C.

Працюй через `demo`: скрипт `scripts/demo.mjs` задає абсолютний шлях до синтетичних fixtures цього пакета й порт 4180. Він не читає `.env.fixtures` і не бере іншу теку з успадкованих змінних термінала. `npm start` без налаштувань може звернутися до справжньої домашньої теки Claude; для вправи це не потрібно. Якщо стан твоєї копії відрізняється, спершу зʼясуй версію й власні зміни. Не підганяй вивід під число зі слайда.

## Підготуй SDD

У показі використано Claude Code. Відкрий його в корені пакета й введи ці команди по черзі. Це команди всередині агента, не команди термінала Node.

```text
/plugin marketplace add genkovich/sdd
/plugin install sdd@sdd
/reload-plugins
```

Перевір, чи агент тепер розпізнає `/sdd:specify`. Якщо ні, зупинися на встановленні та звір повідомлення з [README SDD](https://github.com/genkovich/sdd#install). Для Codex і Cursor в тому самому README є окреме встановлення й таблиця відповідних викликів. У наступних кроках показано синтаксис Claude Code; не вводь його без змін в інший інструмент. Виклики моделі оплачуються за твоїм тарифом. Сам дашборд модель не викликає.

У редакторі відкрий [приклад налаштувань](../../.claude/sdd.local.example.md) та збережи його копію як `.claude/sdd.local.md`. Якщо файл уже є, порівняй налаштування без перезапису. Приклад задає українську прозу, короткі уточнення й одного послідовного виконавця для першого проходу.

Для наступного уроку потрібна git-історія: SDD створюватиме коміти по задачах. Clone уже містить репозиторій. Якщо робота почалася з ZIP, спочатку перевір:

```sh
git rev-parse --show-toplevel
git status --short
```

Шлях має вказувати на корінь саме твоєї окремої копії пакета. Якщо git показує батьківський репозиторій, перенеси копію в окрему робочу теку перед підготовкою. Якщо репозиторію немає, виконай `git init`, переглянь файли й створи початковий коміт лише з матеріалів пакета. Для цього можна використати вікно Source Control редактора: переглянути список, додати перевірені файли й виконати Commit. Секрети, особисті логи та приватні записи не додавай. Загальна підготовка також описана в [README пакета](../../README.md).

## Пройди стадії з паузами на читання

Відкрий [промпти](prompts.md) і [робочий аркуш](worksheet.md). На кожній стадії спочатку дай агенту відповідний промпт і дочекайся підтвердження меж без змін файлів. Потім введи лише одну команду. Промпт готує контекст, а команда запускає потрібний крок SDD. Перед `/clear` збережи рішення в документах; інакше новій сесії буде нічого перечитати.

| Крок | Команда у Claude Code | Що відкрити після виконання |
|---|---|---|
| Вимоги | `/sdd:specify session-index` | `docs/features/session-index/spec.md` |
| Уточнення | `/sdd:clarify session-index` | той самий spec і фактичні зауваження |
| Технічне рішення | `/sdd:design session-index --depth=easy` | `docs/features/session-index/sad.md` |
| Задачі | `/sdd:tasks session-index` | `tasks.json` і файли в `tasks/` поруч |
| План перевірок | `/sdd:plan-tests session-index` | розділ `Test plan` у `spec.md` |

Між цими стадіями починай свіжий контекст через `/clear`. Файли `.size` та `.route` вже задають `S` і `standard`; їх залишаємо. Для розміру S план перевірок записується всередині spec. Відсутність окремого `test-plan.md` тут нормальна.

Перед tasks відкрий початок `sad.md`. У `target_surfaces` має бути `web-frontend`, бо задача містить видиму сторінку; разом із нею доречний `backend-service`. Без UI-позначки SDD може не створити задачі для сторінки. Також tasks вимагає щонайменше одного справжнього погодженого ADR у `docs/features/session-index/adr/` зі статусом `Accepted`. ADR пояснює вибір між альтернативами. У нашому коді вже є питання для розгляду: підключати індекс через реєстр чи продовжити прямі імпорти адаптера в `server.js`. Погодь вибір і запиши причину. Якщо design не створив такого документа, зупини перехід до tasks та попроси зафіксувати реальне рішення через `/sdd:decide-adr session-index session-index-integration`. Не вигадуй рішення лише для проходження перевірки.

У нашому S1 одна сторінка, один новий маршрут, немає БД і подій. Для цього навчального проходу погоджено скорочення повного процесу SDD: пропускаємо `ux-flows`, `api`, `screens`, `sequences`, `data-model`. Після clarify викликай design, після design викликай tasks безпосередньо, навіть якщо підказка інструмента пропонує інше. Зафіксуй це рішення в sad; опис потоку, станів сторінки й контракту нового маршруту все одно потрібен у самому документі. Це вибір для цієї вправи, не правило пропуску для будь-якого проєкту.

## Що саме погоджуємо

Майбутній список має показувати сесії з проєктом, розміром файла й часом останньої зміни, від свіжих до старих. Дані беремо лише з метаданих файлів. Виданий набір містить шість файлів сесій у трьох проєктах; шість рядків очікуємо за ліміту, який їх уміщує. За меншого ліміту потрібні лише найсвіжіші рядки.

Обхід має зупинятися на файлах сесій безпосередньо в теці проєкту. Вкладені `subagents/` та `tool-results/` не додають рядків. Імʼя теки дає лише похідний шлях: `checkout-api` після заміни дефісів може стати `checkout/api`, тому позначка «похідний» обовʼязкова. Людські заголовки, таймлайн, токени та друге джерело залишаються поза S1.

Пʼять типів критеріїв у [шаблоні](../../templates/03-feature-spec.md) допоможуть перевірити повноту: основний результат, помилка або порожнеча, межа читання, кількість із урахуванням ліміту, збереження наявної поведінки. Конкретний дефолт ліміту, помилковий параметр і порядок за однакового часу ще потрібно погодити. Числа 10 та 3 у навчальному прикладі пояснюють правило; вони не встановлюють дефолт твого застосунку.

## Коли можна переходити далі

Після останньої стадії дай новій сесії промпт D для перевірки звʼязків між документами. Кожен критерій має бути покритий задачею й майбутньою перевіркою. Кожне поле `file` у `tasks.json` повинно вести до наявного Markdown-файла від кореня репозиторію. Залежності мають посилатися на наявні задачі й не утворювати циклів. Чистий відгук агента без перевірених файлів цього не доводить.

Онови власний `docs/practice/handoff.md`: збережи посилання на spec із Test plan, sad, tasks.json, фактичні зауваження й невирішені питання. Продуктові та безпекові питання, від яких залежить S1, потрібно закрити до коду. Питання про майбутні функції можна позначити відкладеними з причиною.

```sh
npm run verify
git status --short
git diff
```

Очікуємо незмінний runtime-код і ті самі два тести S0. Нові файли відкрий окремо: звичайний `git diff` їх не показує. У handoff назви наступну команду `/sdd:implement session-index`, але сьогодні її не запускай. Урок 4 присвячено виконанню й перевірці коду; зараз потрібні придатні для нього документи.

Файли з `examples/` агент не читає й не копіює без твого явного дозволу. Порівняти свою роботу з прикладом можна пізніше, усвідомлено. Заповнений аркуш і зелені тести скелета не є доказом готового індексу.
