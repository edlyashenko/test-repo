# Урок 3. Домовляємося про результат і готуємо задачі

Після другого уроку в тебе є перевірена `docs/architecture-map.md` після survey. Задача вже описана в README пакета, а постійні правила лежать в AGENTS.md. У коді досі S0: сервер запускається, два тести перевіряють початкову поведінку, а списку сесій на сторінці ще немає. Тепер підготуємо вимоги до першого списку й документи, за якими агент зможе почати роботу в уроці 4.

Залишаємося в цьому пакеті. Відкрий [README з задачею](../../README.md), власну `docs/architecture-map.md`, [AGENTS.md](../../AGENTS.md), [правила даних](../rules/session-data.md) та [словник](../../CONTEXT.md). Читай їх разом із поточним кодом. Карта описує те, що survey знайшов у коді. Перевір важливі твердження за файлами: автоматично створений документ теж може помилятися.

Основний маршрут цього уроку використовує SDD. Це встановлюваний набір команд для агента, який послідовно записує вимоги, технічні рішення й задачі. Плагін, налаштування й Git уже підготували в уроці 2. Сьогодні перевіряємо цей стан і рухаємося далі.

## Спершу звір початковий стан

Відкрий термінал у корені пакета, поруч із `package.json`. Якщо залежності ще не встановлені, виконай `npm ci`. Потім запусти:

```sh
npm run verify
npm run demo
```

Для незміненого S0 очікуємо два тести й повідомлення «No slice is wired up yet.» на [локальній сторінці](http://127.0.0.1:4180). Збережи свій фактичний вивід. Це перевірка скелета; нову функцію вона ще не підтверджує. Після огляду зупини сервер через Ctrl+C.

Працюй через `demo`: скрипт `scripts/demo.mjs` задає абсолютний шлях до синтетичних fixtures цього пакета й порт 4180. Він не читає `.env.fixtures` і не бере іншу теку з успадкованих змінних термінала. `npm start` без налаштувань може звернутися до справжньої домашньої теки Claude; для вправи це не потрібно. Якщо стан твоєї копії відрізняється, спершу зʼясуй версію й власні зміни. Не підганяй вивід під число зі слайда.

## Перевір підготовку з уроку 2

У Claude Code відкрий список команд і перевір, що доступна `/sdd:specify`. Перечитай свою `.claude/sdd.local.md`: налаштування з другого уроку зберігаємо, повторно копіювати їх не потрібно. Якщо команди немає, повернися до [підготовки уроку 2](../lesson-2/setup.md). Виклики моделі оплачуються за твоїм тарифом; сам дашборд модель не викликає.

В окремому терміналі перевір:

```sh
git rev-parse --show-toplevel
git status --short
```

Шлях має вести саме до твоєї копії пакета. Git уже потрібен був для survey. Якщо показано батьківський репозиторій або історії немає, виправ підготовку за кроками уроку 2 перед продовженням. Не створюй нову історію поверх наявної.

Відкрий `docs/architecture-map.md`, яку створив твій survey, і ще раз звір важливі твердження за кодом. На чистому старті карти немає. Якщо її ще не створено й не перевірено, заверши урок 2. Бриф після interview не є обов’язковим входом: опис задачі вже є в README.

## Збережи початковий коміт уроку 3

SDD може створювати коміти документів, тому наприкінці звичайний `git diff` покаже не всю роботу. Перед specify переглянь поточні зміни й окремо збережи погоджені результати уроку 2 комітом. Не додавай секрети й сторонні файли. Потім виконай:

```sh
git rev-parse HEAD
```

Скопіюй повний хеш у звичайні нотатки поза пакетом. Нижче `BASE_COMMIT` означає саме цей хеш до початку уроку 3. Це позначення для заміни, не команда й не змінна термінала. Якщо SDD пізніше створить коміти, початковий хеш не змінюй.

## Якщо працюєш у Codex або Cursor

SDD уже встановлено для обраного агента в уроці 2. Не встановлюй одразу кілька способів у тому самому інструменті. Після script-install у Codex назви скілів мають префікс `sdd-`. Нижче ті самі стадії з аргументом `session-index`:

| Стадія | Claude Code | Codex після script-install | Cursor |
|---|---|---|---|
| Вимоги | `/sdd:specify session-index` | `$sdd-specify session-index` | У меню `/` обери `sdd-specify`, додай `session-index` |
| Уточнення | `/sdd:clarify session-index` | `$sdd-clarify session-index` | `sdd-clarify` + `session-index` |
| Рішення | `/sdd:design session-index --depth=easy` | `$sdd-design session-index --depth=easy` | `sdd-design` + `session-index --depth=easy` |
| Задачі | `/sdd:tasks session-index` | `$sdd-tasks session-index` | `sdd-tasks` + `session-index` |
| План перевірок | `/sdd:plan-tests session-index` | `$sdd-plan-tests session-index` | `sdd-plan-tests` + `session-index` |
| Свіжий контекст | `/clear` | `/new` | Новий чат |

Ці виклики вводь у чат агента. Рядок із `$sdd-` не призначений для shell. Перед новим контекстом збережи рішення у файлах. Шляхи документів і налаштування `.claude/sdd.local.md` однакові для всіх трьох інструментів. Назва теки `.claude` тут не означає, що Codex її не може прочитати. Запитання в Codex і Cursor можуть бути звичайним нумерованим повідомленням; дай відповідь і дочекайся наступного кроку.

## Пройди стадії з паузами на читання

Відкрий [промпти](prompts.md) і [робочий аркуш](worksheet.md). На кожній стадії спочатку дай агенту відповідний промпт і дочекайся підтвердження меж без змін файлів. Потім введи лише одну команду. Промпт готує контекст, а команда запускає потрібний крок SDD. Перед `/clear` збережи рішення в документах; інакше новій сесії буде нічого перечитати.

| Крок | Команда у Claude Code | Що відкрити після виконання |
|---|---|---|
| Вимоги | `/sdd:specify session-index` | `docs/features/session-index/spec.md` |
| Уточнення | `/sdd:clarify session-index` | той самий spec і фактичні зауваження |
| Технічне рішення | `/sdd:design session-index --depth=easy` | `docs/features/session-index/sad.md` |
| Задачі | `/sdd:tasks session-index` | `tasks.json` і файли в `tasks/` поруч |
| План перевірок | `/sdd:plan-tests session-index` | розділ `Test plan` у `spec.md` |

Між цими стадіями починай свіжий контекст через `/clear`. Файли `.size` та `.route` вже задають `S` і `standard`; їх залишаємо. Для розміру S план перевірок записується всередині spec. Відсутність окремого `test-plan.md` тут нормальна.

Перед tasks відкрий початок `sad.md`. У `target_surfaces` має бути `web-frontend`, бо задача містить видиму сторінку; разом із нею доречний `backend-service`. Без UI-позначки SDD може не створити задачі для сторінки. Також tasks вимагає щонайменше одного справжнього погодженого ADR у `docs/features/session-index/adr/` зі статусом `Accepted`. ADR пояснює вибір між альтернативами. У нашому коді вже є питання для розгляду: підключати індекс через реєстр чи продовжити прямі імпорти адаптера в `server.js`. Погодь вибір і запиши причину. Якщо design не створив такого документа, зупини перехід до tasks та попроси зафіксувати реальне рішення через `/sdd:decide-adr session-index session-index-integration`. Не вигадуй рішення лише для проходження перевірки.

У нашому S1 одна сторінка, один новий маршрут, немає БД і подій. Для цього навчального проходу погоджено скорочення повного процесу SDD: пропускаємо `ux-flows`, `api`, `screens`, `sequences`, `data-model`. Після clarify викликай design, після design викликай tasks безпосередньо, навіть якщо підказка інструмента пропонує інше. Зафіксуй це рішення в sad; опис потоку, станів сторінки й контракту нового маршруту все одно потрібен у самому документі. Це вибір для цієї вправи, не правило пропуску для будь-якого проєкту.

## Що саме погоджуємо

У показі уточнюємо задачу першого списку з README. Друга лекція не визначала її точних інтерфейсів і поведінки: ці рішення погоджуємо зараз. Майбутній список має показувати сесії з проєктом, розміром файла й часом останньої зміни, від свіжих до старих. Дані беремо лише з метаданих файлів. Виданий набір містить шість файлів сесій у трьох проєктах; шість рядків очікуємо за ліміту, який їх уміщує. За меншого ліміту потрібні лише найсвіжіші рядки.

Обхід має зупинятися на файлах сесій безпосередньо в теці проєкту. Вкладені `subagents/` та `tool-results/` не додають рядків. Імʼя теки дає лише похідний шлях: `checkout-api` після заміни дефісів може стати `checkout/api`, тому позначка «похідний» обовʼязкова. Людські заголовки, таймлайн, токени та друге джерело залишаються поза S1.

Пʼять типів критеріїв у [шаблоні](../../templates/03-feature-spec.md) допоможуть перевірити повноту: основний результат, помилка або порожнеча, межа читання, кількість із урахуванням ліміту, збереження наявної поведінки. Конкретний дефолт ліміту, помилковий параметр і порядок за однакового часу ще потрібно погодити. Числа 10 та 3 у навчальному прикладі пояснюють правило; вони не встановлюють дефолт твого застосунку.

## Коли можна переходити далі

Після останньої стадії дай новій сесії промпт D для перевірки звʼязків між документами. Кожен критерій має бути покритий задачею й майбутньою перевіркою. Кожне поле `file` у `tasks.json` повинно вести до наявного Markdown-файла від кореня репозиторію. Залежності мають посилатися на наявні задачі й не утворювати циклів. Чистий відгук агента без перевірених файлів цього не доводить.

Збережи рішення в spec, sad і файлах задач. Підсумок перевірки залиш у чаті поруч із відповіддю агента; окремого документа для передачі не потрібно. Перед переходом виконай:

```sh
npm run verify
git log --oneline BASE_COMMIT..HEAD
git diff BASE_COMMIT
git status --short
```

Заміни `BASE_COMMIT` своїм збереженим хешем. `git diff BASE_COMMIT` порівнює початковий коміт із поточними файлами: так видно і закомічені, і незакомічені зміни. `git status --short` окремо покаже нові невідстежувані файли. Очікуємо незмінний runtime-код і ті самі два тести S0. Нові файли відкрий окремо: звичайний `git diff` їх не показує. Наступна команда в підсумку SDD: `/sdd:implement session-index`; сьогодні її не запускай. Урок 4 присвячено виконанню й перевірці коду; зараз потрібні придатні для нього документи.

Файли з `examples/` агент не читає й не копіює без твого явного дозволу. Порівняти свою роботу з прикладом можна пізніше, усвідомлено. Заповнений аркуш і зелені тести скелета не є доказом готового індексу.
