# Робочий аркуш: від вимоги до передачі виконавцю

Тримай цей аркуш поруч із [маршрутом уроку](README.md). Він допомагає перечитати власні документи після кожної стадії. Переписувати його повністю у spec або створювати ще один обовʼязковий файл не потрібно. Свої рішення зберігай у документах фічі й handoff.

## Спочатку поясни задачу своїми словами

Хто відкриває дашборд і чого бракує в S0? Які відомості потрібні в першому списку? Де вони вже лежать на диску? Якщо відповідь вимагає читати розмову, звір її з межею S1: у цій вправі працюємо лише з метаданими.

Перед тобою шість синтетичних сесій у трьох проєктах. Це джерело числа шість у прикладах. За ліміту 10 усі шість уміщуються; за ліміту 3 потрібні три найсвіжіші. Ці два числа лише демонструють правило. Конкретний дефолт погодь і запиши у своїх вимогах.

## Після specify

Прочитай `docs/features/session-index/spec.md` разом із [шаблоном](../../templates/03-feature-spec.md). Для кожного критерію спробуй назвати передумову, дію й видимий результат. Пʼять типів нижче допомагають не забути важливе; один критерій іноді потребує кількох перевірок.

| Тип | Питання для власного spec |
|---|---|
| Основний результат | Чи зрозуміло, які рядки й поля побачить людина та в якому порядку? |
| Помилка або порожнеча | Що станеться без теки проєктів або коли її неможливо прочитати? |
| Межа читання | Чи виключені вкладені дані, вміст JSONL і вихід за дозволену теку? |
| Кількість | Чи повʼязане число рядків із кількістю придатних файлів та лімітом? |
| Unchanged | Що саме має зберегтися в health і оболонці сторінки з CSP? |

Розділ про дані має називати синтетичні fixtures і межі доступу. Заголовки, таймлайн, токени й друге джерело залишаються поза S1. Якщо потрібен числовий показник швидкодії, назви джерело порога й спосіб виміру. Для цієї вправи вигадувати KPI або відсоток доступності не потрібно.

## Після clarify

Візьми одну фактичну знахідку й простеж її до виправленого критерію. Якщо відповідь є тільки в чаті, збережи її в документі. Якщо зауважень немає, запиши перевірений обсяг без вигаданого finding.

| Питання | Погоджене рішення | Де записано | Статус |
|---|---|---|---|
| Власне питання з перевірки | Власна відповідь або причина відкладення | Розділ / AC | RESOLVED або DEFERRED |

До коду потрібно погодити дефолт ліміту, неправильний параметр, однаковий час, реакцію на недоступні дані й межу читання. Symlink означає файлове посилання на інше місце; явно виріши, як майбутній індекс уникне виходу за навчальну теку. Факт існування такого правила ще не доводить, що код його виконує.

## Після design

Відкрий `sad.md` і спробуй пройти майбутню дію: людина відкриває список, сервер просить метадані, сторінка показує рядки. Де обробляється ліміт? Як узгоджені поля відповіді та HTML? Що відбувається за порожнього результату?

Перевір за кодом, які файли вже існують. `lib/claude/index.js`, `server.js` і `views/layout.js` є в S0. `views/sessions.js` може бути запланованим новим файлом; поки його створювати не потрібно. Підпис «заплановано» не дасть новій сесії сплутати рішення з реалізацією.

Для нашого скороченого маршруту sad також містить стани сторінки й контракт нового маршруту. Запиши, чому окремі стадії UI/API/моделі даних пропущені. ADR додається для важливого вибору між альтернативами; назва документа сама по собі не робить рішення кращим.

Перед tasks потрібні дві конкретні перевірки. У frontmatter sad є `target_surfaces` з `web-frontend`, щоб не загубити задачі видимої сторінки. У `adr/` є щонайменше одне реальне погоджене рішення зі статусом `Accepted`, інакше tasks зупиниться. Розглянь підключення індексу через реєстр або прямий імпорт адаптера в `server.js`, поясни вибір і погодь його. За відсутності такого рішення повернися до design або `/sdd:decide-adr session-index session-index-integration`; порожній ADR не допоможе.

## Після tasks

Відкрий `tasks.json` і одну задачу з його поля `file`. У JSON обовʼязкові поля контракту SDD: `id`, `title`, `layer`, `deps`, `acs`, `dod`, `files_hint`, `file`. Кореневе `slug` має бути `session-index`. Не перейменовуй машинні поля українською; українською пиши їхній зміст.

`deps` називає попередні задачі; циклу на кшталт «T1 чекає T2, а T2 чекає T1» бути не повинно. `acs` посилається на справжні критерії spec. `file` веде до наявного опису задачі від кореня репозиторію. `files_hint` дає змогу побачити спільні файли. `dod` пояснює, за якою перевіркою роботу можна прийняти.

Не вимагай від свого плану рівно чотирьох задач: T1–T4 на слайді лише показують можливий поділ. Орієнтир для однієї задачі: не більше робочого дня та достатньо малий обсяг для зрозумілого перегляду. Залежні задачі або зміни спільного `server.js` зручно виконувати послідовно.

## Після plan-tests

За розміру S відкрий `Test plan` у `spec.md`. Для кожного AC там потрібні назва перевірки, передумови й очікуваний результат. Перевірка файлового читання, HTTP-контракту й видимої сторінки відповідає на різні питання.

Крайовий випадок «файл замість теки проєкту» можна запланувати кросплатформно. Маніпуляції правами через `chmod` не дають однакової поведінки на всіх ОС. Порядок файлів перевіряється на контрольованому часі зміни, включно з тимчасовими копіями. Використовуй `test/oracle.js` та `test/helpers.js` як наявну основу для майбутніх перевірок, але звір їхні межі з погодженим spec.

## Перед уроком 4

Дай новій сесії промпт D. Після погоджених правок перечитай handoff й перевір результат команд:

```sh
npm run verify
git status --short
git diff
```

У handoff назви фактично прочитані документи, результат перевірки, залишкові питання та наступний крок `/sdd:implement session-index`. Окремо вкажи, що runtime і два тести S0 не змінено, якщо це підтверджено твоїм diff і запуском. Код S1 у цьому уроці не пишемо.
