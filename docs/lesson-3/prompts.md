# Запити до агента для уроку 3

Працюй у корені пакета. Кожен запит нижче задає межі відповідної стадії; команду SDD вводь після нього. Якщо команда ставить запитання, дай власну відповідь, спираючись на файли. Невідоме можна назвати невідомим і погодити окремо. Жоден текст нижче не є журналом уже виконаної практики.

## A. Перед specify

```text
Працюємо над session-index у цьому пакеті.
Зараз лише прочитай джерела й підтвердь межі. Нічого не створюй і не змінюй.
Дочекайся окремої /sdd:specify session-index; усі інструкції запису нижче
стосуються саме цієї майбутньої команди.
Прочитай CLAUDE.md, docs/practice/02-context.md,
docs/practice/handoff.md, CONTEXT.md,
docs/idea-brief.md, docs/roadmap.md, docs/architecture-map.md,
.claude/rules/session-index.md і поточні server.js, lib/claude/index.js,
lib/sources.js, views/layout.js, views/CLAUDE.md, test/skeleton.test.js.
Якщо моїх файлів із другого уроку немає, зупинись і назви відсутні шляхи.

Поточне: S0, два тести, сторінка без списку. Очікуване S1:
метадані сесій Claude, проєкт із позначкою «похідний», розмір,
час зміни, порядок від свіжих, погоджений ліміт.
Лише файли безпосередньо в теці проєкту; без вмісту JSONL,
без особистої домашньої теки, без вкладених subagents/tool-results.
Заголовки, таймлайн, токени та друге джерело поза обсягом.
Наявні health і оболонка з CSP мають працювати й далі.

Далі запускаю specify. Пиши українською, пояснюй незрозумілі терміни.
Створи або уточни docs/features/session-index/spec.md.
.size=S і .route=standard залиш незмінними.
Питання про дефолт ліміту, неправильний параметр, однаковий час,
недоступні дані й межу symlink винеси на погодження.
Не ухвалюй ці рішення замість мене.
Використай templates/03-feature-spec.md як аркуш перевірки вимог;
формат документа збережи сумісним із наступними стадіями SDD.
Runtime-код, тести, fixtures і залежності не змінюй.
examples/ не читай і не копіюй. Не починай implement.
Перед комітом покажи diff і список файлів для мого погодження.
```

```text
/sdd:specify session-index
```

Збережи отриману чернетку й прочитай її. Перевір, що кількість рядків повʼязана з лімітом, а очікувана поведінка не описана як уже реалізована. Критерії приймання сформулюй мовою видимого результату. Технічні адреси й форму JSON зафіксуєш у sad.

## B. Перед clarify

Після збереження spec виконай `/clear`. Потім передай запит і команду:

```text
Перевіряємо вимоги session-index до реалізації.
Зараз лише прочитай джерела й підтвердь межі. Документи не змінюй,
перевірку не починай. Дочекайся окремої /sdd:clarify session-index.
Інструкції перевірки й запису нижче виконуй після цієї команди.
Прочитай spec, мої docs/practice/02-context.md та handoff.md,
CONTEXT.md, idea-brief, roadmap і актуальний код.
examples/ не читай. Код і тести не змінюй.
Знайди місця, де можливі різні результати, що формально відповідають
одному реченню. Для кожного наведи цитату, читання A й B та наслідок.
Окремо перевір ліміт, однаковий час, відсутні/недоступні дані,
межу читання, похідний проєкт, незмінну поведінку S0.
Не вигадуй зауважень для кількості. Не вирішуй продуктові питання за мене.
Після погодження внеси рішення в основні вимоги й журнал уточнень.
Для кожної фактичної знахідки зафіксуй RESOLVED або DEFERRED із причиною.
Питання, що блокують правильність чи безпеку S1, не відкладай за межі реалізації.
Перед комітом покажи зміни для погодження.
```

```text
/sdd:clarify session-index
```

RESOLVED означає, що рішення вже внесене у відповідне місце документа. DEFERRED означає свідомо відкладене питання з причиною й моментом повернення. Чистий результат теж можливий: тоді запиши, які місця перевірено, без штучних правок заради вправи.

## C. Перед design, tasks і plan-tests

Почни новий контекст. Цей запит можна повторити на наступних стадіях, змінюючи лише назву стадії.

```text
Продовжуємо підготовку session-index за погодженим spec.
Зараз лише прочитай джерела й підтвердь межі. Нічого не створюй і не змінюй.
Дочекайся окремої команди design, tasks або plan-tests.
Після неї виконай лише названу стадію та зупинись перед наступною.
Прочитай docs/practice/handoff.md, spec, наявні документи фічі
та поточний код. Працюй тільки над документами. examples/ не читай.
S0 ще не реалізує список; не позначай майбутні файли наявними.

Маршрут курсу: design --depth=easy, потім tasks, потім plan-tests.
Для цього S1 свідомо пропускаємо окремі ux-flows, api, screens,
sequences та data-model: одна сторінка, один новий маршрут, без БД/подій.
Запиши причину в sad. Потік, стани сторінки й погоджений контракт
нового маршруту опиши в sad, щоб задачі не вигадували їх по-різному.
У sad врахуй реальні прямі імпорти server.js, локальні HTML-правила
та метадані замість читання JSONL.
У frontmatter sad оголоси target_surfaces з web-frontend і backend-service.
Перед tasks перевір наявність щонайменше одного справжнього погодженого
ADR зі Status: Accepted у docs/features/session-index/adr/.
Питання для розгляду: реєстр проти прямих імпортів адаптера в server.js.
Узгодь вибір зі мною, поясни альтернативу й причину. Якщо Accepted ADR
немає, зупини tasks та назви необхідне погодження; не вигадуй рішення.

Для tasks потрібні tasks.json і докладні Markdown-файли задач.
Використай контракт встановленого SDD: id, title, layer, deps, acs,
dod, files_hint, file. file є шляхом від кореня репо до наявного
файла задачі. У кожній задачі мають бути потрібний контекст і AC.
Залежності без циклів; одна невелика задача на крок.
Не вигадуй паралель, якщо задачі змінюють спільні файли.

Для plan-tests залиш .size=S та .route=standard. План перевірок
запиши в розділ Test plan у spec.md. Кожен AC має принаймні
одну названу перевірку; помилки й межі отримують окремі рядки.
Погодь зі мною потрібні рівні. Дані синтетичні; план переносимий
між ОС. Не записуй PASS для тестів, яких ще немає.
Runtime-код, тести, fixtures і залежності не змінюй.
Не запускай implement. Перед комітом покажи зміни для погодження.
```

Виконуй лише одну стадію за раз. Після кожної прочитай її файли, погодь зміни й збережи рішення перед очищенням контексту.

```text
/sdd:design session-index --depth=easy
```

Після design і збереження рішень: `/clear`, знову рамка C, потім:

```text
/sdd:tasks session-index
```

Після tasks і перевірки файлів: `/clear`, знову рамка C, потім:

```text
/sdd:plan-tests session-index
```

## D. Перевірка перед уроком 4

Це звичайний запит у новій сесії. `/sdd:review` призначений для реалізованої фічі й знадобиться пізніше; зараз перевіряємо документи.

```text
Зроби read-only перевірку документів session-index перед реалізацією.
Прочитай docs/practice/02-context.md, handoff.md, spec.md із Test plan,
sad.md, tasks.json, усі файли задач із поля file, roadmap і поточний код.
examples/ не читай. Нічого не редагуй і не починай implement.

Перевір:
1. Усі AC зі spec покриті tasks.json і Test plan; усі посилання acs реальні.
2. JSON розбирається; slug=session-index, id унікальні, deps посилаються
   на наявні задачі й не мають циклів; dod/files_hint/file заповнені.
3. Кожне file є наявним Markdown-файлом усередині репозиторію.
   Він має контекст, AC, узгоджені deps і умову завершення.
4. Контракт і назви полів однакові між spec, sad і задачами.
5. Обсяг лишається S1: метадані, один рівень, позначений похідний проєкт,
   погоджений ліміт, порожнеча/помилки/межа читання, Unchanged для S0.
6. Немає непогодженого питання, від якого залежить правильність
   або безпека цього зрізу. Відкладене має причину й момент повернення.
7. Не додано реалізації, нових тестів або тверджень про прийнятий S1.
8. У sad target_surfaces містить web-frontend; є щонайменше один
   погоджений ADR зі Status: Accepted. Це справжнє рішення з причиною.

Для кожної знахідки: файл і рядок, суперечність, наслідок, мінімальна правка.
Якщо знахідок немає, назви перевірені файли й межі перевірки.
Це перевірка документів; не називай її виконаними тестами S1.
```

Прочитай зауваження й окремо погодь виправлення. Після них попроси перевірити змінені місця. У handoff збережи фактичний результат; копіювати формулювання «усе пройдено» з навчальних матеріалів не потрібно.
