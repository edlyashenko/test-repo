# Урок 5. Практика: перевіряємо свою реалізацію

Спочатку прочитай [теорію](theory.md). Тут ми застосуємо її до власного `session-index` із четвертого уроку: списку сесій у тому самому навчальному застосунку. Код уже має виконувати погоджені вимоги. Наше завдання тепер: зрозуміти, чи достатньо доказів, щоб прийняти результат.

Зелені тести та перегляд сторінки вже були в уроці 4. Ми не починаємо перевірку з нуля. Перечитаємо наявні докази, знайдемо можливі прогалини й передамо точно зафіксовану версію незалежному рецензенту. Наприкінці рішення залишиться за тобою.

## Як виконувати разом із відео

Рухайся за десятьма кроками. На відео достатньо детально розібрати один критерій: звідки взявся очікуваний результат, що перевіряє тест і чого він не бачить. Для решти критеріїв повтори ту саму перевірку у власному темпі. Під час роботи агента відео можна поставити на паузу; кількість тестів і зауважень у тебе може відрізнятися від показу.

Усі shell-команди нижче виконуємо в корені твоєї копії `agentic-engineering-mini-kit`. Запити від A до D надсилаємо в чат агента. Новий репозиторій, повторний interview і ще одна специфікація не потрібні.

Якщо в четвертому уроці була пауза після першої задачі, спочатку [продовж реалізацію](../lesson-4/README.md#8-продовж-решту-погодженого-плану).

- [ ] Відкрита моя реалізація; усі задачі фічі завершені або приймання зупинено до їх завершення.

## 2. Знайди вимоги, за якими прийматимеш роботу

Відкрий у редакторі:

- `docs/features/session-index/spec.md`: AC, NFR, DoD і розділ `Test plan`;
- `docs/features/session-index/sad.md`: погоджений метод і шлях HTTP, параметри, відповіді та стани сторінки;
- погоджений ADR і файли задач, названі в `tasks.json`;
- `AGENTS.md`, `docs/rules/session-data.md`, а для HTML також `views/AGENTS.md`.

Обери один критерій і поясни його без коду. Наприклад: які файли мають потрапити до списку, які не мають і як це побачити? Очікуваний результат беремо зі специфікації. Сам код не може одночасно бути і відповіддю, і правилом для її оцінювання.

Зберігаємо навчальне скорочення з уроку 3: `Test plan` живе в spec, HTTP-контракт і стани живуть у SAD та задачах. Створювати окремі `test-plan.md`, OpenAPI або screens лише для цього уроку не потрібно. Якщо погодженого правила немає, запиши питання; не змінюй вимоги потайки під готову реалізацію.

- [ ] Знаю джерело очікуваної поведінки й можу пояснити один AC своїми словами.

## 3. Створи коротку записку перевірки

Відкрий чат агента в корені пакета. Надішли [запит A](prompts.md#a-підготувати-записку-перевірки). Він створить `docs/practice/05-verification.md` за [шаблоном](../../templates/05-verification-canvas.md).

У документі лише пʼять частин: версія й джерела, докази за критеріями, розбір сили тесту, незалежне ревʼю та рішення людини. План тестів не переписуємо. Нам потрібні посилання на нього, короткі факти й чесні позначки «не перевірено».

З карти четвертого уроку перенеси `FEATURE_BASE_COMMIT`: це повний хеш перед реалізацією. Не підставляй замість нього нинішній `HEAD`. Якщо базового хешу немає, спочатку знайди правильну межу за історією Git і погодженими документами. Не вгадуй її за назвою `main`.

- [ ] Записка створена; базова версія відома; агент не заповнив результати без запусків.

## 4. Зафіксуй версію, яку перевірятимеш

Спочатку переглянь зміни у **Source Control**. Нові файли відкрий окремо: звичайний diff їх не показує. Виконай:

```sh
node --version
npm ci
npm run verify
git diff
git diff --cached
git status --short
```

Збережи комітом лише свої погоджені зміни реалізації, тестів і потрібних документів. Не використовуй `git add .` навмання й не стирай сторонню роботу заради чистого статусу. Якщо не можеш відділити потрібні зміни від сторонніх, зроби паузу: ще не маємо однозначної версії для приймання.

У **Source Control** вибери потрібні файли, виконай **Stage Changes**, введи короткий опис зміни та натисни **Commit**. Це локальне збереження; **Sync**, **Push** або **Publish Branch** для вправи не натискай. Якщо незакомічених змін немає, зайвий коміт не потрібний.

Після збереження виконай:

```sh
git status --short
git rev-parse HEAD
```

Статус має бути порожнім. Повний хеш запиши як `CANDIDATE_COMMIT` у записку. Назва означає «версія-кандидат на приймання». Далі не змінюємо код, тести, вимоги чи налаштування перевірок, поки збираємо докази для цього хешу. Самі результати можна дописувати в записку; ці зміни документа не слід видавати за частину вже зафіксованого коміту.

У наступних командах заміни обидві назви великими літерами своїми повними хешами; `..` залиш. Це місця для підстановки тексту, не готові змінні shell.

```sh
git log --oneline FEATURE_BASE_COMMIT..CANDIDATE_COMMIT
git diff --stat FEATURE_BASE_COMMIT..CANDIDATE_COMMIT
git diff FEATURE_BASE_COMMIT..CANDIDATE_COMMIT
```

Маєш побачити всю зміну фічі, зокрема вже закомічену агентом. Порожній diff там, де очікується реалізація, означає, що межі потрібно перевірити.

- [ ] Є повні базовий і кандидатний хеші; зрозуміло, які саме зміни перевіряємо.

## 5. Повтори gate й перечитай один цикл RED → GREEN

На зафіксованому кандидатові виконай:

```sh
npm run verify
echo $?
git rev-parse HEAD
git status --short
```

`echo $?` у bash/zsh показує код завершення попередньої команди: 0 означає успішне завершення. Виконуй цей рядок відразу після verify. У PowerShell замість нього введи `$LASTEXITCODE`. Це результат запуску набору; пропущені випадки все одно потрібно прочитати у підсумку тестів.

Запиши дату, версію Node, команду, фактичний підсумок, код завершення та хеш. Окремо зазнач пропущені тести й `todo`, якщо вони є. Код завершення 0 не перетворює пропущений сценарій на перевірений. У статусі після фіксації кандидата допустимі лише названі тобою нові докази й записи; несподівану зміну коду спочатку розбери.

З карти уроку 4 візьми один справжній цикл RED → GREEN. Знайди той самий тест, рядок падіння та причину. Падіння через імпорт або зламане середовище не доводить відсутності потрібної поведінки.

Історичний RED може стосуватися старого хешу. Так і запиши: він пояснює розробку тесту. Нинішній GREEN для приймання має стосуватися кандидата. Якщо історичного виводу немає, чесно зазнач це. Не ламай готовий код, щоб заднім числом намалювати TDD. Якщо поведінка вже працювала до змін, поясни це без штучного RED.

- [ ] Є свіжий gate кандидата й чесний розбір одного тесту без вигаданих доказів.

## 6. Перевір, чи тести ставлять потрібні запитання

Надішли [запит B](prompts.md#b-перечитати-докази-та-силу-тестів). Агент поки лише читає. Відкрий названі ним місця в spec і тестах. Для кожного AC у §2 записки має бути перевірка, фактичний результат або явна прогалина. Включи погоджені помилки, граничні випадки й захищену поведінку, зокрема межу читання даних.

Ось зрозумілий приклад прогалини. За специфікацією дві сесії з однаковим часом зміни повинні мати визначений додатковим правилом порядок. Якщо тестові файли завжди мають різні дати, перевірка може не помітити, що це правило взагалі відсутнє. Потрібні дві синтетичні сесії з однаковим контрольованим `mtime` та очікуваний порядок, виведений із твого AC. Сам Git час зміни не зберігає.

Не треба запускати mutation testing framework для завершення вправи. За бажанням можна перевірити одну гіпотезу про чутливість тесту в окремій одноразовій копії точного коміту, із синтетичними даними. Перед будь-якою зміною перевір шлях копії та її чистий стан; основний проєкт, видані fixtures й особисті логи не змінюй. Якщо такої ізольованої копії немає, залиш це як незапущену додаткову перевірку. Припущення «тест мав би впасти» не є результатом запуску.

- [ ] Для кожного AC видно доказ або прогалину; можу пояснити хоча б одну межу тесту.

## 7. Перевір справжній екран і погоджений HTTP-контракт

У shell виконай:

```sh
npm run demo
```

Відкрий [http://127.0.0.1:4180](http://127.0.0.1:4180), потім потрібну сторінку за своїм SAD. Порівняй видимі поля, порядок і ліміт із власними вимогами. У пакеті шість основних сесій; усі шість очікуємо лише коли погоджений ліміт їх уміщує. Вкладені службові файли не повинні перетворюватися на рядки списку.

Для HTTP знайди точні метод, шлях і параметри у своєму SAD. Якщо це GET, адресу можна відкрити в браузері; код відповіді та тіло подивись у **Developer Tools → Network**. Для іншого методу скористайся погодженим у плані HTTP-тестом. Не підставляй вигаданий `/api/sessions` лише тому, що він знайомо звучить. Перевір погоджений правильний і неправильний параметр, а результат запиши поруч із AC.

Порожні чи недоступні дані перевіряй своїми тестами на тимчасових синтетичних теках, без видалення виданих fixtures. Візуальний перегляд сторінки не доводить, що код ніколи не читає JSONL: для цієї межі потрібні перевірка реалізації та відповідні тести. Не користуйся `npm start`, який не є навчальним запуском із гарантовано заданими fixtures.

Збережи власні результати та зупини сервер через **Ctrl+C**. Якщо порт зайнятий, зупини лише свій попередній сервер або спочатку зʼясуй, хто його використовує.

- [ ] Переглянуто власну сторінку й контракт; неперевірені стани названо явно.

## 8. Передай фічу незалежному рецензенту

Відкрий свіжу сесію без історії виконавця. Надішли [запит C](prompts.md#c-незалежний-перегляд-фіксованої-версії) разом із командою чату:

```text
/sdd:review session-index
```

Команда записана для Claude Code. Для Codex і Cursor використай [відповідники уроку 3](../lesson-3/README.md#якщо-обрано-codex-або-cursor). Вартість і доступність залежать від твого інструмента. Якщо скіл недоступний, той самий запит може отримати колега або нова сесія агента; познач фактично використаний спосіб.

Перед переглядом рецензент має назвати обидва хеші й обсяг diff. Поточний `HEAD` має дорівнювати `CANDIDATE_COMMIT`. Не запускай паралельно implement. SDD може визначати базу від гілки автоматично; звір її зі своїм `FEATURE_BASE_COMMIT`. Якщо межі розійшлися, спочатку виправ обсяг запиту, без вигаданих CLI-прапорців.

Перегляд має охопити відповідність усім AC, потім якість і ризики реалізації. Рецензент не виправляє код; керівна сесія SDD зберігає звіт у `docs/features/session-index/_review/`. Відкрий фактично створений файл. Для зауваження шукай `file:line`, наслідок і спосіб перевірки. Відсутність знахідок корисна лише разом із названими межами перегляду. Інструкція «не редагуй» сама по собі не встановлює технічної заборони запису.

- [ ] Незалежний перегляд стосується точного кандидата й усієї зміни; прочитано findings і межі.

## 9. Розбери зауваження й повтори потрібні перевірки

Для кожного зауваження обери рішення: виправити зараз, відкласти з причиною та відповідальним або відхилити з доказом. Порушення погодженого AC чи межі приватності не можна сховати під словом «потім» і прийняти всю фічу без змін.

Для погодженого виправлення використай [запит D](prompts.md#d-виправити-погоджене-зауваження) та обери відповідний маршрут. Відтворювана помилка проходить через `/sdd:fix session-index` із конкретним симптомом. Якщо review створив follow-up задачу, її реалізує `/sdd:implement session-index` за погодженим обсягом. Не запускай обидві стадії автоматично. Зміни вимог потрібно спочатку погодити.

Після виправлення збережи новий кандидатний коміт. Для нього повтори потрібний тест, весь `npm run verify`, зачеплену перевірку екрана/HTTP та незалежне ревʼю. Старий звіт лишається історією старої версії. Базовий `FEATURE_BASE_COMMIT` не змінюється; у поточній записці онови кандидата й посилання на його докази.

Якщо дефектів не знайдено, запиши це разом з обсягом і межами. Вигадувати помилку для завершення уроку не потрібно.

- [ ] Кожна знахідка має обґрунтоване рішення; після змін докази й ревʼю оновлено для нового кандидата.

## 10. Прийми рішення й збережи наступний крок

Перечитай §2 та §4 записки. Чи всі погоджені AC і потрібні NFR мають достатні докази? Чи завершено DoD? Чи немає відкритої знахідки, яка заважає правильності або безпеці? Знову звір `git rev-parse HEAD` і `git status --short`: результат має стосуватися названого кандидата, без непомічених змін реалізації.

У §5 сам запиши рішення: «прийнято», «не прийнято» або «прийнято з явно погодженим обмеженням». Якщо обмеження змінює вимоги, спочатку погодь цю зміну та знову перевір відповідність. Формальний PASS агента не замінює твого рішення.

Додай одну коротку нотатку для уроку 6: що могло пропустити помилку та який тест, уточнення чи gate варто обговорити. Якщо нового механізму не потрібно, поясни чому. Не запускай новий interview і не створюй roadmap лише заради статусу shipped.

Це локальне приймання навчальної фічі. Воно не дає автоматичного дозволу на `ship`, push, PR, merge або deploy. Репозиторій роздачі існує на GitHub, але можливість його завантажити не означає право публікувати туди свою роботу. Якщо зберігаєш звіт окремим документаційним комітом, залиш у ньому точний кандидатний хеш; новий `HEAD` не стає заднім числом перевіреною версією.

- [ ] Є моє рішення з доказами та межами, наступна навчальна дія й відсутність автоматичної публікації.

## Що залишиться після практики
