# Урок 5. Чи вистачає доказів для приймання?

Це самоперевірка після [теорії](theory.md) й [практики](README.md). Новий документ не потрібний: відповідай усно, а важливі факти збережи у своїй `docs/practice/05-verification.md`.

## Перевір звʼязок із попередніми уроками

- [ ] Можу показати вимогу зі spec, відповідну задачу, зміну коду й тест на неї.
- [ ] Знаю, чому зелений gate із четвертого уроку ще не є незалежним прийманням.
- [ ] `FEATURE_BASE_COMMIT` збережений до реалізації; `CANDIDATE_COMMIT` називає точну перевірювану версію.
- [ ] Моя назва гілки, endpoint, ліміт і число тестів узяті з власного результату, без підстановки показників лектора.

## Пʼять ситуацій

**1. Агент каже: «Усі тести зелені». Чи можна одразу прийняти фічу?**

Ще ні. Треба зʼясувати, які вимоги перевіряють ці тести, на яких даних, для якого коміту й що залишається поза ними. Далі потрібні незалежний перегляд, рішення щодо findings і перевірка погодженого DoD. Зелені тести є важливим доказом у визначеному обсязі.

**2. Тест сортування має лише різні дати. Він доводить правильний порядок за однакового часу?**

Ні. Для цього потрібні щонайменше дві синтетичні сесії з однаковим контрольованим `mtime` й очікування за погодженим додатковим правилом. Не обчислюй очікування тією самою функцією сортування, яку перевіряєш.

**3. Є історичний RED на старій версії. Це недопустимий доказ?**

Він допустимий як історія розвитку тесту, зі своїм хешем і причиною падіння. Для приймання потрібен фактичний GREEN на поточному кандидатові. Старий RED не потрібно переносити на цей хеш. Якщо поведінка працювала від початку, штучно ламати її для історії не потрібно.

**4. Після PASS ми трохи змінили тести й код. Старого звіту достатньо?**

Ні. Він описує стару версію. Зафіксуй нового кандидата, повтори потрібні сценарії й повний gate, передай нову зміну на незалежне ревʼю. Залиш старий звіт історією, без підміни хешу в ньому.

**5. Скіл радить наступною командою запустити ship. Фіча вже має бути опублікована?**

Ні. Рекомендація наступної стадії не є дозволом на публікацію. У цій практиці зупиняємося на локальному рішенні про приймання. Push, PR, merge та deploy потребують окремо погодженого обсягу й доступу.

## Що можеш показати

- [ ] Коротку записку з точними версіями та фактичним станом Git, без дубля плану.
- [ ] Для кожного AC і потрібної NFR: команду або дію, результат, доказ та межу; прогалини названі явно.
- [ ] Пояснення, чому помилка імпорту не є потрібним поведінковим RED.
- [ ] Один розбір сили тесту: яку помилку він спіймає й яку може пропустити.
- [ ] Свіжий gate, перегляд потрібного екрана й HTTP за своїм контрактом; skipped і todo не видані за пройдені перевірки.
- [ ] Незалежний review всієї зміни кандидата, з джерелами, межами й рішенням щодо кожної знахідки.
- [ ] Після виправлень докази відповідають новому кандидатові; без знахідок немає вигаданих дефектів для галочки.
- [ ] Моє рішення про приймання та одна конкретна тема для навчання в уроці 6.

Якщо не можеш пояснити пункт, повернися до відповідного кроку. Мета цієї вправи: навчитися відрізняти переконливу відповідь агента від достатнього доказу.
