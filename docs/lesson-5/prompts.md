# Запити до агента для уроку 5

Спочатку відкрий [маршрут практики](README.md). Це запити для чату агента в корені власного пакета. Замінюй `FEATURE_BASE_COMMIT` і `CANDIDATE_COMMIT` фактичними повними хешами; не надсилай ці позначення як нібито готові значення.

Команди SDD записані для Claude Code і контракту SDD 2.3.0. У Codex після script-install заміни `/sdd:review` на `$sdd-review`, у Cursor вибери `sdd-review` у меню `/`; так само для `fix`. Вбудовані `/code-review`, `/security-review` і `/simplify` є лише в Claude Code, для Codex і Cursor їх заміняють запити C і E. Перед кожним запитом B, C, D, E і F починай свіжий контекст: `/clear`, `/new` або новий чат.

## A. Записка перевірки з реальних виводів

Надішли разом із фактичним виводом кроку 3: обидва хеші, підсумок `npm run verify` з кодом завершення, що побачив на сторінці й у HTTP.

```text
Готуємо незалежне приймання моєї реалізації session-index після уроку 4.
Прочитай AGENTS.md, правила в .claude/rules/, views/AGENTS.md,
docs/practice/04-workflow.md, мої spec.md, sad.md, Accepted ADR,
tasks.json і tasks/tracker.md у docs/features/session-index/.
Звір стан задач із кодом. Якщо фіча часткова, назви незавершене
і зупинись: не оголошуй її готовою і не продовжуй implement сам.

Ось мої фактичні виводи (нічого з них не змінюй і не доповнюй):
FEATURE_BASE_COMMIT: <повний хеш з карти уроку 4>
CANDIDATE_COMMIT: <повний хеш після коміту>
<вивід npm run verify з кодом завершення>
<що побачив на сторінці та у відповіді HTTP на правильний і неправильний ліміт>

Створи лише docs/practice/05-verification.md за
templates/05-verification-canvas.md, збережи пʼять секцій шаблону.
Заповни §1 і §2 виключно з виводів вище: для кожного AC і потрібної NFR
рядок із джерелом, назвою наявного тесту або позначкою «тест не знайдено»,
фактичним результатом і межею. Чого у виводах немає, познач «не перевірено».
Не вигадуй команди, вивід, PASS, RED чи факт перегляду браузера.
§3-§5 залиш із підказками шаблону: їх заповнимо після ревʼю.
Не переписуй Test plan, не створюй test-plan.md, OpenAPI, screens чи roadmap.
Не читай examples/, особисті логи або вміст JSONL.
Runtime, тести, fixtures, вимоги й налаштування не змінюй.
Нічого не коміть і не публікуй. Покажи створену записку та прогалини.
```

## B. Незалежний перегляд зафіксованої версії

Надішли у свіжій сесії разом із командою під ним. Не передавай історію, в якій агент переконував себе, що реалізація правильна.

```text
Виконай незалежний review моєї session-index без виправлення коду.
FEATURE_BASE_COMMIT: <повний базовий хеш до реалізації>.
CANDIDATE_COMMIT: <повний кандидатний хеш>.
Покажи фактичний HEAD і перевір його рівність кандидатові.
Назви базу та обсяг diff: потрібна вся зміна від базового хешу
до кандидата з усіма комітами агента, не лише останній коміт.
Якщо автоматично обрана база інша або робоче дерево відрізняється
від кандидата, зупинись і поясни, як погодити правильний обсяг.

Передай свіжому рецензенту AGENTS.md, правила в .claude/rules/,
views/AGENTS.md, мою architecture-map, spec з Test plan, SAD,
Accepted ADR, tasks.json і файли задач, tracker, повний diff,
код, тести та docs/practice/05-verification.md з фактичними доказами.
Не передавай історію розмови виконавця. Не читай examples/ чи особисті логи.
Спочатку перевір відповідність кожному AC, NFR, DoD і захищеній поведінці S0,
разом із критеріями, про які виконавець у підсумку не написав.
Потім перевір якість, обробку помилок, чутливість тестів і ризики безпеки.
Контракт HTTP і стани бери з мого SAD; окремі OpenAPI/screens
за навчальним override не потрібні. Не підмінюй погоджений endpoint.

Рецензент не редагує runtime, тести, fixtures, spec або налаштування.
Відтворюй лише безпечні перевірки на синтетичних даних;
для повного gate використовуй npm run verify, для показу npm run demo.
Кожна знахідка: file:line, порушений критерій або ризик, вплив,
спосіб відтворення чи доказ; відокрем факт від підозри.
Для кожного AC назви доказ, межу або неперевірений крок.
Збережи звіт у docs/features/session-index/_review/ з точними
base/candidate, виконаними командами й межами перегляду.
Якщо знахідок немає, не вигадуй їх; PASS супроводжуй межами.
Нічого не виправляй, не коміть, не запускай ship/push/PR/merge/deploy.
Після звіту зупинись: рішення щодо зауважень і приймання ухвалюю я.
```

```text
/sdd:review session-index
```

## C. Другий і третій погляд без вбудованих скілів

Для Codex і Cursor замість `/code-review` і `/security-review`. Надішли у свіжій сесії. Форма знахідок як у скілі `requesting-code-review` з superpowers: місце, проблема, доказ.

```text
Зроби другий і третій погляд на мою session-index. Лише читання, без правок.
FEATURE_BASE_COMMIT: <повний базовий хеш>. CANDIDATE_COMMIT: <повний кандидатний хеш>.
Виконай git diff FEATURE_BASE_COMMIT...CANDIDATE_COMMIT і працюй лише з цим обсягом.
Звіт першого погляду в docs/features/session-index/_review/ не читай:
твоя цінність у незалежності від нього.

Блок «коректність»: помилки логіки, крайові випадки, неправильні
припущення про дані, помилки в тестах, які дають зелений результат
на неправильному коді. Порівнюй лише з spec, SAD і кодом.
Блок «безпека»: інʼєкції у параметрах запиту, XSS через шаблони у views/,
шляхи поза fixtures/ і symlink, секрети й особисті дані в коді чи логах,
запис у джерело даних. Дивись лише перевірений обсяг.

Кожна знахідка: file:line, у чому проблема, доказ або спосіб відтворення,
який AC або правило порушено, впевненість (висока / середня / низька).
Знахідки без доказу не пиши. Якщо в блоці нічого не знайдено, напиши
«не знайдено в перевіреному обсязі» і перелічи класи, які дивився.
Нічого не правити, не комітити, не запускати ship/push/PR/merge/deploy.
Після звіту зупинись: рішення ухвалюю я.
```

## D. Виправити одну погоджену знахідку

Надішли у свіжій сесії разом із командою під ним. Одна знахідка на один прохід.

```text
Погоджую лише таке виправлення session-index:
<номер знахідки і погляд, симптом, кроки відтворення, очікування за моїм AC>.
Звіти: <шлях у _review/ і вивід другого або третього погляду>.
Поточний кандидат: <повний хеш>. FEATURE_BASE_COMMIT не змінюй.
Прочитай AGENTS.md, правила в .claude/rules/, views/AGENTS.md,
spec, SAD, потрібні задачі й код. Особисті дані та examples/ не читай.
Перевір поточні зміни Git; сторонню роботу не стирай і не коміть.

Спочатку відтвори проблему і зроби тріаж: регресія проти наявного AC,
неоднозначне формулювання AC чи прогалина без критерію.
Напиши мінімальний pinning-тест на рівні поведінки, покажи правильний RED
і процитуй рядок падіння. Потім мінімальний фікс до GREEN без супутніх
рефакторингів, npm run verify, запис у docs/features/session-index/_fixes/.
Використовуй лише синтетичні тимчасові дані; видані fixtures не переписуй.
Не послаблюй AC чи assertion, щоб отримати зелений результат.
Якщо потрібна зміна spec, покажи формулювання до і після й дочекайся
мого погодження; сам spec не змінюй.

Перед комітом покажи точні файли та diff. Наприкінці назви зміну,
фактичні перевірки, що повторити в браузері/HTTP і які файли
передати на повторне ревʼю. Не запускай ship, push, PR, merge або deploy.
Зупинись після виправлення.
```

```text
/sdd:fix session-index
```

## E. Спростити без зміни поведінки

Для Codex і Cursor замість `/simplify`. Лише на чистому дереві після коміту фіксу.

```text
Прочитай diff FEATURE_BASE_COMMIT...CANDIDATE_COMMIT моєї session-index
і запропонуй спрощення без зміни поведінки за чотирма питаннями:
що можна перевикористати з наявного коду, що спростити, що працює зайво,
чи не завелика висота абстракції для цієї задачі.
Спецкейси під конкретний тест і дублі одного правила познач окремо.
Багів не шукай: це не ревʼю.

Для кожної запропонованої зміни: файл і рядки, що саме змінюється,
чому поведінка лишається тією самою, який наявний тест це доводить.
Якщо доказу немає, зміну не пропонуй. Спочатку покажи список,
нічого не змінюй до мого погодження. Після погодження внось лише
погоджені правки, запусти npm run verify і покажи diff.
Не коміть: збереження зроблю сам.
```

## F. Правило й hook з фактичної знахідки

Надішли у свіжій сесії. Правило в `AGENTS.md` вставляєш сам після відповіді.

```text
Прочитай docs/features/session-index/_fixes/ (якщо є)
і docs/features/session-index/_review/, а також AGENTS.md.
З причини виправленої або найважливішої знахідки сформулюй одне речення-правило
для розділу «Запуск і перевірки» в AGENTS.md: що робити і чому,
з конкретним прикладом невалідного входу або межі. Форма як у наявних
рядках розділу. Не вставляй його в файл: покажи текст, вставлю сам.
Якщо знахідок не було, запропонуй правило з межі, яку рецензент
назвав неперевіреною, і так це і познач.

Потім відкрий .claude/settings.example.json і scripts/verify-hook.mjs.
Поясни своїми словами: на яку подію спрацьовує hook, що він запускає,
коли повертає 0, коли 2, куди йде stderr і що означає stop_hook_active.
Звір, що команда в example відповідає скрипту. Якщо бачиш розбіжність,
назви її; файли не змінюй. Нічого не коміть.
```

Після відповіді повернися до кроку 11 маршруту: підключи hook, зроби контрольний провал і запиши результат у §2 записки.
