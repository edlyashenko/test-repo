# Запити до агента для уроку 5

Спочатку відкрий [маршрут практики](README.md). Це запити для чату агента в корені власного пакета. Замінюй `FEATURE_BASE_COMMIT` і `CANDIDATE_COMMIT` фактичними повними хешами. Не надсилай ці позначення як нібито готові значення.

Команди SDD нижче записані для Claude Code і контракту SDD 2.3.0. Відповідники для Codex і Cursor є в [уроці 3](../lesson-3/README.md#якщо-обрано-codex-або-cursor). Для іншої версії спочатку прочитай її контракт. Тут не встановлюємо скіли повторно й не додаємо окремі API/UI-документи поверх погодженого навчального маршруту.

## A. Підготувати записку перевірки

```text
Готуємо незалежне приймання моєї реалізації session-index після уроку 4.
Прочитай AGENTS.md, docs/rules/session-data.md, views/AGENTS.md,
docs/practice/04-workflow.md, мої spec.md, sad.md, Accepted ADR,
tasks.json і tasks/tracker.md у docs/features/session-index/.
Звір стан задач із кодом. Якщо фіча часткова, назви незавершене:
не оголошуй її готовою до приймання й не продовжуй implement сам.

Створи лише docs/practice/05-verification.md за
templates/05-verification-canvas.md. Збережи пʼять секцій шаблону.
Перенеси фактичний FEATURE_BASE_COMMIT з карти уроку 4 й назву гілки.
Кандидатний хеш поки залиш незаповненим: його зафіксую після коміту.
Для кожного AC, потрібної NFR і захищеної поведінки додай рядок
з посиланням на джерело та наявний тест або позначкою «тест не знайдено».
Не переписуй план тестів. Виправ відносні посилання для нового місця файла.

Наш Test plan у spec; HTTP-контракт і стани в SAD та задачах.
.size=S, .route=standard з явно погодженим навчальним override зберігаються.
Нові test-plan.md, OpenAPI, screens, roadmap або handoff не створюй.
Не вигадуй команди, вивід, PASS, RED чи факт перегляду браузера.
Неперевірене познач прямо. Приклад лектора не є моїм результатом.
Не читай examples/, особисті логи або вміст JSONL.
Runtime, тести, fixtures, вимоги й налаштування не змінюй.
Нічого не коміть і не публікуй. Покажи створену записку та прогалини.
```

## B. Перечитати докази та силу тестів

```text
Перечитай докази session-index. Лише аналіз, без змін файлів і без запуску
mutation testing. FEATURE_BASE_COMMIT: <повний базовий хеш>.
CANDIDATE_COMMIT: <повний кандидатний хеш>.
Спочатку перевір фактичний HEAD і стан Git. Якщо код, тести, вимоги
або конфіг перевірок відрізняються від кандидата, зупинись і назви різницю.
Зміни самої записки доказів переліч окремо; не видавай їх за частину коміту.

Прочитай AGENTS.md, docs/rules/session-data.md, views/AGENTS.md,
spec.md з Test plan, sad.md з контрактом і станами, задачі,
docs/practice/04-workflow.md, docs/practice/05-verification.md,
реалізацію й тести. Не читай examples/ або особисті дані.

Для кожного AC і потрібної NFR назви:
джерело очікуваної поведінки; файл і назву тесту; які дані той отримує;
що саме порівнює; на яку помилку не відреагує; наявний доказ або прогалину.
Перевір happy path, error, boundary, захищену поведінку S0 та межу даних.
Зверни увагу на ліміт, однаковий mtime, прямі й вкладені файли,
недоступне джерело та погоджену поведінку symlink за моїм spec.
Очікування не повинне обчислюватись тією самою production-функцією,
правильність якої перевіряємо. Git не зберігає mtime.

Для одного тесту поясни історичний RED/GREEN з уроку 4, якщо є доказ.
Старий RED має власну версію; фінальний GREEN має стосуватися кандидата.
Не вимагай штучного падіння для вже наявної поведінки.
Якщо доказу немає, так і напиши. Запропонуй один конкретний сценарій,
який перевірить важливу прогалину, але нічого не реалізуй самостійно.
Відокрем припущення про чутливість від реально запущеної перевірки.
Поверни короткий розбір і точні місця. Рішення про зміни залиш мені.
```

## C. Незалежний перегляд фіксованої версії

Надішли цей запит у свіжу сесію разом із командою під ним. Не передавай історію, в якій агент переконував себе, що реалізація правильна.

```text
Виконай незалежний review моєї session-index без виправлення коду.
FEATURE_BASE_COMMIT: <повний базовий хеш до реалізації>.
CANDIDATE_COMMIT: <повний кандидатний хеш>.
Покажи фактичний HEAD і перевір його рівність кандидатові.
Покажи базу та обсяг diff. Потрібна вся зміна від мого базового хешу
до кандидата, з усіма комітами агента, не лише останній commit/diff.
Якщо автоматично обрана база інша або робочі код/тести/вимоги/конфіг
відрізняються від кандидата, зупинись і поясни, як погодити правильний обсяг.
Нові записи доказів переліч окремо. Не включай їх у нібито перевірений коміт.

Передай свіжому рецензенту AGENTS.md, docs/rules/session-data.md,
views/AGENTS.md, мою architecture-map, spec з Test plan, SAD,
Accepted ADR, tasks.json і файли задач, tracker, повний diff,
код, тести та docs/practice/05-verification.md з фактичними доказами.
Не передавай історію розмови виконавця. Не читай examples/ чи особисті логи.
Спочатку перевір відповідність усім AC/NFR/DoD і захищеній поведінці.
Потім перевір якість, чутливість тестів і ризики безпеки.
Контракт HTTP і стани бери з мого SAD: окремі OpenAPI/screens
за навчальним override не потрібні. Не підмінюй погоджений endpoint.

Рецензент не редагує runtime, тести, fixtures, spec або налаштування.
Відтворюй лише безпечні перевірки на синтетичних даних;
для повного gate використовуй npm run verify, для показу npm run demo.
Врахуй, що підготовчі скрипти цих команд вирівнюють mtime виданих fixtures;
це не дозвіл довільно змінювати навчальні дані. Мутації тут не запускай.
Не називай текстову заборону запису технічною ізоляцією.

Кожна знахідка: file:line, порушений критерій або ризик, вплив,
спосіб відтворення чи доказ; відокрем факт від підозри.
Для кожного AC назви доказ, межу або неперевірений крок.
Керівна сесія може зберегти звіт у docs/features/session-index/_review/.
У звіті зафіксуй точні base/candidate, виконані команди й обмеження.
Якщо знахідок немає, не вигадуй їх; PASS супроводжуй межами.
Нічого автоматично не виправляй, не коміть, не запускай ship/push/PR/merge/deploy.
Після звіту зупинись: рішення щодо зауважень і приймання ухвалюю я.
```

```text
/sdd:review session-index
```

## D. Виправити погоджене зауваження

Спочатку обери маршрут. Для конкретного відтворюваного дефекту надішли запит із `/sdd:fix session-index`. Для погодженої follow-up задачі, яку підготував review, використай `/sdd:implement session-index` і вкажи її ID. Це два варіанти, не команди для послідовного автоматичного запуску.

```text
Погоджую лише таке виправлення session-index:
<номер finding, симптом, кроки відтворення, очікування за моїм AC>.
Обраний маршрут: <fix для дефекту / implement для follow-up задачі ID>.
Відкрий фактичний review: <шлях>. Поточний кандидат: <повний хеш>.
Прочитай AGENTS.md, політику session-data, вкладені views/AGENTS.md,
spec, SAD, потрібні задачі й код. Особисті дані та examples/ не читай.
Перевір поточні зміни Git; сторонню роботу не стирай і не коміть.

Спочатку відтвори проблему та поясни звʼязок із критерієм.
Додай або посиль тест, покажи валідний RED, виправ код до GREEN,
виконай npm run verify. Використовуй лише синтетичні тимчасові дані.
Видані fixtures не переписуй для проходження перевірки.
Не послаблюй AC чи assertion, щоб отримати зелений результат.
Якщо fix потребує змін spec або проблема ще не покрита вимогою,
покажи запропоноване рішення й дочекайся погодження до зміни контракту.
Для follow-up виконуй лише погоджений обсяг; нові задачі сам не додавай.

Перед комітом покажи точні файли та diff. Збереження виконаємо після
погодження. Не змінюй FEATURE_BASE_COMMIT. Старі результати не перенось
на новий кандидат без запуску. Наприкінці назви зміну, фактичні перевірки,
що потрібно повторити в браузері/HTTP і які місця передати на новий review.
Не запускай ship, push, PR, merge або deploy. Зупинись після виправлення.
```

Після нового коміту повернися до кроків перевірки кандидата. Виправлений рядок без повторного gate і незалежного перегляду ще не завершує приймання.
