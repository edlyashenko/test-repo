# Запити для роботи з контекстом

Ці повідомлення вводь у розмову з Claude Code, відкриту в корені пакета біля `package.json`. Команди npm залишаються у звичайному терміналі. Додаткових skills для цих запитів не потрібно. Перед підтвердженням змін переглянь, які файли агент збирається редагувати.

## Відкрити першу сесію

Спочатку пройди [підготовку](setup.md): завантаження пакета, встановлення залежностей, два тести та порожня сторінка на фікстурах. Залиш сервер працювати й відкрий у редакторі **Terminal → New Terminal** у тій самій теці. Перевір `claude --version`. Якщо команда не знайдена, у підготовці є окремі команди встановлення для macOS/Linux/WSL і Windows PowerShell; постав відео на паузу та повернися після перевірки версії.

Коли інструмент працює, введи у звичайному терміналі:

```sh
claude
```

Під час першого запуску пройди вхід за підказками; повторний вхід викликається через `/login` усередині Claude Code. Тепер передай перший запит:

```text
Прочитай CLAUDE.md і лише ці п’ять файлів:
server.js, lib/claude/index.js, lib/sources.js,
views/layout.js, test/skeleton.test.js.
Нічого не змінюй і не запускай команди. Особисті логи не відкривай.
Поясни, що зараз відбувається після відкриття / і /api/health.
Назви файли та функції, які це підтверджують.
Чи є вже функція, яка читає список сесій із диска?
Відділи виконуваний код від намірів у коментарях.
```

Дочекайся відповіді та відкрий названі місця в редакторі. Перш ніж просити зміни, важливо побачити, чи правильно агент описує поточний код. Вказівка не змінювати файли задає межу завдання; технічні права інструмента від цього не зникають.

## Прочитати локальні правила

```text
Прочитай CLAUDE.md, views/CLAUDE.md і .claude/rules/session-index.md.
Код не змінюй. Поясни, для якої частини проєкту потрібен кожен файл.
Порівняй шлях lib/claude/index.js із патерном lib/claude/**/*.js.
Чи підходить під цей патерн views/layout.js?
Відокрем текст вимоги від доказу її виконання.
Явне читання в цьому запиті не називай перевіркою автозавантаження.
```

## Звірити власний контекст

Перед цим відкрий `templates/02-context-pack.md` і збережи власну копію через **File → Save As** у `docs/practice/02-context.md`. Теку `practice/` створи всередині `docs/`, якщо її ще немає. Заповни контекст за кодом, правилами й roadmap та додай справжній підсумок свого запуску. Початковий шаблон залиш без змін. Тепер є конкретний документ, який можна перевірити:

```text
Прочитай docs/practice/02-context.md, CLAUDE.md, views/CLAUDE.md,
.claude/rules/session-index.md, CONTEXT.md, docs/architecture-map.md
і рішення D1-D3 у docs/roadmap.md. Звір твердження з server.js,
lib/claude/index.js, lib/sources.js, views/layout.js і test/skeleton.test.js.
Не змінюй код, тести, налаштування чи документи. Приклади в examples/ не читай.
Відокрем те, що працює зараз, від майбутнього S1 session-index.
Для кожної неточності покажи файл і функцію або рядок.
Питай лише про рішення, яких справді бракує; наявні вибори roadmap не вигадуй заново.
Наприкінці запропонуй короткі правки тільки до docs/practice/02-context.md.
Дочекайся мого рішення перед редагуванням.
```

## Записати передачу перед паузою

```text
Підготуй docs/practice/handoff.md для продовження уроку 2 в новій сесії.
Запиши мету, поточний стан скелета, шлях до docs/practice/02-context.md,
правила й файли коду для читання, погоджені рішення, змінені файли,
фактичні команди та результати, невідоме й наступний крок без реалізації.
Використовуй лише перевірені відомості цієї сесії. Якщо запуску немає,
напиши «не перевірено». Не копіюй результати з навчального прикладу.
Не додавай секретів, особистих логів чи приватних шляхів.
Змінювати можна лише docs/practice/handoff.md.
```

## Продовжити в новій сесії

Перечитай і збережи `docs/practice/handoff.md` перед виходом. Усередині Claude Code введи `/exit`. Коли повернеться звичайний shell, у тій самій теці пакета знову введи `claude`, без відновлення попередньої розмови через resume чи continue. Передай новій сесії лише запит нижче, без копіювання старого чату.

```text
Прочитай docs/practice/handoff.md, зазначений у ньому контекст,
кореневі й локальні правила та відповідні файли коду.
Файли не змінюй, session-index не реалізуй, examples/ не читай.
Поясни, що працює зараз, що має додати S1 і що до нього не входить.
Назви файли та функції, якими підтверджуються поточні факти.
Окремо назви вимоги з документів, фактичні результати перевірок і невідоме.
Не вважай позначки чекліста доказом і не домислюй пропущених запусків.
```

Звір відповідь із файлами: поточна поведінка, майбутній S1, правила й невідоме мають бути розділені. Збережи фактичний результат у своєму контексті. Жоден із цих запитів не перевіряє, чи інструмент завантажив правила автоматично: ми прямо просимо їх відкрити.

## Після відповіді: перевірити власні файли

Цей крок виконуй у звичайному терміналі, не в промпті агента. Повтори `npm run verify`. Для ZIP без Git-історії розпакуй збережений початковий архів тієї самої версії в окрему недоторкану теку й порівняй з робочою копією:

```sh
node scripts/compare-kit.mjs "<path to unpacked untouched kit>"
```

Команду запускай із робочої копії. Заміни текст у лапках на повний шлях до недоторканої теки з `package.json`: скопіюй шлях чи перетягни теку в термінал і перевір лапки. [Підготовка](setup.md) пояснює винятки та помилки. Після уроку очікуємо лише два `ADDED`, власний контекст і handoff. Код 1 означає знайдені відмінності, 2 помилку; записуй фактичний список, не очікування з прикладу.
