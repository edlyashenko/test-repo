# 0001 — Rebuild the session index synchronously per request, with no cache or persisted store

- **Status:** Accepted
- **Date:** 2026-09-10
- **Deciders:** maintainer (Architect), під час Сократичного проходу `design` (easy-режим)

## Context

`session-index` — перший крок роадмапи: перелік усіх сесій усіх проєктів на головній сторінці дашборда, зібраний з метаданих файлів (імʼя, розмір, час зміни), відсортований від найсвіжіших і обрізаний лімітом. Домашня тека джерела може містити тисячі сесій (spec §6 NFR), і на цей самий перелік спиратимуться кроки 2 (перегляд сесії) і 3 (вартість у токенах). Треба вирішити, чи будувати перелік заново на кожен запит, чи вести якийсь персистентний/кешований стан між запитами.

## Decision drivers

- spec §6 NFR: типова довжина переліку 50 рядків, стеля 1000; орієнтир ≤400ms на 200 сесій, ≤50ms на 6-сесійних фікстурах — без ворота на «свіжість» даних, лише на швидкість відповіді.
- spec §6 NFR: «Записи в домашню теку джерела — рівно 0» — будь-яке рішення не повинно вимагати запису навіть службового кеш-файлу в `CLAUDE_HOME`.
- `AGENTS.md` §agent-ops-dashboard: «Бази даних... немає» — рішення не повинно вводити персистентний стан поза файловою системою джерела.
- `docs/architecture-map.md` §Conventions: синхронний `node:fs` уже є конвенцією читання джерела (`lib/claude/index.js`, `test/oracle.js`).

## Considered options

1. **Синхронний скан без кешу** — на кожен `GET /` адаптер обходить `CLAUDE_HOME/projects` рівно два рівні, читає метадані, сортує в памʼяті й обрізає лімітом після сортування.
2. **Кешований/персистентний індекс** — окремий кеш (у памʼяті процесу або на диску поза `CLAUDE_HOME`) з інвалідацією за mtime теки проєктів.

## Decision outcome

**Chosen:** Option 1, синхронний скан без кешу. Найпростіша реалізація, що вкладається в S-розмір фічі й не вводить інвалідацію стану; орієнтир §6 NFR (≤400ms на 200 сесій) розрахований саме на цей підхід і не є воротами, тому передчасна оптимізація кешем не виправдана.

## Consequences

**Positive**
- Перелік завжди відповідає реальному стану диска — жодного застарілого кешу, жодної логіки інвалідації.
- Нуль нового стану поза файловою системою джерела; узгоджується з «Записи в домашню теку джерела — 0» і з відсутністю бази даних у репо.
- Найпростіший шлях для кроків 2/3 роадмапи, які читатимуть той самий підхід.

**Negative**
- Кожен запит повторно читає весь диск — на дуже великих домашніх теках (десятки тисяч сесій) це помітно повільніше за кешований варіант.

**Neutral**
- Перехід на кешований варіант згодом можливий, але означає окрему ітерацію: інвалідацію, можливо збереження стану, узгодженість між запитами — прийнятний борг зафіксовано в §11 SAD.
