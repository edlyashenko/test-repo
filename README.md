# Agentic Engineering: пакет учасника мінікурсу

[Відкрити анкету з підказками](https://genkovich.github.io/ai-work-check/). Вона заповнюється просто на сторінці; завантажувати пакет для цього не потрібно.

Почни з [«Як я працюю з AI: 10 простих запитань»](first-step.html). Оціни кожну звичку від 0 до 4, подивися, який стик ланцюга курсу в тебе найслабший і який урок його розбирає, і натисни «Завантажити result.json». Запитання про практики, яких курс і вчить, тому низький результат на старті очікуваний. Збережи перший результат незмінним і вибери одну звичку з підказки. На анкету можна закласти 3-5 хвилин; це орієнтир, який ще не вимірювали на пілоті.

Для першого уроку достатньо браузера. Якщо переглядаєш пакет на GitHub, обери **Code → Download ZIP**, розпакуй архів і відкрий `first-step.html` локально. Сторінка HTML на GitHub показує код. Анкета працює без встановлення залежностей, сервера чи репозиторію; відповіді не зберігаються автоматично, тому завантаж файл до закриття сторінки. Є також [текстова версія](templates/01-ai-development-audit.md).

Підказки використовують приклад списку покупок: товари вже можна додавати, а ти просиш AI додати позначку «Куплено» біля «Молоко». Додавання нового товару, наприклад «Хліб», має працювати й далі. Це лише ілюстрація; будувати таку сторінку для анкети не потрібно. Відповідай про свої звички, а за відсутності досвіду обирай відповідний варіант.

## Практика з кодом починається з уроку 2

Почни зі [сторінки другого уроку з десятьма кроками](https://genkovich.github.io/ai-work-check/context-check.html). Є і [локальна копія](context-check.html). Команди, пояснення та промпти вже на сторінці; усі файли для роботи лежать у цьому пакеті. На уроці 2 підготуєш лише контекст і handoff та перевіриш їх у новій сесії. Сам список сесій розроблятимемо в наступних уроках.

Якщо ще немає локальної копії, відкрий [приватний репозиторій пакета](https://github.com/genkovich/agentic-engineering-mini-kit) зі свого GitHub-акаунта, натисни **Code → Download ZIP** і розпакуй архів. Відкрий у редакторі саме теку, де лежить `package.json`: у VS Code це **File → Open Folder**, потім **Terminal → New Terminal**. [Покрокова підготовка](docs/lesson-2/setup.md) пояснює кожну дію, містить HTTPS-clone як альтернативу й підказує, де зробити паузу при помилці. Для всього уроку використовуємо цей один пакет.

Нижче описано репозиторій для практики з кодом, який лектор рухає на екрані: `agent-ops-dashboard`, локальний дашборд над логами сесій Claude Code (Node + Express, одна залежність). Тут він у стані **скелета**: сервер відповідає на перевірку здоровʼя, сторінка каже «No slice is wired up yet», на диску лежать шість синтетичних сесій, і два тести підтверджують, що це все працює. Жодного зрізу ще не підключено.

Твоя практика: провести перший зріз, **індекс сесій** (`session-index`), тим самим конвеєром, яким його веде лектор, від контексту до прийнятого результату. Конвеєр за замовчуванням це SDD, плагін лектора для Claude Code. Spec Kit, OpenSpec і BMAD проходять той самий маршрут іншими командами, дивись [ALTERNATIVES](ALTERNATIVES.md). Свій репозиторій теж підходить, з тими самими шаблонами: це основна доріжка головної програми, у мінікурсі вона доступна, але не обовʼязкова.

## Що потрібно

Для другого уроку потрібні [Node.js 22 або 24](https://nodejs.org/en/download), термінал, редактор і Claude Code із доступом до сервісу. У підготовці є перевірки `node --version`, `npm --version`, `claude --version` та команди встановлення Claude Code для своєї ОС. Git корисний для перегляду змін, але можна почати з розпакованого ZIP. SDD встановлювати зараз не потрібно: готові звичайні промпти є на сторінці практики та в `docs/lesson-2/prompts.md`.

Нижче наведено також підготовку SDD до наступних уроків. Для анкети першого уроку ці інструменти не потрібні.

- Node.js 22 або 24 LTS, git, термінал.
- Coding-агент: Claude Code (SDD ставиться як плагін), або Codex CLI чи Cursor (SDD ставиться скриптом). Виклики агента оплачуються за твоїм тарифом; сам дашборд і його тести модель не викликають.
- SDD у Claude Code:

```text
/plugin marketplace add genkovich/sdd
/plugin install sdd@sdd
/reload-plugins
```

Для Codex і Cursor команда встановлення в [README SDD](https://github.com/genkovich/sdd). Там же таблиця відповідників: `$sdd-specify` у Codex, `/sdd-specify` у Cursor, `/new` замість `/clear`.

## Перший запуск

У терміналі біля `package.json` спочатку встанови залежності:

```sh
npm ci
```

Дочекайся завершення та нового запрошення вводу. Якщо команда завершується помилкою, спочатку розбери її за [підготовкою](docs/lesson-2/setup.md), потім запускай тести:

```sh
npm run verify
```

Очікуємо два тести без падінь; це орієнтир, власний вивід ще треба зберегти. Після успішної перевірки запусти дашборд:

```sh
npm run demo
```

Коли термінал покаже адресу http://127.0.0.1:4180, відкрий її в браузері. На сторінці має бути «No slice is wired up yet»: шість файлів сесій на диску, нуль сесій на сторінці. Термінал із сервером залишиться зайнятим, тому для агента вибери **Terminal → New Terminal** у тій самій теці. У кроці 6 збережи дослівний вивід перевірки й короткий опис сторінки у власному `docs/practice/02-context.md` під назвою «Початковий запуск». Файл анкети першого уроку залиш окремо.

Для реалізації в наступних уроках пакет має бути git-репозиторієм: `implement` комітить кожну задачу, а `branch_strategy: feature` створює гілку. Clone це дає одразу. Після ZIP можна виконати `git init`, переглянути файли й створити початковий коміт тільки з матеріалів пакета. Не додавай приватні файли або секрети. Перед використанням SDD скопіюй `.claude/sdd.local.example.md` у `.claude/sdd.local.md`: там налаштовано найпростіший режим для першого проходу, один агент послідовно. Для завершення другого уроку ці дії не обов’язкові.

`npm start` без налаштувань вказує на справжню `~/.claude`. Для практики його не запускаємо: `demo` через `scripts/demo.mjs` явно задає абсолютну теку `fixtures/claude-home` і порт 4180, незалежно від успадкованих `CLAUDE_HOME` та `PORT`. `.env.fixtures` цей запуск не читає. Сам сервер слухає лише `127.0.0.1` і нічого на диск не пише; підготовчий `predemo` вирівнює дати навчальних фікстур.

Далі перевір `claude --version` і запусти `claude` в корені пакета. Пройди вхід за підказками та передай [перший запит на читання п’яти файлів](docs/lesson-2/prompts.md). Після власного контексту й handoff перевірка новою сесією йде так: збережи handoff, введи `/exit` всередині Claude Code, потім `claude` у звичайному shell без відновлення старої розмови. У наступних уроках SDD читатиме `docs/architecture-map.md`, `docs/roadmap.md` і `CONTEXT.md` із цього ж пакета.

Для фінальної перевірки ZIP-копії без Git розпакуй збережений початковий архів тієї самої версії в окрему недоторкану теку. Із термінала робочої копії виконай команду нижче, замінивши текст у лапках на повний шлях до початкової теки з `package.json`. Шлях можна скопіювати або перетягнути теку в термінал; перевір одну пару лапок навколо шляху з пробілами.

```sh
node scripts/compare-kit.mjs "<path to unpacked untouched kit>"
```

Команда лише читає файли й показує всі `ADDED`, `CHANGED`, `REMOVED`. Ігнорує тільки `node_modules/`, `.git/`, `.DS_Store`, `Thumbs.db`; `.claude/` включено, дати файлів не порівнюються. Символічні посилання й помилки читання зупиняють перевірку. Очікування уроку 2: лише два додані власні документи. Код завершення 1 означає відмінності, 0 їх відсутність, 2 помилку. Збережи фактичний підсумок; детальні кроки й приклад виводу є в [підготовці](docs/lesson-2/setup.md).

Для свого репо з БД і кількома екранами ці стадії обовʼязкові. Утиліти в будь-який момент: `/sdd:classify-size`, `/sdd:decide-adr`, `/sdd:config`.

Як конвеєр виглядав у сухому прогоні лектора і що в його артефактах варто помітити: [examples/session-index/README.md](examples/session-index/README.md).

## Який зріз приймаємо

Індекс сесій: на сторінці список сесій із проєктом, розміром файлу і часом останньої зміни, від свіжих до старих, зібраний лише з метаданих файлів, без читання вмісту. Пʼять типів AC, які має покрити твій spec:

- **happy:** шість сесій із фікстур видно списком, кожна з проєктом, розміром і часом; найсвіжіша перша.
- **error:** тека проєктів відсутня або нечитабельна, і сторінка показує порожній стан замість помилки.
- **boundary:** дашборд читає лише налаштовану теку; файли з `subagents/` і `tool-results/` у списку не зʼявляються.
- **invariant:** кількість сесій у переліку дорівнює кількості файлів сесій на диску на одному рівні під текою проєкту, поки їх не більше за ліміт; понад ліміт показуємо найсвіжіші.
- **Unchanged:** перевірка здоровʼя і оболонка сторінки з CSP працюють як до зрізу; два тести скелета лишаються зеленими без правок.

Заголовки сесій, таймлайн, токени і будь-що, що вимагає читати файл, у зріз не входять: це non-goals у твоєму spec, і саме вони тримають задачі в межах ~150 рядків. Назву проєкту індекс відновлює з імені теки заміною `-` на `/`, і для `checkout-api` це дає `checkout/api`: шлях неточний за задумом, тому поруч обовʼязкова позначка «похідний». Точний шлях лежить лише всередині файлу, а це вже наступний крок.

**Розширення для тих, кому вистачило часу:** людські заголовки сесій (крок S2 у `docs/roadmap.md`). Той самий конвеєр, свій slug `session-titles`, вхід: рядок S2 у roadmap. Це розмір XS, і на ньому видно, як пайплайн стискається під маленьку фічу.

## Пастки, які варто знати наперед

Зібрані з мого сухого прогону тієї самої фічі на цьому пакеті; кожна відтворилась, не з памʼяті.

- **mtime після clone однаковий у всіх шести файлів.** Git не зберігає час зміни, тому «від свіжих» без вирівнювання це тавтологія. `npm run verify` і `npm run demo` вирівнюють дати самі; `cpSync` у тесті теж ставить «зараз», тож тимчасова копія фікстур потребує власного `utimesSync`.
- **Словник без ролі.** `specify` бере ролі лише зі словника. У `CONTEXT.md` пакета роль «розробник» уже є; для свого репо додай роль першим терміном.
- **Інваріант проти ліміту.** «Рядків стільки, скільки файлів» суперечить «показуємо 50 найсвіжіших», щойно ти додаєш ліміт. Clarify це знайде; формулюй інваріант у межах ліміту одразу.
- **«Нечитабельна тека» не відтворюється на Windows.** Права через Node на NTFS не зняти; CI ганяє Windows. Крайовий випадок для error-AC бери кросплатформний: файл замість теки проєкту.
- **Хендоф веде на стадії, яких у маршруті нема.** ux-flows, api, screens, див. вище. Не йди за хендофом сліпо, звіряй із таблицею уроків.
- **Test-author може дописати «чернетку» реалізації, щоб перевірити тест.** Перед GREEN дивись `git status --short`: у дереві має бути лише тестовий файл. Червоний тест треба побачити самому; звіт агента тут доказом не є.
- **Задача типу «тести» після реалізації зелена з першого прогону.** Це сторож; RED задачі несе тест на нову поведінку. Доводь чутливість мутацією: зламай сортування або зроби обхід рекурсивним і подивись, що падає.
- **`Number.parseInt` для ліміту.** `?limit=3abc` дає 3, `?limit=1e3` дає 1. Тест, який перевіряє лише `abc`, цього не бачить. Ревʼю має брати власні входи, окремі від тестових.
- **Тест на tie-break може бути мертвим.** Усі фікстури мають різні mtime, а стабільне сортування плюс порядок readdir дають потрібний порядок і без компаратора. Компаратор перевіряй напряму.
- **Оракул і адаптер по-різному дивляться на symlink.** `statSync` іде за посиланням, адаптер його пропускає; інваріантний тест червоніє на правильній поведінці. В `test/oracle.js` пакета вже `lstatSync`.
- **Design на маршруті standard робить по коміту на секцію.** Дванадцять doc-комітів на S-фічу це нормально за протоколом; хочеш менше, збатч і напиши це в повідомленні коміту.

## Свій репозиторій замість дашборда

Підходить, якщо його безпечно запускати, у ньому немає секретів і чужих даних, а зміна вміщається в один зовнішньо видимий зріз з крайовим випадком і захищеною старою поведінкою. Маршрут той самий: `/sdd:survey` замість виданої карти, далі за таблицею. Шаблони ті самі.

## Коли пакет пройдено

Прийнятий зріз за [Verification Canvas](templates/05-verification-canvas.md): усі AC зрізу мають докази на одному коміті, незалежне ревʼю зроблене, знахідки мають рішення, межі названі. CI з `.github/workflows/verify.yml` запускається лише у твоєму форку на GitHub; локальний `npm run verify` він не заміняє. Потім [фінальна анкета](final-step.html) уроку 6: 35 запитань про практики основної програми. Стартовий файл вона не читає, але поклади його поруч: стики ті самі, і по них видно, що змінилось. Окремо запиши один приклад із практики й результат його перевірки за [шаблоном уроку 6](templates/06-delta-audit.md). Бали описують звички й не доводять працездатності коду. Заповнені файли без прогону перевірок пакет не закривають.

## Якщо щось не працює

Якщо практика зупинилася на помилці, почни з її тексту. Нижче зібрані ситуації, які можуть трапитися під час запуску пакета й роботи з агентом. Знайди схожу на свою та пройди запропоновані перевірки. Не кожна помилка означає, що ти вже щось зламав у фічі: іноді термінал просто відкритий не в тій теці.

### Термінал не знаходить Node або не запускає пакет

Якщо команда `node` або `npm` не знайдена, встанови Node 22 або 24 LTS з [nodejs.org](https://nodejs.org/en/download). Після встановлення відкрий новий термінал і виконай `node --version`, щоб побачити доступну версію.

Якщо `npm ci` зупиняється на lock-файлі, перевір поточну теку. Ти маєш бути в корені пакета, поруч із `package.json`. Також перевір Node: версії нижче 20 пакет не підтримує.

Поточний `npm run demo` запускає `scripts/demo.mjs` без `--env-file`. Якщо бачиш `bad option: --env-file`, перевір версію пакета й команду в `package.json`: імовірно, це старі матеріали. Для курсу перевір Node 22 або 24 й візьми актуальний пакет, зберігши власні документи.

### Сервер не може відкрити порт

Якщо порт 4180 зайнятий, можливо, твій попередній запуск дашборда ще працює. Повернися до його термінала й зупини через Ctrl+C. Навчальний launcher фіксує порт 4180; зміна `.env.fixtures` чи успадкованого `PORT` його не перемикає. Якщо порт займає інша потрібна програма, постав практику на паузу й узгодь запуск із командою курсу. Чужі процеси зупиняти не потрібно.

Помилки `EPERM` чи `EACCES` на `listen` означають, що середовище забороняє локальний сервер. Дозволь localhost або повтори запуск у звичайному терміналі. Такий результат стосується середовища; його не можна записувати як RED, що доводить відсутню поведінку твоєї задачі.

### На сторінці не те, чого ти очікував

Якщо після своїх змін бачиш свої справжні сесії замість шести навчальних, ти запустив `npm start` без змінних оточення. У такому режимі дашборд читає `~/.claude`. Зупини його й запусти `npm run demo`. Сам дашборд лише читає диск, нічого не записує й слухає `127.0.0.1`; дані через нього нікуди не надсилалися.

Порожня сторінка «No slice is wired up yet» на старті очікувана. Список сесій ти додаватимеш під час курсу. Для практики вистачить даних із `fixtures/`, домашню теку `~/.claude` підключати не потрібно.

Якщо список є, але порядок «від свіжих» не збігається з датами в файлах, ти запустив сервер не через `npm run demo`, а напряму. Git не зберігає mtime, після clone усі шість файлів мають одну дату; `predemo` і `preverify` вирівнюють їх скриптом `scripts/pin-fixture-mtimes.mjs`. Запусти його рукою або перезапусти через `npm run demo`.

### Агент не знаходить документ або команду SDD

Коли `/sdd:specify` не бачить карти архітектури, перевір, у якій теці відкритий агент. У нашому пакеті файл `docs/architecture-map.md` уже є, і працювати треба з кореня репозиторію. Якщо взяв власний проєкт, спочатку виконай `/sdd:survey`.

Якщо в списку взагалі немає команд `/sdd:…`, плагін може бути не встановлений або ще не перезавантажений. Виконай `/plugin install sdd@sdd`, потім `/reload-plugins`. У Codex і Cursor назви відрізняються: шукай `$sdd-specify` або `/sdd-specify`, як описано в README SDD.

### Перевірки зупинили роботу

Якщо `/sdd:implement` вимагає lint, у цьому репозиторії лінтера справді немає. Постав `gate_lint: false` у `.claude/sdd.local.md` або зафіксуй це у Verification Canvas: перевірка ввімкнена, але команди для неї не налаштовано.

Якщо після твоїх змін `npm run verify` показує червоний тест, прочитай його назву й перший assertion. Вони допоможуть зрозуміти, яка поведінка змінилася. Збереження старої поведінки скелета входить до AC, тому міняти очікування двох стартових тестів лише заради зеленого результату не можна.

Якщо тест зелений у тебе і червоний у CI на Windows, глянь, чи не викликає він `find`, `grep`, `wc` або `jq` через shell. Таких команд там немає. Підрахунки з диска роби через `test/oracle.js`, він на чистому Node.

Гілки Node звірені з [таблицею релізів](https://nodejs.org/en/about/previous-releases) на 2026-09-06: 22 і 24 в LTS, 20 вже EOL.
