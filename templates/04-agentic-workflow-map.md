# Карта виконання: session-index

Це коротка записка про те, як ми виконуємо погоджений план і що вже перевірили. Сам план залишається в `tasks.json` та файлах задач. Не потрібно вдруге переписувати сюди залежності, вимоги або критерії: дві копії легко розійдуться.

В уроці 4 створи свою карту як `docs/practice/04-workflow.md`. Можна попросити агента заповнити її за запитом A з [практики](../lessons/04-implementation.md#a-підготувати-карту-без-змін-коду). ## 2. Як виконуємо роботу

Для першого проходу використовуємо одного агента послідовно. Він виконує різні дії циклу TDD, але ці дії не стають трьома ізольованими субагентами. Незалежне ревʼю всієї зміни буде в уроці 5.

| Крок | Хто виконує і чому | Вхід | Вихід | Як перевіряємо | Якщо не вийшло |
|---|---|---|---|---|---|
| Обрати задачу | Агент читає погоджений порядок | tasks.json, tracker, файл задачі | ID і пояснення готовності | Людина звіряє залежності | Не запускати заблоковану задачу |
| RED | Той самий агент переводить AC у тест | Файл задачі, потрібний AC і Test plan | Тест і фактичний рядок падіння | Чи падає через відсутню поведінку? | Виправити зламаний тест або уточнити вимогу |
| GREEN і рефакторинг | Агент змінює код у межах задачі | Валідний RED, погоджений підхід | Код і повторний результат тесту | Потрібна поведінка зʼявилася | Пауза за лімітом; не послаблювати вимогу |
| Повна перевірка | Скрипт повторює задані перевірки | Поточний код і тести | Вивід npm run verify, код завершення | Людина читає підсумок і межі | Не позначати задачу done |
| Зберегти результат | Агент або людина за налаштуванням Git | Перевірені зміни задачі | Коміт або явний запис незакомічених змін; tracker | Зіставити задачу, diff і gate | Не додавати сторонні файли |
| Передати до уроку 5 | Людина переглядає стан | Зміни від базового хешу, tracker, логи, сторінка | Чесний підсумок у §4 | Усі задачі виконано чи прохід частковий? | Записати блокер і наступну дію |

## 3. Налаштування, права та зупинки

Наявну `.claude/sdd.local.md` змінюємо через `/sdd:config` лише в погоджених полях. Повного нового файла поверх старого не вставляємо. [Запит B](../lessons/04-implementation.md#b-погодити-налаштування) задає значення для цієї вправи.

- **Режим, який підтвердив запуск:** `<sequential; фактичний banner>`.
- **Команда перевірки:** `<фактично виявлена команда; очікуємо npm run verify>`.
- **Git:** `<чинні auto_commit і branch_strategy; хто робить коміт>`.
- **Дозволені зміни:** `<файли задач; тести; потрібне оновлення tracker>`.
- **Без окремого рішення не змінюємо:** вимоги, ADR, правила, адаптери інструкцій, видані fixtures, залежності та межі доступу.
- **Механізм обмеження прав:** `<фактичні permissions / лише інструкція>`. Текст запиту сам не створює файлової ізоляції.

`require_integration: never` вимикає окрему інтеграційну стадію SDD із перевіркою Docker. Наші файлові та HTTP-перевірки мають виконуватися всередині `npm run verify`; це налаштування їх не скасовує.

`max_red_retries: 3` задає кількість звичайних повторів GREEN до подальшої ескалації SDD. Це не глобальна стеля всіх спроб: стандартний процес може змінити модель або поділити задачу. Для навчання додатково просимо паузу після трьох невдалих спроб GREEN на одній задачі, до такої ескалації. Це інструкція в запиті; її виконання контролює людина.

- **Пауза після першої задачі:** `<попросили; агент підтвердив / довелося зупинити вручну>`.
- **Бюджет усього проходу:** `<доступний час або вартість>`.
- **Як стежимо:** `<таймер / фактичний лічильник витрат інструмента>`.
- **Коли зупиняємося:** перша задача завершена; три невдалі GREEN на одній задачі; бюджет вичерпано; потрібне нове рішення щодо вимог, прав або залежностей.
- **Що зберігаємо при зупинці:** `<ID задачі, diff, остання команда та результат, невідоме питання>`.

Не запускаємо `review`, `ship` або розгортання автоматично. Пауза не означає дозвіл стерти поточну роботу: спочатку фіксуємо стан і вирішуємо, які саме власні зміни можна відкотити.

## 4. Що відбулося насправді

Коротко запиши факти. Детальний стан кожної задачі залишається у tracker; нижче потрібні докази навчального проходу та відхилення від очікуваного.

| Момент | Факт або посилання на збережений вивід |
|---|---|
| Перший RED | `<ID, команда, точний рядок, чому це валідне падіння>` |
| GREEN тієї самої перевірки | `<команда та фактичний результат>` |
| Повний gate після задачі | `<npm run verify; підсумок; що перевірка не доводить>` |
| Збереження задачі | `<хеш із SDD-Task/SDD-AC або чому зміни ще не в коміті>` |
| Послідовність | `<посилання на tracker; пояснення розбіжностей із планом>` |
| Сторінка після всіх задач | `<адреса із SAD, що фактично видно; або не перевірено>` |
| Поточний обсяг | `<усі задачі реалізовано / частково / заблоковано; посилання на tracker>` |
| Що далі | `<продовжити конкретну задачу / перейти до перевірки уроку 5>` |

Щоб побачити також коміти агента, заміни `FEATURE_BASE_COMMIT` нижче на свій повний хеш. Це позначення для підстановки, не готова shell-змінна.

```sh
git log --oneline FEATURE_BASE_COMMIT..HEAD
git diff FEATURE_BASE_COMMIT..HEAD
git diff
git diff --cached
git status --short
```

Нові невідстежувані файли відкрий окремо: diff їх не покаже.
