# Записка перевірки: session-index

Тут зберігаємо достатньо фактів, щоб пояснити рішення про приймання: яку версію перевіряли, за якими вимогами, що побачили й чого ще не знаємо. Заява агента «готово» та приклад у відео не є результатами твоєї перевірки.

У практиці уроку 5 створи свій файл як `docs/practice/05-verification.md`. Допоможе [запит A](../lessons/05-verification.md#a-записка-перевірки-з-реальних-виводів). Заміни підказки фактичними даними. Якщо перевірку не виконано, так і напиши. Не потрібно копіювати сюди весь Test plan, задачі або довгі логи.

## 2. Докази за вимогами

Для кожного AC і потрібної NFR додай рядок. Один критерій може потребувати кількох перевірок: наприклад, тесту файлового читання та перегляду сторінки. ID та очікування бери зі свого spec. Error, boundary й захищена поведінка мають бути видимі, без приховування в загальному «все працює».

| Вимога та джерело | Перевірка / команда / дія | Фактичний результат і дата | Де доказ; версія | Межа або прогалина |
|---|---|---|---|---|
| `<AC-ID, секція spec>` | `<назва тесту, команда або дія>` | `<фактичний підсумок; код завершення>` | `<шлях до логу/скріншота; повний хеш>` | `<чого ця перевірка не бачить>` |

**Повний gate кандидата:**

Код завершення: <фактичний>
Доказ: <точний шлях або потрібні рядки виводу>
~~~

- **Екран і HTTP:** `<адреса та сценарії зі свого SAD; фактичні результати; або не перевірено>`.
- **Автоматичний запуск:** `<що справді запускає наявний CI / лише локально / не перевірено>`.
- **Блокування merge:** `<чим підтверджено налаштування / не встановлено / не перевірено>`.
- **Hook у репо:** `<Stop-hook з npm run verify підключений у .claude/settings.json; контрольний провал: зламаний assert дав 2, після git restore 0 / не підключений / Codex або Cursor: pre-commit або verify руками>`.

Код завершення 0 не доводить пропущену перевірку. Якщо потрібний для AC тест має skipped чи todo, це прогалина. Лічильник усіх тестів не замінює відповідності вимогам.

## 3. Сила одного тесту

Обери один зрозумілий критерій. Наприклад, порядок двох сесій з однаковим часом зміни: якщо тест має лише різні дати, він не перевіряє це правило.

- **Критерій:** `<ID і джерело>`.
- **Тест:** `<файл, назва>`.
- **Звідки очікування:** `<правило spec; чому очікування незалежне від production-функції>`.
- **Історичний RED:** `<власний хеш/стан, команда, точний рядок падіння й причина; або доказ не збережено>`.
- **Історичний GREEN:** `<його версія та результат; або поведінка працювала до змін>`.
- **GREEN кандидата:** `<посилання на фактичний запуск у §2>`.
- **Яку помилку тест може пропустити:** `<конкретний сценарій>`.
- **Перевірка чутливості:** `<фактично виконана на ізольованій копії: версія, зміна, команда й результат / не запускалася; лише гіпотеза>`.

Історичний RED має право належати старій версії: це доказ розвитку тесту, не приймання поточного коду. Помилка імпорту або середовища не є поведінковим RED. Якщо тест був зелений відразу, поясни наявну поведінку або слабкість перевірки; не вимагай штучного падіння.

Контрольована мутація необовʼязкова для цієї вправи. Її запускають тільки в окремій одноразовій копії точного коміту із синтетичними даними. Робочу реалізацію, видані fixtures та особисті логи заради демонстрації не змінюємо.

## 4. Незалежне ревʼю та виправлення

- **Рецензент:** `<свіжа сесія/модель або колега; дата>`.
- **Обсяг:** `<точні базовий і кандидатний хеші; вся зміна фічі>`.
- **Отримані джерела:** `<spec, SAD, ADR, задачі, diff, код, тести, фактичні докази>`.
- **Права:** `<фактичне технічне обмеження / лише інструкція не редагувати>`.
- **Звіт:** `<точний шлях у docs/features/session-index/_review/ або інший фактичний запис>`.
- **Вердикт і межі:** `<PASS / CHANGES REQUESTED або фактичний вердикт колеги; що не перевірено>`.

Три погляди на один обсяг. Другий і третій запускаються після першого в свіжому контексті; порожній список із названими межами теж результат.

| Погляд | Інструмент | Обсяг | Знахідок | Звіт |
|---|---|---|---|---|
| Ревʼю за spec | `/sdd:review session-index` або відповідник | `<FEATURE_BASE_COMMIT..CANDIDATE_COMMIT>` | `<число>` | `<шлях у _review/>` |
| Коректність коду | `/code-review medium <BASE>...<CANDIDATE>` або запит C | `<той самий діапазон>` | `<число або «не знайдено в обсязі»>` | `<де збережено вивід>` |
| Безпека | `/security-review` або блок «безпека» запиту C | `<той самий діапазон>` | `<число або «не знайдено в обсязі»; класи, які дивились>` | `<де збережено вивід>` |

| Знахідка та місце | Вплив / порушене правило | Рішення людини | Виправлення й повторна перевірка |
|---|---|---|---|
| `<ID, file:line, джерело>` | `<наслідок і доказ>` | `<виправити / відкласти: чому, хто, коли / відхилити: доказ>` | `<новий хеш, команда, результат і повторний review / не застосовується>` |

Якщо знахідок немає, напиши «не знайдено в перевіреному обсязі» та назви межі. Вигадувати дефект не потрібно. Зміни коду або тестів створюють нового кандидата: повтори його gate, зачеплені ручні сценарії й незалежне ревʼю. Старі звіти залишаються історією.

Відкладений дефект, який порушує погоджений AC або безпеку, не стає прийнятним через запис у таблиці. Потрібне виправлення чи явне нове погодження вимог із наступною перевіркою.

- **Хто погодив і коли:** `<імʼя, дата>`.
- **Наступна дія:** `<потрібне виправлення / тема для уроку 6>`.
- **Один висновок для Learning:** `<що пропустило помилку; який тест, уточнення або gate варто обговорити; або чому нового механізму не потрібно>`.

Це локальне приймання. Воно не запускає автоматично ship, push, PR, merge чи deploy. Рекомендація скіла перейти далі не замінює дозволу людини.

## Перевір себе

- [ ] Усі задачі завершені; кожен AC і потрібна NFR мають доказ кандидата або чесну прогалину.
- [ ] Є фактичний gate; skipped, todo й межі не сховані.
- [ ] Один тест пояснено без штучного RED; історичні докази мають власні версії.
- [ ] Незалежне ревʼю охопило всю зміну; findings мають рішення, після виправлень перевірки оновлено.
- [ ] Рішення про приймання моє; обмеження й наступна дія записані.
