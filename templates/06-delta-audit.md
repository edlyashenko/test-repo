# Підсумок: що беру в наступну задачу

Цей документ допомагає зрозуміти власний досвід на session-index. Тут достатньо коротких відповідей і посилань на фактичні джерела. Новий план реалізації, копія всіх тестів чи вигаданий звіт про прогрес не потрібні.

Збережи свою копію як `docs/practice/06-delta.md`. Якщо така записка вже є, продовж її без перезапису. У редакторі можна відкрити практику `docs/lesson-6/README.md` та запит A у `docs/lesson-6/prompts.md`. Тут і далі шляхи до власних документів рахуємо від кореня репозиторію.

## 1. Джерела й версія

- **Початковий результат:** `<файл, дата, версія анкети / початкового запису немає>`.
- **Записка перевірки:** `docs/practice/05-verification.md`, `<потрібні розділи>`.
- **Перевірений кандидат:** `<точний CANDIDATE_COMMIT з уроку 5 / не встановлено>`.
- **Рішення з уроку 5:** `<дослівний статус та назване обмеження, якщо є / рішення немає>`.
- **Чи є пізніші зміни коду, тестів, вимог або налаштувань:** `<які саме / немає / не перевірено>`.
- **Інші використані джерела:** `<власні spec, SAD, карта виконання, тест, звіт ревʼю; точні шляхи й потрібні розділи>`.

Старі запуски залишаються доказами своїх версій. Новий коміт записки не змінює кандидат заднім числом. Для приймання зміненого коду потрібні новий кандидат і перевірки за уроком 5. Тут можна послатися на вже зібрані докази без обовʼязкового повторного запуску.

## 2. До курсу й на цій задачі

Запиши одну-дві конкретні дії в кожному рядку. Колонку «До курсу» заповнюй за початковим записом; якщо його немає, так і познач. Не відновлюй бажаний результат із памʼяті.

| Частина роботи | До курсу: що є в початковому записі | На цій session-index | Джерело або прогалина |
|---|---|---|---|
| Зрозуміла задача | `<відповідь / запису немає>` | `<як погоджено поведінку й межі>` | `<spec, розділ / чого немає>` |
| Потрібна інформація | `<відповідь / запису немає>` | `<який контекст використано>` | `<документ і приклад / не підтверджено>` |
| Робота по кроках | `<відповідь / запису немає>` | `<як виконано погоджені задачі>` | `<карта, tracker, історія / прогалина>` |
| Перевірка результату | `<відповідь / запису немає>` | `<що перевірено й ким прийнято>` | `<доказ із датою та версією / не перевірено>` |
| Корисні висновки | `<відповідь / запису немає>` | `<що вже збережено або лише запропоновано>` | `<запис, перевірка / поки план>` |

Одна задача показує застосування практики в одному випадку. Для висновку «роблю це зазвичай» потрібен повторюваний досвід. Різні анкети не дають порівнюваних балів навіть за однакових назв груп. Ця таблиця також не вимірює приріст продуктивності.

## 3. Один корисний висновок

Підійде проблема, прогалина в доказах або вдалий механізм. Вигадувати дефект для завершення уроку не потрібно.

- **Спостереження:** `<що саме сталося або чого бракує>`.
- **Джерело:** `<потрібне місце у власному документі, тесті чи звіті; дата й версія доказу>`.
- **Пояснення:** `<підтверджена причина й доказ / гіпотеза / причина ще невідома>`.
- **Межа висновку:** `<чого цей випадок не доводить>`.
- **Що варто зберегти або змінити:** `<тест, перевірка, уточнення документа, повторення вдалої дії / нового механізму не потрібно, чому>`.

Навчальний приклад: тест із різними датами файлів не перевіряє порядок за однакового mtime. Звідси ще не випливає, що код сортує неправильно. Для такого висновку потрібен окремий доказ.

## 4. Одна наступна дія

- **Моя дія:** `<одна конкретна зміна або повторення вдалої практики>`.
- **Де й коли застосую:** `<задача, документ чи перевірка; дата YYYY-MM-DD>`.
- **Як перевірю результат:** `<який випадок, очікування та фактичний доказ потрібні>`.
- **Коли повернуся до результату:** `<дата YYYY-MM-DD>`.
- **Що може змінити мій висновок:** `<який результат покаже, що обране поліпшення не допомагає>`.

Стан обраного механізму зараз:

- **Рішення зафіксовано:** `<де / ще ні>`.
- **Дію механізму перевірено:** `<випадок, доказ і версія / не перевірено>`.
- **Провал блокує потрібну дію:** `<яку дію і де доказ / не перевірено / блокування тут не потрібне, чому>`.

Кожна властивість потребує власного доказу. Сам файл із правилом не доводить його виконання. Якщо дія поки запланована, залиш відповідні перевірки як невиконані. Нове правило, зміна коду чи налаштувань потребують окремого погодженого виконання; підсумкова записка не запускає його автоматично.

## 5. Чесний підсумок

- **Стан навчальної фічі:** `<рішення для точного кандидата за уроком 5 / приймання не завершено>`.
- **Що залишається незакритим:** `<суттєва прогалина й наступний крок / у погодженому обсязі відкритих прогалин не зафіксовано>`.
- **Що тепер можу пояснити на власному прикладі:** `<одне конкретне вміння>`.

Можна завершити рефлексію з чесною прогалиною. Але суттєва непідтверджена вимога залишається перешкодою для приймання фічі.

За бажанням відкрий у браузері `final-step.html`: там 35 запитань для пошуку наступних тем. У редакторі є `templates/06-team-adoption-checklist.md` із сімома командними питаннями. Обидва матеріали необовʼязкові. Результат іншої анкети не порівнюємо чисельно зі стартовим, а бал не визначає готовність коду чи потребу купувати програму.

Якщо хочеш обговорити участь в основній програмі, на [чинному сайті](https://agenticengineering.it.com/) натисни «Залишити анкету». Це заявка на консультацію щодо покупки, окрема від навчальної самооцінки. Для завершення цього документа вона не потрібна.
