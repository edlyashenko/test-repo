## 5. Acceptance criteria

<!-- instruction: щонайменше по одному AC кожного з пʼяти типів покриття. Формат:

### AC-NN (US-XX) - <тип>
**Given** <передумови з погляду ролі: стан її обʼєктів, попередні події>
**When** <дія ролі>
**Then** <що роль бачить / що система блокує і як пояснює / що система записує>

AC описує результат, який видно ззовні. НЕ описує, як система це робить.

Заборонено в тексті AC (без винятків):
- HTTP-дієслова (GET/POST) і шляхи (`/api/sessions`)
- числові коди відповіді (200/404/500)
- рядки кодів помилок вигляду `module.error_name`
- фрагменти JSON і назви полів payload
- SQL і назви обмежень БД
- імена файлів і функцій реалізації
Усе це живе в контракті API і в задачах. Тут лише те, що спостерігає роль.

Пʼять обовʼязкових типів:
1. happy: роль робить головну дію → система записує і підтверджує.
2. error: некоректний вхід або битий файл → система не падає і показує решту / пояснює.
3. authorization / boundary: роль або процес без права → система відмовляє або не показує.
   Для локального інструмента це межа читання: лише налаштована тека, нічого поза нею.
4. domain invariant: роль порушує названий інваріант → система блокує і називає його.
   Для індексу сесій інваріант: кількість сесій у переліку дорівнює кількості файлів сесій
   на диску на одному рівні під текою проєкту, ні більше, ні менше.
5. cross-context: дія залежить від стану в іншому контексті → система дотримує правило
   на стику. Для дашборда це стик із наявною поведінкою: перевірка здоровʼя і оболонка
   сторінки працюють як до зрізу (Unchanged нижче).

Тип, який до задачі не застосовується, познач `N/A: причина`, не пропускай мовчки.
Крайовий випадок того самого AC додавай як AC-NNb. Один AC може потребувати кількох
перевірок (unit + HTTP + браузер); «один AC = один тест» це помилка.

Legacy-зміна: додай під AC блок Current / Expected / Unchanged: що підтверджено сьогодні,
що змінюється, що мусить працювати як раніше. Unchanged це теж AC, з власною перевіркою. -->
