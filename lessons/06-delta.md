# Урок 6. Що беремо в наступну задачу

Теорія цього уроку є в уроці LMS; тут лише практика.

## Мета

Зʼясувати, що досвід уроків 2–5 змінив у способі роботи, і записати це в один файл `docs/practice/06-delta.md`: порівняти конкретні дії до курсу й на цій `session-index`, розібрати один висновок і вибрати наступну дію. Новий застосунок, ще один скіл або повторний запуск усіх тестів для цього не потрібні.

## Що має бути готове

- Реалізація після уроків 4 і 5 та записка `docs/practice/05-verification.md` з `CANDIDATE_COMMIT`, доказами й рішенням про приймання. Суттєве незакрите зауваження з уроку 5 може залишитися наступною дією; приховувати його заради завершення уроку не треба. Якщо записки уроку 5 немає, кандидатом буде останній коміт фічі з `git log`, а докази беремо з `docs/features/session-index/_review/`.
- Збережений результат першої анкети з уроку 1, якщо він є: відкрий збережений файл, у репо його не клади. Без нього колонка «До курсу» отримає позначку «початкового запису немає».
- [Шаблон підсумкової записки](../templates/06-delta-audit.md).

Нижче вісім кроків. Коли лектор відкриває документ, відкривай свою версію того самого документа; на відео достатньо розібрати один рядок порівняння та один висновок, решту заповни на паузі.

## Кроки

### 1. Відкрий ту саму роботу

Через **File → Open Folder** відкрий теку своєї реалізації в редакторі. Не завантажуй чистий кіт поверх цієї роботи: у виданому початковому стані S0 фіча ще не реалізована. Через **Terminal → New Terminal** відкрий термінал у корені проєкту; ці команди лише показують стан:

```sh
git rev-parse --show-toplevel
git branch --show-current
git status --short
git rev-parse HEAD
```

Подивися на шлях і назву гілки. Не перемикайся на гілку з назвою `practice` лише за прикладом: потрібна саме твоя робота.

- [ ] Знаю, яку копію проєкту відкрито; сторонні зміни не видалено.

### 2. Прочитай рішення з уроку 5

Відкрий `docs/practice/05-verification.md`. Знайди `CANDIDATE_COMMIT`, докази за вимогами, незалежне ревʼю та своє рішення про приймання. `FEATURE_BASE_COMMIT` лишається початковою межею з четвертого уроку.

Якщо записки уроку 5 немає (Канва 05 була бонусом), візьми кандидатом останній коміт фічі:

```sh
git log --oneline -10
```

Докази тоді беремо зі звітів у `docs/features/session-index/_review/`. У записці так і напиши: кандидат узято з `git log`, рішення про приймання окремо не записане.

Поточний `HEAD` може відрізнятися від кандидата через пізніший коміт самої записки. Це не переносить перевірку на нову версію. Якщо після кандидата змінено код, тести, вимоги чи налаштування перевірок, зазнач це: для приймання нового стану потрібно повернутися до [уроку 5](05-verification.md).

Для цього підсумку можна використати наявні докази з їхньою датою та версією. Не треба запускати тест ще раз лише заради свіжої дати. Якщо документа чи доказу немає, познач прогалину; не проси агента відновити успішний запуск із памʼяті.

- [ ] Відомі перевірений кандидат, рішення та межі доказів або явно записано, чого бракує.

### 3. Створи одну підсумкову записку

Відкрий [шаблон](../templates/06-delta-audit.md). У ньому три частини: дії до курсу й на цій задачі (першим рядком там джерела), один висновок і наступний крок.

У панелі файлів редактора створи `docs/practice/06-delta.md` і скопіюй у нього шаблон. Якщо файл уже є, продовж його, не замінюй заповнені відповіді. Інший варіант: надішли [запит A](#a-підготувати-підсумкову-записку) агенту в цьому проєкті. Він допоможе з чернеткою, але особисті відповіді й рішення залишаються за тобою.

Перенеси точний `CANDIDATE_COMMIT` із записки уроку 5 або з `git log`, якщо записки немає. Вставляй посилання на власні документи замість копіювання всіх логів. Для файлів збережи шляхи від кореня репозиторію.

- [ ] Є один підсумковий файл; результати без джерела не заповнено за мене.

### 4. Порівняй дії, які можеш описати

Відкрий збережений результат першої анкети. Не переписуй його і не клади в репо. Якщо файла немає, у колонці «До курсу» зазнач «початкового запису немає».

У §1 записки є пʼять рядків: задача, контекст, виконання, перевірка, висновки. Для кожного коротко запиши, що видно на цій `session-index`, і назви документ чи результат. Наприклад: «У spec є правило сортування; у записці перевірки є результат тесту цього правила». Якщо результату тесту немає, залиш тільки те, що справді відомо.

Один прохід показує твої дії на одній задачі. Він ще не доводить звичку «завжди перевіряю». Не обчислюй зростання продуктивності або різницю балів між різними анкетами. Без стартового запису сьогоднішній підсумок стане точкою відліку для наступного порівняння.

- [ ] Заповнено пʼять рядків; факти відділено від припущень і відсутнього досвіду.

### 5. Розбери один корисний висновок

Обери один випадок з уроку 5, який допоміг помітити проблему або показав межу перевірки. Підійде і вдалий механізм: наприклад, рецензент знайшов потрібне правило в spec без повторного пояснення в чаті.

Навчальний приклад, не готовий результат твоєї роботи: у вимогах описано порядок сесій з однаковим `mtime`, але тестові дані містять тільки різні дати. Це пояснює, чому саме цей тест не перевіряє додаткове правило сортування. Чи є помилка в самому сортуванні, без іншого доказу ще невідомо.

У §2 назви спостереження, його джерело, можливе пояснення та межу знання. Створювати нове правило після кожного випадку не потрібно. Якщо причини не перевірено, назви її гіпотезою.

- [ ] Один висновок спирається на власний випадок; не вигадано дефект, причину чи виправлення.

### 6. Обери наступну дію та спосіб її перевірити

У §3 запиши одну посильну дію, дату та очікуваний доказ. Тут же вибери механізм: тест, автоматичну перевірку, уточнення документа або повторення вдалого способу роботи. Для прикладу з однаковими датами це може бути: «Уточнити тестові дані для погодженого правила сортування; перевірити, що очікуваний порядок взято зі spec». Нові тести чи код зараз автоматично не запускаємо в роботу.

Розрізняй три речі: рішення записано; механізм перевірено на визначеному випадку; його провал блокує потрібну дію. Файл із правилом не доводить двох останніх. Якщо поліпшення лише заплановано, так і напиши. Коли зміна зачепить код або перевірки, докази для нового кандидата збираємо за уроком 5.

- [ ] Є одна наступна дія, дата й спосіб перевірки; план не названо вже виконаним поліпшенням.

### 7. Дай комусь перевірити логіку записки

Перечитай записку самостійно або передай її колезі. За бажанням у новій сесії агента надішли [запит B](#b-перевірити-висновки-без-редагування). Спеціальний скіл для цього не потрібний.

Агент шукає лише непідтверджені висновки, суперечності версій і незрозумілу наступну дію. Це перевірка підсумкової записки, не повторне незалежне приймання коду. Він повертає зауваження без редагування файлів; текстова заборона запису сама по собі не встановлює технічних обмежень доступу.

Прочитай кожне зауваження та самостійно виправ потрібні місця. Не підвищуй оцінку результату лише тому, що агент назвав записку переконливою.

- [ ] Можна простежити кожен важливий висновок до джерела або чесної позначки «не перевірено».

### 8. Збережи підсумок і визнач наступний крок

В останньому рядку §3 назви стан фічі за уроком 5 окремо від результату цієї рефлексії. Можна завершити записку з чесною прогалиною. Називати весь навчальний зріз прийнятим до її закриття не можна.

Збережи файл через **File → Save** і закоміть його разом з рештою роботи. PR і deploy для вправи не потрібні. Як здати роботу на сертифікат, описано в [README](../README.md#сертифікат). Потім пройди фінальну анкету на 33 запитання ([`final-step.html`](../final-step.html) у пакеті або та сама сторінка на GitHub Pages): 11 тем, одна роль, інженер на проєкті з агентом. Вона показує, які теми в тебе зараз найслабші, і що з цього дає основна програма. Результат відкрий і збережи в себе, у репо його не клади. Якщо відповідаєш за команду, за бажанням вибери одне з [семи командних питань](../templates/06-team-adoption-checklist.md).

Тепер у тебе є конкретний наступний крок, який можна виконати самостійно. Якщо потрібне обговорення участі в основній програмі, заповни [анкету на сайті](https://agenticengineering.it.com/agenticintensive01/anketa?utm_source=kit): це окрема заявка на консультацію щодо покупки, необовʼязкова для завершення Інтенсиву.

- [ ] Записку збережено; знаю стан фічі й наступну дію; чужі обіцянки не підміняють власних доказів.

## Готові запити

Ці запити допомагають прочитати досвід, який уже є в проєкті. Вони не запускають нову реалізацію чи приймання.

### A. Підготувати підсумкову записку

Надішли в чат агента у своїй копії кіта. Якщо початковий результат анкети збережений поза проєктом, самостійно прочитай його й додай потрібні відповіді без особистих даних. Агенту не потрібно шукати файли по всьому компʼютеру.

```text
Допоможи підготувати docs/practice/06-delta.md за templates/06-delta-audit.md для моєї session-index.

Спочатку прочитай AGENTS.md, шаблон, docs/practice/05-verification.md і лише потрібні посилання з цієї записки. Якщо docs/practice/05-verification.md немає, візьми кандидатом останній коміт фічі з git log, а докази зі звітів у docs/features/session-index/_review/, і прямо напиши, що рішення про приймання не записане. За потреби звір попередні docs/practice/04-workflow.md, docs/features/session-index/spec.md та sad.md. Не читай examples/, особисті логи, секрети або файли поза цим проєктом. Скажи, яких потрібних документів немає.

Покажи точний CANDIDATE_COMMIT і рішення з уроку 5, якщо воно є. HEAD не підставляй замість перевіреного кандидата. Факти з наявних доказів залиш із їхніми версіями й датами. Не запускай тести, сервер, SDD, install, git write, push чи deploy.

Склади чернетку трьох частин шаблону. Для пʼяти рядків порівняння назви факти з цієї задачі та джерела. Особисті стартові відповіді не вигадуй. Якщо початкового запису немає серед наданих матеріалів, напиши «початкового запису немає». Один прохід не називай сталою звичкою, бали різних анкет не порівнюй, приріст продуктивності не обчислюй.

Запропонуй один висновок зі справжнього спостереження: проблема, прогалина або вдалий механізм. Відділи підтверджену причину від гіпотези. Не вигадуй дефект чи RED/GREEN. Запропонуй одну наступну дію з перевіркою; дату й остаточний вибір залиш мені.

Можеш створити лише docs/practice/06-delta.md. Якщо він уже заповнений, спершу покажи пропоновані зміни в чаті без перезапису. Інші файли не змінюй. Наприкінці переліч, що заповнено за джерелами, а що маю вирішити я. Статус приймання фічі не підвищуй.
```

### B. Перевірити висновки без редагування

Запит для свіжої сесії або колеги. Після відповіді відкрий названі місця й прийми рішення самостійно.

```text
Перевір логіку docs/practice/06-delta.md для session-index. Це review підсумкової записки, не повторне приймання коду й не дозвіл щось реалізовувати.

Прочитай AGENTS.md, записку й лише потрібні джерела всередині цього проєкту. Не читай examples/, особисті логи або секрети. Не редагуй файли; не запускай тести, сервер, SDD, install, git write, push чи deploy.

Перевір пʼять речей:
1. Чи є джерело для кожного важливого факту; чи відсутній стартовий запис не відновлено з памʼяті.
2. Чи CANDIDATE_COMMIT і рішення узгоджені з docs/practice/05-verification.md (а якщо записки немає, з git log і docs/features/session-index/_review/); чи старі докази не приписано новій версії.
3. Чи один випадок не названо звичкою; чи немає числового порівняння різних анкет або непідтвердженого виграшу швидкості.
4. Чи висновок відрізняє спостереження, гіпотезу, перевірений механізм і реальне блокування. Якщо причини не доведено, це має бути видно.
5. Чи наступна дія посильна, має дату та спосіб перевірки; чи рефлексія не підміняє приймання всієї фічі.

Для кожного зауваження поверни місце в записці, що саме не підтверджено, потрібне джерело або запитання до мене. Якщо зауважень немає, назви обсяг і межі читання. Не вигадуй знахідку для заповнення звіту. Жодних правок файлів.
```

## Готово, коли

- [ ] Пʼять рядків порівняння заповнені з джерелами або чесним «початкового запису немає»; бали анкет і продуктивність не порівнювалися.
- [ ] Один висновок у §2 спирається на власний випадок, а причина позначена як перевірена або гіпотеза.
- [ ] §3 має одну наступну дію з датою та способом перевірки і окремо називає стан фічі за уроком 5.
