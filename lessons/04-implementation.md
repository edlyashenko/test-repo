# Урок 4. Виконуємо погоджений план

Теорія цього уроку є в уроці LMS; тут лише практика.

## Мета

Реалізувати `session-index` за власним планом з уроку 3 одним агентом у послідовному режимі з TDD: список сесій із дозволених метаданих має зʼявитися в тому самому застосунку. Перед кодом складаємо коротку карту виконання `docs/practice/04-workflow.md`, після першої задачі робимо контрольну паузу, наприкінці збираємо докази для уроку 5. Новий проєкт або інший кіт не потрібний.

## Що має бути готове

- Копія пакета з уроків 2 і 3: карта архітектури, `spec.md` з Test plan, `sad.md`, Accepted ADR, `tasks.json` і файли задач у `docs/features/session-index/`. Якщо документів ще немає, повернися до [уроку 3](03-specification.md); не запускай interview або survey заново лише для старту цього уроку.
- Обраний агент із SDD. Для Codex і Cursor користуйся [таблицею відповідників уроку 3](03-specification.md#якщо-обрано-codex-або-cursor); не запускай кілька агентів одночасно на тій самій копії.
- Розуміння, що виклики агента оплачуються за твоїм тарифом; час очікування у відео може бути скорочено монтажем.

Нижче десять кроків. У відео детально розбираємо першу задачу: як обрали її, чому впав тест і що підтвердив повторний запуск; після неї буде контрольна пауза. Решту плану можна виконати у власному темпі тим самим способом. Пауза після одного кроку не означає, що весь список реалізований: до перевірки фічі в уроці 5 переходимо, коли завершено всі її задачі.

## Кроки

### 1. Відкрий ту саму копію проєкту

У редакторі обери **File → Open Folder** і відкрий `agentic-engineering-mini-kit` з попередніх уроків. Через **Terminal → New Terminal** відкрий звичайний термінал у його корені:

```sh
git rev-parse --show-toplevel
git status --short
```

Перша команда має показати саме твою навчальну копію. Друга показує поточні зміни: не стирай їх і не завантажуй нову копію поверх цієї. Відкрий `docs/architecture-map.md`, а потім `docs/features/session-index/spec.md`. Виданий шаблон не замінює погоджену специфікацію.

- [ ] Відкрита моя копія з контекстом і документами попередніх уроків.

### 2. Перевір початковий стан

```sh
node --version
npm ci
npm run verify
```

Для пакета потрібен Node.js 24 LTS, підійде 22 або 26. У незміненому S0 є три початкові тести. Вони повинні пройти, але ще не доводять, що майбутній список працює. Збережи свій фактичний результат.

Якщо продовжуєш перервану реалізацію, тестів уже може бути більше. Спочатку звір стан задач і власні зміни. Не повертай проєкт до S0 заради числа «три» і не оголошуй початковим станом те, що вже змінилося.

- [ ] Знаю стан, з якого починаю; перевірка справді виконана.

### 3. Перечитай входи до реалізації

Відкрий у редакторі:

- `AGENTS.md`, `CONTEXT.md`, правила в `.claude/rules/` і карту проєкту;
- `docs/features/session-index/spec.md`, зокрема AC та розділ `Test plan`;
- `docs/features/session-index/sad.md` і погоджений ADR зі статусом `Accepted`;
- `docs/features/session-index/tasks.json` і Markdown-файли, названі в полях `file`.

Специфікація визначає потрібну поведінку, SAD пояснює технічний підхід, файли задач описують конкретні кроки. Знайди одну задачу, її критерій і заплановану перевірку: чи зрозуміло, що має змінитися та за чим це буде видно?

Залишаємо `.size=S` і `.route=standard`. В уроці 3 ми явно погодили навчальне скорочення: контракт HTTP і стани сторінки записані в SAD та відповідних задачах без окремих API/UI-документів. Уся погоджена поведінка залишається в обсязі реалізації. Якщо контракту немає, залежності суперечать одна одній або важливе питання лишилося відкритим, спочатку виправ підготовку. Порожні файли з потрібними назвами не зроблять план готовим.

- [ ] Можу пояснити наступну задачу та її перевірку; потрібні рішення погоджені.

### 4. Збережи точку перед змінами коду

SDD може сам створювати коміти, тому потрібен хеш до реалізації: інакше звичайний `git diff` наприкінці може бути порожнім, хоча агент уже змінив багато файлів.

SDD уже закомітив документи уроку 3 сам, по коміту на документ. У **Source Control** редактора переглянь, чи лишилось щось незакомічене, і збережи комітом лише погоджені документи підготовки. Нові файли відкрий окремо. Перед комітом виконай `npm run verify`; не додавай усе через `git add .`. Налаштування SDD можуть бути локальними й навмисно ігноруватися Git; не додавай їх примусово. Після збереження:

```sh
git branch --show-current
git status --short
git rev-parse HEAD
```

Збережи повний хеш. У наступному кроці він потрапить у поле `FEATURE_BASE_COMMIT` твоєї карти. Це нова точка перед реалізацією, не хеш до створення вимог у третьому уроці. Не змінюй її після першої задачі. Сторонні незакомічені зміни запиши, не привласнюй і не стирай.

- [ ] Є повний базовий хеш, назва гілки та запис початкового стану Git.

### 5. Підготуй коротку карту виконання

Відкрий Claude Code у корені пакета командою `claude` у shell. Якщо сесія з третього уроку ще відкрита, спочатку збережи рішення й почни свіжий контекст через `/clear`.

Надішли [запит A](#a-підготувати-карту-без-змін-коду), замінивши `FEATURE_BASE_COMMIT` на свій хеш. Агент створить `docs/practice/04-workflow.md` за [шаблоном](../templates/04-agentic-workflow-map.md). У карті мають бути посилання на план, виконавці кроків, входи й виходи, перевірки, дії при помилці та місце для фактичного стану. Другий список задач не потрібний. Попроси назвати першу доступну задачу з твого плану та пояснити її залежності; ідентифікатори не зобовʼязані збігатися з відео.

Тепер збережи карту й відкрий нову сесію без історії її створення. Передай [запит F](#f-перевірити-карту-до-реалізації): він просить перевірити передачу результатів, відповідальність, спільні ресурси та умови зупинки. Це перевірка способу виконання до коду, не ревʼю реалізації з уроку 5.

Прочитай зауваження. Погоджені правки внеси вручну або передай попередній сесії з дозволом змінити тільки карту. Повторно звір виправлені місця й запиши результат у карті. Якщо знахідок немає, збережи названі межі перевірки; вигадувати помилку для галочки не потрібно. Бюджет і налаштування уточнимо в кроці 6, тому до запуску C перевір також, що ці поля вже заповнені.

Закоміть `docs/practice/04-workflow.md` разом із документами підготовки через **Source Control** або в терміналі:

```sh
git add docs/practice/04-workflow.md docs/features/session-index/
git commit -m "docs: workflow map for session-index"
```

- [ ] Карта посилається на мій план; її перечитано у свіжій сесії, погоджені зауваження виправлено.

### 6. Налаштуй простий послідовний прохід

Надішли [запит B](#b-погодити-налаштування), додавши в те саме повідомлення команду чату:

```text
/sdd:config
```

Обираємо послідовну роботу одного агента з увімкненим TDD. Це дає змогу простежити весь цикл без додаткової координації. Ролі RED і GREEN не означають, що зараз створюються окремі ізольовані агенти.

Перечитай зміни в `.claude/sdd.local.md`. Запит змінює лише перелічені поля, зберігаючи решту, зокрема налаштування моделей і Git. Для перевірки використовуємо `npm run verify`: вона має запускати також потрібні файлові та HTTP-тести, вимкнення окремої Docker-стадії SDD цих перевірок не скасовує.

Запиши в карті власний бюджет часу або вартості й запусти таймер чи стеж за фактичним лічильником інструмента. Три звичайні повтори GREEN у SDD не є глобальним лімітом: далі можлива ескалація. Для вправи домовляємося про паузу після трьох невдалих спроб на одній задачі до зміни моделі або поділу задачі. За цією умовою стежиш ти; зовнішнього механізму, який гарантує таку зупинку, ми тут не налаштовували.

- [ ] Налаштування перечитано; розумію режим, перевірки, бюджет і межі автоматичних зупинок.

### 7. Пройди першу задачу й зроби паузу

Почни свіжий контекст. Надішли [запит C](#c-перша-задача-з-контрольною-паузою) разом із командою:

```text
/sdd:implement session-index
```

Перед кодом агент має показати режим і виявлені команди. Перевір, чи виконання послідовне, чи TDD увімкнено та чи команда перевірки відповідає `npm run verify`. Якщо бачиш інший режим або команду, зупини запуск і розбери налаштування.

Попросили паузу після першої завершеної задачі, але в SDD немає окремого прапорця «виконати лише одну». Це інструкція для керування уроком. Якщо інструмент не може її забезпечити, не запускай безконтрольний прохід; якщо вже продовжив, скористайся зупинкою поточної генерації та перевір стан.

Простеж за циклом. Спочатку має зʼявитися тест на потрібну поведінку та справжній RED. Помилка імпорту або неправильно написаний тест потребують виправлення самого тесту. Не проси агента дописати production-код лише для створення видимості RED. Якщо перевірка одразу зелена, зʼясуй, чи поведінка вже існує, чи тест нічого нового не перевіряє.

Потім агент додає код до GREEN, за потреби спрощує його й запускає повну перевірку. Знайди один і той самий тест до та після зміни. Запиши точний рядок падіння й фактичний результат. Статус done допустимий лише після потрібного gate; спосіб коміту залежить від чинного `auto_commit`.

- [ ] Є фактичний розбір першої задачі та контрольна пауза: RED → GREEN → gate або пояснення вже наявної поведінки й погоджене рішення, як узгодити з нею план. Штучного RED немає.

### 8. Продовж решту погодженого плану

Перечитай diff першої задачі та її статус у `docs/features/session-index/tasks/tracker.md`. Перевір, чи агент залишився в межах потрібних файлів і не змінив вимоги заради зеленого тесту. На цьому місці можна закінчити навчальну сесію, записавши частковий результат у карті.

Щоб продовжити, почни свіжий контекст і передай [запит D](#d-продовжити-збережений-прохід) разом із тією самою командою:

```text
/sdd:implement session-index
```

Агент має звірити tracker із кодом і комітами та обрати наступну незавершену задачу, чиї залежності готові. Не видаляй виконані задачі з `tasks.json` і не змінюй їхні ID для повторного запуску. Якщо tracker та код розійшлися, спочатку зʼясуй причину.

Під час роботи з файлами використовуємо синтетичні тимчасові теки й контрольовані дати. Тести не повинні звертатися до особистих логів, читати JSONL або залежати від shell-команд для підрахунку файлів. Видані fixtures не переписуємо для проходження тесту. Кількість нових тестів визначає твій план; готового числа для S1 немає.

- [ ] Усі задачі реалізовано або частковий стан і причина паузи явно записані.

### 9. Перевір результат своїми командами

```sh
npm run verify
npm run demo
```

Відкрий [http://127.0.0.1:4180](http://127.0.0.1:4180), а звідти перейди на погоджену в SAD сторінку списку, якщо вона має окрему адресу. Адресу бери зі свого контракту: приклад із відео його не змінює.

Після всіх задач мають бути рядки з проєктом, позначкою «похідний», розміром і часом зміни за погодженими правилами. У виданих даних шість основних сесій у трьох проєктах; шість рядків очікуємо лише тоді, коли погоджений ліміт уміщує їх усі. До завершення задач сторінки список може ще не відображатися: тоді маємо частковий результат, фіча ще не готова.

Запиши фактичний результат і зупини сервер через **Ctrl+C**. Для вправи використовуй саме `demo`: він явно підключає навчальні fixtures. Якщо порт зайнятий, зупини свій попередній запуск; невідомі процеси не завершуй навмання.

- [ ] Є фактичний вивід перевірки й результат перегляду сторінки або чесний запис, що ще не працює.

### 10. Збережи докази для уроку 5

У командах нижче заміни `FEATURE_BASE_COMMIT` повним хешем зі своєї карти; `..HEAD` залиш. Це підстановка тексту, не готова змінна shell.

```sh
git log --oneline FEATURE_BASE_COMMIT..HEAD
git diff FEATURE_BASE_COMMIT..HEAD
git diff
git diff --cached
git status --short
```

Перші дві команди покажуть коміти й закомічені зміни агента. Наступні покажуть незакомічену роботу. Нові невідстежувані файли відкрий окремо. Передай [запит E](#e-звірити-фактичний-стан-без-редагування) у свіжий контекст і за його відповіддю сам онови §4 карти. Це звірка стану, не незалежне приймальне ревʼю.

Збережи точні шляхи до задач, результати команд, незавершене й наступну дію в `docs/practice/04-workflow.md`. Окремий handoff-файл не потрібний. Автоматично запускати `review`, `ship` або розгортання не треба: перевірку всієї реалізації розберемо в уроці 5.

- [ ] Можна відновити роботу без переказу чату; статус усієї фічі не підмінений успіхом однієї задачі.

## Готові запити

Ці запити продовжують твою власну підготовку `session-index` з уроку 3. Команди SDD вводимо в чат Claude Code, не у звичайний термінал. Для B, C і D скопіюй текст запиту та команду під ним в одне повідомлення. Перед C, D і E почни свіжий контекст після збереження результатів. Запит F використай у новій сесії одразу після A. Якщо SDD поводиться інакше, ніж тут описано, зупинись на конкретній розбіжності, не заповнюй відсутні входи порожніми файлами і не обходь перевірку готовності.
