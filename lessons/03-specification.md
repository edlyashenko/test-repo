# Урок 3. Від специфікації до плану

Теорія цього уроку є в уроці LMS; тут лише практика.

## Мета

Провести фічу `session-index` через пʼять стадій SDD: `specify` → `clarify` → `design` → `tasks` → `plan-tests`, і отримати погоджені документи в `docs/features/session-index/`. Сесія тут означає розмову з агентом для розробки. Початковий стан S0 запускається, але списку ще немає; код почнемо змінювати в уроці 4.

У `docs/roadmap.md` крок 1 описано повністю, як дашборд; у курсі робимо лише його перший зріз S1 із запиту A, таблицю сесій із дозволених метаданих, а решта рядка лишається кроку.

## Що має бути готове

- Копія пакета з уроку 2 з перевіреною `docs/architecture-map.md`. У початковому пакеті цієї карти навмисно немає; якщо копії ще немає, спочатку пройди [урок 2](02-context-engineering.md), а interview не запускай: задум задачі вже є в [README](../README.md).
- Node.js 22 або 24, Git, обраний агент із SDD. На екрані використовується Claude Code; відповідники для Codex і Cursor є в кінці уроку.
- Наявну `.claude/sdd.local.md` не перезаписуй: це спільний шлях налаштувань SDD, навіть якщо працюєш через інший агент.

Нижче десять кроків. Після кожного можна поставити позначку й зупинитися. Очікування відповідей агента у відео може бути скорочене монтажем; повний прохід займає більше часу. SDD створює документи послідовно, але їхній зміст усе одно потрібно прочитати: кількість створених файлів не доводить, що задача готова.

## Кроки

### 1. Відкрий свою копію пакета

Відкрий у редакторі теку `agentic-engineering-mini-kit` з другого уроку: **File → Open Folder**, потім **Terminal → New Terminal**. У корені видно `package.json`, `README.md` і `AGENTS.md`. Тут виконуй усі shell-команди нижче.

Якщо копії ще немає, завантаж її з термінала у власній теці для навчальних проєктів:

```sh
git clone https://github.com/genkovich/agentic-engineering-mini-kit.git
cd agentic-engineering-mini-kit
```

Це лише для нової копії. Наявну теку не перезаписуй. Репозиторій приватний: помилка 404 не означає, що треба шукати інший кіт.

- [ ] Відкрита саме моя навчальна копія; карта після survey є й перевірена.

### 2. Переконайся, що початкова версія працює

```sh
node --version
git rev-parse --show-toplevel
git status --short
npm ci
npm run verify
```

Друга команда має назвати корінь саме цього пакета; якщо показано батьківський репозиторій, це помилка. Для незміненого S0 перевірка очікувано завершується трьома успішними тестами. Збережи свій фактичний вивід; ці тести ще не перевіряють список.

```sh
npm run demo
```

Відкрий [http://127.0.0.1:4180](http://127.0.0.1:4180). Напис `No slice is wired up yet.` означає, що бачиш початкову оболонку без списку. Зупини сервер через **Ctrl+C**. Якщо порт зайнятий, зупини власний попередній запуск; невідомі процеси не завершуй навмання. Для вправи потрібен саме `demo`: він задає шлях до синтетичних файлів пакета й порт 4180. `npm start` без налаштувань може звернутися до особистої теки Claude, тому тут його не використовуємо.

- [ ] Є фактичний результат verify і початкова сторінка; особисті дані не використовуються.

### 3. Відкрий агента й збережи точку відліку

Прочитай [AGENTS.md](../AGENTS.md), [словник](../CONTEXT.md), [roadmap](../docs/roadmap.md), [правила зон](../.claude/rules/) та власну карту. У звичайному терміналі відкрий Claude Code:

```sh
claude
```

Перевір показану теку та наявність `/sdd:specify` у списку команд. Якщо команди немає, повернися до встановлення з уроку 2. Виклики моделі оплачуються за твоїм тарифом; дашборд модель не викликає.

SDD може сам створювати коміти документів. Тому перед першою стадією збережи погоджену роботу другого уроку. Якщо карта ще не закомічена, в окремому shell-терміналі виконай:

```sh
git diff -- docs/architecture-map.md
git add -- docs/architecture-map.md
git diff --cached
npm run verify
git commit -m "Keep verified architecture map"
```

Новий невідстежуваний файл відкрий також у редакторі: перша команда його не покаже. Перед комітом у staged-змінах мають бути тільки погоджені файли. Незрозумілі сторонні зміни спочатку розбери, не додавай усе одним `git add .`.

Збережи початковий хеш:

```sh
git rev-parse HEAD
```

Скопіюй повний результат у нотатки поза пакетом. Далі `BASE_COMMIT` означає цей хеш до початку уроку 3; це позначення для заміни, не готова змінна термінала. Збережи також початковий `git status --short`, щоб відрізнити давні незакомічені зміни від роботи уроку.

- [ ] SDD доступний; початковий хеш і стан Git збережено.

### 4. Погодь вимоги через specify

Від цього кроку команди SDD вводяться **в чат агента**, не в shell. Скопіюй [запит A](#a-погоджуємо-вимоги-specify) і додай до того самого повідомлення команду; так само поєднуй запит і команду на наступних стадіях:

```text
/sdd:specify session-index
```

Маршрут адаптовано до контракту SDD 2.3.0; інша встановлена версія може мати інші вимоги, тож якщо скіл відмовляється продовжувати, прочитай причину й не підмінюй відсутні документи порожніми файлами.

Агент прочитає поточний контекст і поставить запитання. Відповідай за змістом задачі: наприклад, «останні» потребує і правила сортування, і ліміту. Якщо рішення невідоме, попроси пояснити два варіанти та їхні наслідки.

Відкрий створений `docs/features/session-index/spec.md`. У ньому мають бути потрібний результат, межі зміни та перевірні критерії. Майбутній список показує проєкт, розмір і час зміни, від свіжих записів до старих.

Назва проєкту відновлюється з назви теки приблизно, тому потрібна позначка «похідний». У наборі є тека `-Users-demo-sources-checkout-api`: роздільники шляху перетворено на дефіси, але в самій назві `checkout-api` дефіс теж міг бути від початку. За самою назвою теки неможливо довести правильний початковий шлях.

У наборі є шість основних сесій у трьох проєктах. Шість рядків очікуємо, якщо ліміт уміщує їх усі. Вкладені `subagents/` і `tool-results/` не додають рядків. Читаємо лише метадані файлів безпосередньо в теці проєкту, не вміст JSONL. Заголовки розмов, таймлайн, токени й друге джерело не входять у цю зміну.

Окремо погодь порожній стан, помилки доступу, неправильний ліміт, однаковий час зміни та символічні посилання. Символічне посилання може вести за межі навчальної теки, тому це також питання безпечного читання. Наявні health-відповідь і HTML-оболонка з її політикою безпеки мають зберегтися.

[Шаблон перевірки](../templates/03-feature-spec.md) допомагає перечитати вимоги. Не копіюй його як другу специфікацію: чинний документ один, `spec.md`.

- [ ] Можу пояснити свої критерії; невідоме не замінене здогадками агента.

### 5. Знайди неоднозначності через clarify

Спочатку збережи погоджені рішення у spec. Почни свіжий контекст через `/clear` і передай [запит B](#b-шукаємо-різні-прочитання-clarify) разом із командою:

```text
/sdd:clarify session-index
```

Просимо незалежно прочитати вимоги й показати два різні результати, які формально підходять під одне формулювання. Наприклад, «останні сесії» може означати весь відсортований список або обмежену кількість. Це приклад способу перевірки, не зауваження, яке обовʼязково знайдеться у твоєму файлі.

Для справжньої неоднозначності погодь рішення й відкрий змінене місце у spec. Важливо виправити саме вимогу; відповідь лише в чаті наступна сесія не побачить. Якщо зауважень немає, попроси назвати перевірені місця. Штучну помилку для вправи створювати не потрібно.

- [ ] Важливі неоднозначності вирішено; актуальні рішення збережено у spec.

### 6. Підготуй технічне рішення через design

Почни свіжий контекст і передай [запит C](#c-погоджуємо-технічне-рішення-design) разом із командою:

```text
/sdd:design session-index --depth=easy
```

Відкрий `docs/features/session-index/sad.md`. SAD пояснює, як потрібні частини працюватимуть разом: звідки беремо метадані, як сервер передає їх сторінці та що відбувається при помилці. Карта другого уроку описує наявний код, SAD описує погоджену зміну.

Для цієї вправи свідомо використовуємо навчальне відхилення від повного процесу SDD: `.size=S`, `.route=standard`, без окремих стадій `ux-flows`, `api`, `screens`, `sequences`, `data-model`. Файли розміру й маршруту вже є в пакеті. Це не автоматичне правило SDD для будь-якої малої фічі: новий HTTP-маршрут та інтерфейс у нас є, тому їхній контракт, потік і стани все одно погоджуємо та записуємо в SAD. Запит C пояснює агенту це скорочення.

На початку SAD у `target_surfaces` має бути `web-frontend` разом із `backend-service`. Перед наступною стадією потрібен щонайменше один погоджений ADR зі статусом `Accepted` у `docs/features/session-index/adr/`. У нашому коді є реальне питання: підключати перелік через реєстр джерел чи зберегти прямі імпорти адаптера в сервері. Якщо design не зафіксував погоджений вибір, залишайся на цьому кроці й попроси записати реальне рішення:

```text
/sdd:decide-adr session-index session-index-integration
```

Не вигадуй ADR лише для проходження перевірки. Режим easy спрощує розмову, але не обіцяє миттєвого створення всього пакета.

- [ ] Розумію технічний підхід; контракт і стани описані; реальний ADR погоджено.

### 7. Отримай невеликі задачі через tasks

Після збереження рішень почни свіжий контекст і передай [запит D](#d-розбиваємо-роботу-на-задачі-tasks) разом із командою:

```text
/sdd:tasks session-index
```

Відкрий `docs/features/session-index/tasks.json` і файли в `docs/features/session-index/tasks/`. JSON допомагає агенту знаходити задачі й залежності, а Markdown пояснює роботу конкретної задачі. Один формат не замінює інший.

Знайди один критерій зі spec і подивися, яка задача його забезпечує. Прочитай, що вона змінює та як перевірятиметься. Якщо потрібні і дані, і сторінка, обидві частини мають потрапити в план. Спільний файл у двох задачах це привід перевірити порядок роботи; запускати їх паралельно без такої перевірки не можна.

Точний HTTP-контракт у нас записаний у SAD. Запит D вимагає перенести потрібну частину до відповідних задач із посиланням на джерело. Відсутність окремого OpenAPI-файла не означає відсутності API.

- [ ] Є tasks.json і реальні описи задач; бачу звʼязок із критеріями та порядок роботи.

### 8. Домовся про перевірки через plan-tests

Почни свіжий контекст і передай [запит E](#e-плануємо-перевірки-plan-tests) разом із командою:

```text
/sdd:plan-tests session-index
```

Для виданого розміру S результат лежить у розділі `Test plan` всередині `spec.md`. Окремий `test-plan.md` не потрібен. Для кожного AC знайди названу перевірку, її дані та очікуваний результат. Помилки й межі читання теж мають свої випадки.

Агент запропонує рівні перевірок; попроси пояснити, що саме вони доводять. Для файлів потрібна контрольована тимчасова тека із синтетичними даними та відомими датами зміни: не можна випадково перевіряти сортування за датою завантаження ZIP. Прибирання тимчасових даних також входить у план. Сьогодні тести не пишемо й не називаємо їх успішними.

- [ ] Кожен критерій має зрозумілу майбутню перевірку, включно з помилками й межами.

### 9. Дай новій сесії звірити документи

Збережи всі рішення, почни свіжий контекст і надішли [запит F](#f-перечитуємо-пакет-перед-реалізацією), замінивши в ньому `BASE_COMMIT` власним початковим хешем. Це звичайна перевірка документів без редагування, не команда ревʼю готового коду.

Агент покаже конкретні суперечності між spec, SAD, задачами та планом перевірок: чи збігається ліміт, чи не зник порожній стан, чи є задача для видимої сторінки. Він також перевірить службові поля SDD; заучувати їх не потрібно.

Зауваження прочитай і окремо погодь виправлення. Потім перевір змінені місця ще раз. Питання, від яких залежить правильність або безпека цієї фічі, потрібно закрити до реалізації. Майбутні побажання можна залишити поза обсягом із поясненням.

- [ ] Перевірено звʼязки документів; блокувальних питань для S1 не залишилося.

### 10. Перевір межі змін і збережи результат

У shell-терміналі виконай, замінивши `BASE_COMMIT` збереженим хешем:

```sh
npm run verify
git log --oneline BASE_COMMIT..HEAD
git diff BASE_COMMIT
git status --short
```

Порівняння від початкового коміту покаже також зміни, які SDD уже закомітив. Нові невідстежувані файли видно в status; відкрий їх окремо. Порожній звичайний `git diff` без початкового хешу не доводить, що код не змінювався.

Результат цього уроку: погоджений `spec.md` із Test plan, `sad.md`, Accepted ADR, `tasks.json` та Markdown-файли задач. Службові файли SDD можуть додатися, але їх теж переглянь. Runtime-код, залежності, тести й навчальні дані залишаються незмінними. Три успішні тести підтверджують лише S0.

Підсумок перевірки можна залишити в чаті або нотатках. Окремий handoff-файл не потрібен; чинні рішення вже лежать у документах фічі. Наступний крок у четвертому уроці: `/sdd:implement session-index`. Сьогодні його не запускай. Файли з `examples/` не потрібні для проходу; агент не читає й не копіює їх без твого окремого дозволу.

- [ ] Можу пояснити майбутню поведінку; документи збережено; реалізація ще не почалася.

## Якщо обрано Codex або Cursor

Це відповідники для встановлення SDD скриптом, описаного в уроці 2. Якщо назви у твоїй інсталяції відрізняються, перевір список доступних скілів. Не встановлюй другий спосіб поверх першого навмання.

| Дія | Claude Code | Codex після script-install | Cursor: вибір у меню / |
|---|---|---|---|
| Вимоги | `/sdd:specify session-index` | `$sdd-specify session-index` | `sdd-specify` + `session-index` |
| Уточнення | `/sdd:clarify session-index` | `$sdd-clarify session-index` | `sdd-clarify` + `session-index` |
| Технічне рішення | `/sdd:design session-index --depth=easy` | `$sdd-design session-index --depth=easy` | `sdd-design` + `session-index --depth=easy` |
| Запис рішення, якщо потрібен | `/sdd:decide-adr session-index session-index-integration` | `$sdd-decide-adr session-index session-index-integration` | `sdd-decide-adr` + `session-index session-index-integration` |
| Задачі | `/sdd:tasks session-index` | `$sdd-tasks session-index` | `sdd-tasks` + `session-index` |
| План перевірок | `/sdd:plan-tests session-index` | `$sdd-plan-tests session-index` | `sdd-plan-tests` + `session-index` |
| Свіжий контекст | `/clear` | `/new` | Новий чат |

Рядки з `$sdd-` вводяться в чат Codex, не в shell. Перед новим контекстом зберігай рішення у файлах: команди зміни контексту не замінюють збереження. Ті самі запити A–F підходять для обраного агента; змінюється лише спосіб запуску стадії.

## Готові запити

Відкрий чат агента в корені своєї копії пакета. Для стадій від A до E скопіюй запит і команду під ним в одне повідомлення. Окреме «можна починати?» перед кожною стадією не потрібне. Коли SDD запитає про поведінку фічі або важливе рішення, прочитай варіанти й дай відповідь. Перед наступною стадією відкрий створені файли та збережи погоджені зміни, потім почни свіжий контекст: кожен запит знову називає потрібні джерела, переказувати попередню розмову не потрібно.

### A. Погоджуємо вимоги: specify

