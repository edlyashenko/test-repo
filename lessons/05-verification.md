# Урок 5. Три погляди, фікс, правило й hook

Теорія цього уроку є в уроці LMS; тут лише практика.

## Мета

Зафіксувати кандидата власної `session-index` з уроку 4, подивитись на нього трьома незалежними поглядами, виправити одну погоджену знахідку, спростити код і перенести урок у пайплайн: рядок правила в `AGENTS.md` і Stop-hook, який ганяє `npm run verify` на кожній зупинці агента. Зелені тести та перегляд сторінки вже були в уроці 4; ми не починаємо перевірку з нуля. Рішення про приймання наприкінці залишиться за тобою.

## Що має бути готове

- Реалізація з уроку 4: усі погоджені задачі завершені, стан `docs/features/session-index/tasks/tracker.md` відповідає коду, у `docs/practice/04-workflow.md` є `FEATURE_BASE_COMMIT`. Якщо в уроці 4 була пауза після першої задачі, спочатку [продовж реалізацію](04-implementation.md#8-продовж-решту-погодженого-плану). У виданому S0 списку ще немає; його три стартові тести не є доказом готовності S1.
- Обраний агент із SDD. Вбудовані `/code-review`, `/security-review` і `/simplify` є лише в Claude Code; для Codex і Cursor відповідники в кінці уроку.
- Усі shell-команди виконуємо в корені своєї копії `agentic-engineering-mini-kit`. `FEATURE_BASE_COMMIT` і `CANDIDATE_COMMIT` це місця для підстановки повних хешів, не змінні shell.

Нижче 12 кроків; у відео вони злиті в пʼять сцен. Кількість тестів, знахідок і назва маршруту у тебе будуть свої, з власних документів. Новий репозиторій, повторний interview і ще одна специфікація не потрібні.

### 2. Зафіксуй кандидата

З карти уроку 4 візьми `FEATURE_BASE_COMMIT`: повний хеш до реалізації. Не підставляй замість нього нинішній `HEAD` і не вгадуй межу за назвою `main`.

У **Source Control** переглянь зміни, нові файли відкрий окремо. Вибери лише свої погоджені зміни реалізації, тестів і документів, виконай **Stage Changes**, введи короткий опис і натисни **Commit**. **Sync**, **Push** і **Publish Branch** для вправи не натискай. Якщо незакомічених змін немає, зайвий коміт не потрібний. Потім:

```sh
git status --short
git rev-parse HEAD
git log --oneline FEATURE_BASE_COMMIT..CANDIDATE_COMMIT
git diff --stat FEATURE_BASE_COMMIT..CANDIDATE_COMMIT
```

Статус має бути порожнім. Повний хеш `HEAD` це `CANDIDATE_COMMIT`: версія-кандидат на приймання. Далі код, тести, вимоги й налаштування перевірок не змінюємо, поки збираємо докази для цього хеша. Дві останні команди мають показати всю зміну фічі разом із комітами агента; порожній diff там, де очікується реалізація, означає, що межі треба перевірити.

- [ ] Є повні базовий і кандидатний хеші; зрозуміло, які саме зміни перевіряємо.

### 3. Gate і екран

На зафіксованому кандидаті:

```sh
npm run verify
echo $?
```

`echo $?` показує код завершення попередньої команди; виконуй його одразу після verify. У PowerShell замість нього введи `$LASTEXITCODE`. Нуль означає, що набір завершився успішно, і не більше: пропущені тести і `todo` прочитай у підсумку окремо, вони критерій не приймають.

Потім у другому терміналі:

```sh
npm run demo
```

Відкрий [http://127.0.0.1:4180](http://127.0.0.1:4180), а звідти сторінку списку за своїм SAD. Для HTTP знайди точні метод, шлях і параметри у своєму SAD і перевір погоджений правильний і неправильний ліміт; код відповіді й тіло видно в **Developer Tools → Network**. Збережи фактичні результати й зупини сервер через **Ctrl+C**. `npm start` тут не використовуємо: demo працює на виданих fixtures.

- [ ] Є свіжий gate кандидата з кодом завершення, перегляд сторінки й HTTP за своїм контрактом; skipped і todo не видані за пройдені перевірки.

Відкрий чат агента в корені пакета й надішли [запит A](#a-записка-перевірки-з-реальних-виводів) разом із виводом кроку 3: хеші, підсумок verify з кодом завершення, що побачив на сторінці й у HTTP. Неперевірене має бути позначене прямо; вигаданих результатів у записці бути не може.

### 5. Перший погляд: ревʼю за spec

Почни свіжу сесію без історії виконавця: `/clear`. Надішли [запит B](#b-незалежний-перегляд-зафіксованої-версії) разом із командою:

```text
/sdd:review session-index
```

Перед переглядом рецензент має назвати обидва хеші й обсяг diff. Поточний `HEAD` має дорівнювати `CANDIDATE_COMMIT`. Якщо база визначилась інакше, спочатку виправ обсяг запиту. Перегляд іде у дві стадії: відповідність кожному AC, потім якість і ризики. Рецензент код не змінює; звіт лягає у `docs/features/session-index/_review/`. Відкрий створений файл: для кожної знахідки потрібні `file:line`, критерій, відтворення і наслідок; для вердикту потрібні межі.

- [ ] Звіт першого погляду стосується точного кандидата й усієї зміни; вердикт і межі прочитано.

### 6. Другий погляд: коректність коду

Знову `/clear`. У Claude Code запусти вбудований code review на явному рівні й явному діапазоні з повними хешами (три крапки між ними):

```text
/code-review medium FEATURE_BASE_COMMIT...CANDIDATE_COMMIT
```

Без цілі команда дивиться на коміти попереду upstream, якого в навчальній копії може не бути. На рівні `medium` знахідок менше, але впевненіших; `high` як другий прогін необовʼязковий. `--fix` не додавай: рішення на кожну знахідку ухвалюєш ти на кроці 8. Збережи вивід у нотатки або в §4 записки.

У Codex і Cursor вбудованої команди немає: надішли [запит C](#c-другий-і-третій-погляд-без-вбудованих-скілів) у свіжій сесії; спершу він дає блок «коректність».

- [ ] Є другий погляд на той самий діапазон; знахідки або «не знайдено в обсязі» записані.

### 7. Третій погляд: безпека

Знову `/clear`:

```text
/security-review
```

Це одноразовий прохід по змінах на гілці: перевірка входу, авторизація, секрети, інʼєкції, витік даних. На нашому невеликому застосунку список часто порожній. «Нічого не знайдено в перевіреному обсязі» це результат: запиши обсяг і класи, які команда дивилась. У Codex і Cursor це блок «безпека» того самого запиту C.

- [ ] Є третій погляд на той самий діапазон з обсягом і класами.

### 8. Рішення на кожну знахідку

Збери знахідки трьох поглядів у §4 записки або в нотатки: спочатку таблиця «Погляд | Інструмент | Обсяг | Знахідок | Звіт», потім таблиця знахідок. Дублікати між поглядами познач як одну. На кожну знахідку запиши рішення: виправити зараз, відкласти з причиною, власником і строком, або відхилити з доказом. Порушення погодженого AC чи межі даних не можна сховати під словом «потім» і прийняти фічу без змін. Впевнений тон рецензента без відтворення доказом не є: відтвори сам.

- [ ] Кожна знахідка трьох поглядів має рішення людини; дублікати позначені.

### 9. Один фікс

Обери одну погоджену знахідку. Надішли [запит D](#d-виправити-одну-погоджену-знахідку) разом із командою:

```text
/sdd:fix session-index
```

Fix відтворює симптом, робить тріаж (регресія, помилка spec чи прогалина), пише pinning-тест із правильним RED і цитує рядок падіння, потім робить мінімальний фікс до GREEN, проганяє gate і пише `docs/features/session-index/_fixes/<дата>-<slug>.md`. Зміну spec він показує до застосування; погоджуєш її ти. Після коміту це новий кандидат:

```sh
npm run verify
git rev-parse HEAD
```

Новий хеш запиши в §1 як поточного кандидата, `FEATURE_BASE_COMMIT` не змінюється. Потім `/clear` і повторний `/sdd:review session-index` на зачеплені файли; зачеплені сценарії сторінки й HTTP повтори руками. Старий звіт лишається історією старої версії.

Якщо знахідок не було або всі відхилені з доказом, крок пропускаєш: у §4 запиши «не знайдено в перевіреному обсязі» з межами. Вигадувати дефект для завершення уроку не потрібно.

- [ ] Погоджена знахідка виправлена з GOOD red і записом у `_fixes/`, або крок пропущений із чесним записом; новий кандидат має свіжий gate і повторний погляд.

### 10. Спрощення на чистому дереві

Крок необовʼязковий. Після коміту фіксу, коли `git status --short` порожній, у Claude Code:

```text
/simplify
```

Це окремий прохід за чотирма питаннями: перевикористання, спрощення, ефективність, висота абстракції. Багів він не шукає і сам править дерево, тому одразу:

```sh
git diff
```

Кожну правку лишаєш або відкидаєш. Потім `npm run verify` і коміт погодженого, або `git restore .`, якщо правки не потрібні. У Codex і Cursor надішли [запит E](#e-спростити-без-зміни-поведінки): він має пояснити кожну зміну і назвати тест, який доводить еквівалентність.

- [ ] Спрощення прочитано в diff і прийнято або відкинуте; після нього verify зелений.

### 11. Урок у пайплайн: правило й hook

Надішли [запит F](#f-правило-й-hook-з-фактичної-знахідки). Агент читає `_fixes/` і `_review/` і пропонує одне речення-правило для розділу «Запуск і перевірки» в `AGENTS.md`. Вставляєш його сам: інструкції для агента пише людина. Приклад із знахідки #1 журналу лектора: «Числові параметри запиту (`limit` тощо) розбирай через `Number()` і приймай лише цілі в погоджених межах: `parseInt` бере префікс, `3abc` стає 3. На кожне таке правило один тест із невалідним значенням.»

Правило це прохання. Примус дає hook. У пакеті лежить `.claude/settings.example.json` і `scripts/verify-hook.mjs`: на кожен `Stop`, тобто коли агент вважає роботу завершеною, hook запускає `npm run verify`; на зеленому повертає 0 і агент зупиняється, на червоному повертає код 2 з хвостом виводу в stderr, і агент мусить виправити причину. Лише код 2 блокує; його stderr іде моделі. Підключи:

```sh
cp .claude/settings.example.json .claude/settings.json
echo '{"stop_hook_active":false}' | node scripts/verify-hook.mjs; echo $?
```

Очікуємо 0. Тепер контрольний провал: зламай один assert у будь-якому файлі `test/`, повтори другий рядок, очікуємо 2 і текст «Не зупиняйся» у stderr. Поверни файл:

```sh
git restore test/
echo '{"stop_hook_active":false}' | node scripts/verify-hook.mjs; echo $?
```

Знову 0. У Claude Code команда `/hooks` показує підключений Stop-hook. Файл `settings.json` шариться в репо, локальні правки тримай у `settings.local.json`. Без контрольного провалу блокування не доведене; сам факт наявності файла нічого не гарантує.

Для Codex і Cursor: те саме правило в `AGENTS.md`, а замість hook сніпет `.git/hooks/pre-commit` з розділу нижче або verify руками з позначкою в §2 «Hook у репо».

- [ ] Рядок правила в `AGENTS.md`; hook підключений; контрольний провал дав 2, після відновлення 0; результат записаний у §2.

### A. Записка перевірки з реальних виводів

```text

docs/practice/04-workflow.md, мої spec.md, sad.md, Accepted ADR,
tasks.json і tasks/tracker.md у docs/features/session-index/.
Звір стан задач із кодом. Якщо фіча часткова, назви незавершене

Ось мої фактичні виводи (нічого з них не змінюй і не доповнюй):
FEATURE_BASE_COMMIT: <повний хеш з карти уроку 4>
CANDIDATE_COMMIT: <повний хеш після коміту>

<що побачив на сторінці та у відповіді HTTP на правильний і неправильний ліміт>

Створи лише docs/practice/05-verification.md за
templates/05-verification-canvas.md, збережи пʼять секцій шаблону.
```
